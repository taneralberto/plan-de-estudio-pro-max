# 1.1 — Debugging y Evidencia

> **Estado:** `DIAGNÓSTICO ★` · Unidad 1 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** poder ejecutar y probar un backend local.
> **Cierre:** si apruebas el diagnóstico o estudias el hueco, cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Encontrar la causa de un fallo mediante hipótesis y evidencia, corregirla una vez en el lugar compartido y demostrar que el síntoma no regresó. Debugging no es usar una herramienta concreta ni evitar `console.log`: es reducir incertidumbre sin cambiar cosas al azar.

## Orientación

**Qué debes lograr:** reproducir un bug, aislar su causa y demostrar un arreglo acotado sin regresión.

**Cómo abordarlo:** registra hechos antes de interpretar, predice antes de inspeccionar y revisa callers antes de editar.

**Entregarás:** un diff acotado, un test de regresión y un informe breve con la cadena de evidencia.

**Investiga fuera solo si:** una hipótesis concreta exige una herramienta que no dominas; no hagas un tour de debuggers.

## Diagnóstico — 30 a 60 minutos

**Contexto proporcionado:** un bug de backend que no conozcas, tomado de trabajo reproducido sin datos privados, un proyecto propio o una rama con un defecto sembrado sin revelarte la causa.

**Decisiones que debes tomar:** qué hipótesis probar primero, qué evidencia la falsaría, dónde corregir la causa compartida y qué riesgo o rollback queda.

Antes de editar:

1. escribe comportamiento esperado y observado;
2. registra el comando, request o dato que lo reproduce;
3. reduce el caso hasta que falle de forma consistente;
4. formula al menos dos hipótesis falsables y ordénalas por evidencia/coste de prueba;
5. prueba una hipótesis con logs, debugger, stack trace, test o historial;
6. localiza los callers y caminos hermanos antes de elegir dónde corregir;
7. crea un test de regresión que falle antes del cambio y pase después;
8. explica la cadena causal y el riesgo residual.

Si puedes completar el resultado mínimo del [ROADMAP](../ROADMAP.md), no repitas tutoriales de herramientas. Si no, estudia únicamente el paso donde perdiste evidencia y repite con otro fallo pequeño.

## Método mínimo

### 1. Observar sin interpretar

Separa hechos de conclusiones:

```text
Hecho: POST /reservations devuelve 500 con quantity=0.
Conclusión todavía no probada: la validación no funciona.
```

Conserva el error exacto, input, versión y entorno. “No funciona” no es reproducible.

### 2. Reducir

Elimina ruido hasta encontrar el request, test, función o cambio mínimo que conserva el fallo. Si el bug es intermitente, registra frecuencia y condiciones en vez de llamarlo aleatorio.

### 3. Formular una hipótesis falsable

Una hipótesis útil predice una observación:

```text
Si el DTO transforma 0 en undefined, el valor ya será undefined al entrar al servicio.
```

Decide qué observar antes de ejecutar. Si el resultado contradice la predicción, descarta la hipótesis y actualiza el modelo.

### 4. Elegir la herramienta por la pregunta

| Pregunta | Evidencia mínima útil |
|---|---|
| ¿Qué camino ejecutó? | stack trace, breakpoint o log temporal con contexto |
| ¿Dónde cambió el valor? | watch/breakpoint, aserción o logs antes/después |
| ¿Qué cambio introdujo el fallo? | `git log`, `git diff` o `git bisect` |
| ¿Por qué falla solo un test? | ejecutar ese test con debugger y controlar datos/tiempo |
| ¿El arreglo cubre otros callers? | búsqueda de referencias y test de un camino hermano |

`console.log`, logs estructurados y breakpoints son opciones válidas. Usa la que produzca evidencia con menor perturbación y retira instrumentación temporal que no aporte a operación.

### 5. Corregir la causa y verificar

Distingue:

- **síntoma:** lugar donde el fallo se vuelve visible;
- **causa inmediata:** estado o operación que lo dispara;
- **causa raíz accionable:** condición compartida que permitió llegar a ese estado.

Prefiere un arreglo en la función, constraint o límite común por donde pasan los callers afectados. No “limpies” código vecino mientras diagnosticas: un diff pequeño hace más clara la causalidad y el rollback.

Verifica en este orden:

1. el test falla sin el arreglo;
2. pasa con el arreglo;
3. los tests relacionados siguen pasando;
4. el reproducer negativo ya no falla y, cuando haya callers compartidos, un camino hermano sigue cubierto;
5. el diff contiene solo cambios explicables por la causa.

## Entregable y evidencia

- **Artefacto:** diff acotado, test de regresión e informe breve.
- **Evidencia:** baseline reproducible, predicción previa, prueba de hipótesis, test rojo→verde y tests relacionados en verde.
- **Caso negativo:** el reproducer o test que falla sin el arreglo; un camino hermano demuestra alcance compartido, pero no lo sustituye.
- **Límite o riesgo:** incertidumbre residual y rollback del cambio.

Usa esta plantilla para el informe:

```md
Esperado / observado:
Reproducción:
Hipótesis y predicción:
Prueba y resultado:
Causa:
Cambio:
Regresión:
Callers o caminos revisados:
Riesgo residual / rollback:
```

Puede vivir en la descripción de un PR, issue o nota local. No requiere otro documento si esa evidencia ya existe.

## Herramientas que debes poder usar

Para esta unidad basta:

- debugger de Node.js/IDE: breakpoint, call stack, scope, step over/into/out y watch;
- ejecución aislada de un test;
- logs temporales o estructurados con identificador de request;
- búsqueda de referencias e historial de Git.

Heap snapshots, `strace`, `tcpdump` y debugging de código desconocido tienen destino en [4.6 — Debugging Avanzado](../Etapa%204%20—%20Profundización/4.6%20—%20Debugging%20Avanzado.md); no son requisito del diagnóstico básico.

## Done cuando

- [ ] El bug se reproduce con comando/datos exactos y existe una baseline observable.
- [ ] Escribiste una predicción antes de inspeccionar o editar y falsaste o confirmaste la hipótesis con evidencia.
- [ ] Puedes trazar desde la entrada hasta la causa y distinguirla del síntoma.
- [ ] El test de regresión falla antes y pasa después del arreglo.
- [ ] Revisaste callers o caminos hermanos para evitar un parche local repetido.
- [ ] El diff contiene solo cambios explicables por la causa.
- [ ] Puedes explicar la evidencia, la incertidumbre y el rollback.
- [ ] Conservaste el reproducer o test rojo como caso negativo.
- [ ] Completaste la recuperación R1 del cierre crítico.
