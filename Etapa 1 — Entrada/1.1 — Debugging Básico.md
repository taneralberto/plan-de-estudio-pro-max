# 1.1 — Debugging Básico

> **Cierre 🔴:** además de los checks locales, cumple el [cierre de un tema crítico](../METODOLOGIA.md#cierre-de-un-tema-crítico).

Antes de escribir código complejo, necesitas saber encontrar por qué NO funciona. El debugging NO es "probar cosas al azar hasta que ande" — es una habilidad sistemática.

---

- [ ] **Chrome DevTools — Lo básico**

Breakpoints: cómo ponerlos, qué pasa cuando el código se detiene. Call Stack: ver la cadena de llamadas que te llevó hasta ahí. Scope: qué variables están disponibles en cada momento. Step over vs Step into vs Step out: cuándo usar cada uno. Watch expressions: monitorear valores específicos mientras avanzas.

**Por qué importa:** Usar solo `console.log` limita el estado y el flujo que puedes inspeccionar. Los breakpoints permiten inspeccionar estado en cualquier punto, pausar, avanzar paso a paso, y entender exactamente qué está pasando. Sin esta habilidad, debugging es adivinar.

**<span style="color: #29B6F6">Ejercicio:</span>** Agrega un bug intencional en un proyecto (ej: una función que retorna `undefined` en ciertos casos). Usa Chrome DevTools para: (1) poner un breakpoint donde se produce el `undefined`, (2) inspeccionar el call stack, (3) encontrar el origen del problema en menos de 5 minutos, sin `console.log`.

**<span style="color: #FFA726">FreePress:</span>** Haz este ejercicio directamente en el frontend de FreePress — los bugs de rendering son los mejores para aprender breakpoints porque puedes inspeccionar el DOM en vivo mientras avanzas paso a paso.

**Done cuando:** Puedes debuggear un problema en código que no conoces usando breakpoints, call stack y scope inspection — sin agregar ni un solo `console.log`. Puedes explicar la diferencia entre Step Over y Step Into y cuándo usar cada uno.

**Recursos:**
- [Chrome DevTools Docs — Pause code with breakpoints](https://developer.chrome.com/docs/devtools/javascript/breakpoints/) — la guía oficial, clara y completa
- Video: "Chrome DevTools Crash Course" en YouTube (cualquier versión reciente, lo básico no cambia)

- [ ] **Console methods que no son console.log**

`console.log` es el martillo que hace todo parecer un clavo. Pero existen otros: `console.table()` para ver arrays de objetos en formato tabla, `console.dir()` para inspeccionar objetos con profundidad, `console.time()` / `console.timeEnd()` para medir performance, `console.assert()` para validar condiciones, `console.group()` para organizar logs relacionados.

**Por qué importa:** Si estás loggeando arrays de 100 objetos con `console.log`, estás perdiendo tiempo leyendo basura. `console.table(data)` te da una tabla legible en segundos. Si estás midiendo performance con `Date.now()` manual, estás reinventando `console.time()`. Estas herramientas existen para hacerte más eficiente — úsalas.

**<span style="color: #29B6F6">Ejercicio:</span>** Toma un array de objetos con datos estructurados (ej: lista de artículos con título, autor, fecha). Muéstralo con `console.log` y después con `console.table`. Mide cuánto tarda un loop con `console.time`. Escribe una aserción con `console.assert` que falle intencionalmente para ver cómo se ve.

**<span style="color: #FFA726">FreePress:</span>** Usa los datos reales de FreePress — el array de artículos es perfecto para `console.table` porque cada artículo tiene múltiples campos que se ven claros en formato tabla.

**Done cuando:** Puedes elegir el método de console correcto para cada situación sin dudar. No usas `console.log` para todo — sabes cuándo `table`, `dir`, `time` o `assert` son mejores opciones.

**Recursos:**
- [MDN — Console API](https://developer.mozilla.org/en-US/docs/Web/API/console) — referencia completa de todos los métodos

- [ ] **Node.js debugging — backend sin console.log**

`node --inspect`: cómo conectar Chrome DevTools a un proceso de Node. Debugging en VS Code: configuración de launch.json, breakpoints en el editor, debug console. Debugging de tests: cómo debuggear tests de Jest o Vitest paso a paso. Debugging de procesos remotos: conectar a un servidor en producción (con precaución).

**Por qué importa:** Tu backend corre en Node. Si solo sabes debuggear frontend, estás ciego cuando el problema está en el servidor. El debugging de Node es casi igual al de browser — pero necesitas saber cómo conectar las herramientas.

**<span style="color: #29B6F6">Ejercicio:</span>** Configura debugging en VS Code para un backend Express. Agrega un bug en un endpoint (ej: retorna 500 en ciertas condiciones). Usa el debugger de VS Code para encontrar el origen del problema, con breakpoints y variable inspection.

**<span style="color: #FFA726">FreePress:</span>** Haz este ejercicio en el backend de FreePress — configura el `launch.json` para que puedas debuggear los endpoints directamente desde VS Code. Este setup te va a servir para toda la Etapa 1.

**Done cuando:** Tienes configurado debugging en VS Code para un backend Node.js y puedes debuggear un problema en un endpoint sin agregar `console.log` al código.

**Recursos:**
- [VS Code — Node.js Debugging](https://code.visualstudio.com/docs/nodejs/nodejs-debugging) — guía oficial de VS Code
- [Jest — Debugging Tests](https://jestjs.io/docs/troubleshooting#debugging-tests) — cómo debuggear tests de Jest

- [ ] **La metodología de debugging — No es adivinar**

El error común: "prueba esto, prueba aquello, reinicia, quizás es esto". Eso NO es debugging — es shooting in the dark.

**El método correcto:**
1. **Reproducir** el bug de forma consistente (si no puedes reproducirlo, no puedes debuggearlo)
2. **Reducir** el problema: aísla el código mínimo que reproduce el bug
3. **Formular hipótesis** de qué está mal (no "quizás algo", sino "probablemente X retorna undefined cuando Y")
4. **Testear la hipótesis** con el debugger (poner breakpoint donde X se calcula, verificar)
5. **Repetir** si la hipótesis estaba mal, pero ahora con más información

**Por qué importa:** Un bug de 2 horas se convierte en 30 minutos cuando usas metodología. Sin metodología, puedes pasar días probando cosas sin avanzar. El debugger es la herramienta, pero la metodología es lo que te hace eficiente.

**<span style="color: #29B6F6">Ejercicio:</span>** Toma un bug real o inventado en un proyecto que conozcas. Aplica la metodología paso a paso: (1) escribe pasos exactos para reproducir, (2) aísla el código mínimo, (3) escribe tu hipótesis ANTES de usar el debugger, (4) verifica la hipótesis con breakpoints, (5) documenta qué aprendiste.

**<span style="color: #FFA726">FreePress:</span>** Usa un bug real de FreePress — si no tienes uno, inventa un bug de autenticación (ej: un usuario no admin puede editar artículos) y aplica la metodología completa.

**Done cuando:** Puedes explicar el método de debugging de 5 pasos y aplicarlo a un problema nuevo sin "probar cosas al azar". Cuando te encuentras con un bug, tu primer impulso es "reproducir, reducir, hipótesis", no "quizás si reinicio funciona".

**Recursos:**
- Artículo: *"Debugging: The 9 Indispensable Rules"* de David Agans — el libro corto que define la metodología estándar de debugging
- Video: "How to Debug Anything" por ThePrimeagen — enfoque práctico y directo
