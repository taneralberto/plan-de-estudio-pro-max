> **Estado:** `ACTIVO` · Preparación de la unidad 2 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** JavaScript asíncrono básico y una versión local de Node.js que puedas registrar.

## Propósito

Explicar qué ejecuta JavaScript, qué trabajo espera fuera del call stack y por qué una operación CPU-bound puede retrasar solicitudes no relacionadas. El objetivo es predecir y comprobar comportamiento, no memorizar un orden universal de callbacks.

## Orientación

**Qué debes lograr:** usar el modelo del event loop para predecir qué señal cambiará ante trabajo CPU-bound.

**Cómo abordarlo:** aplica la preparación de `Predicción útil` dentro del ejercicio único de [2.7](../Etapa%202%20—%20Fundamentos/2.7%20—%20Concurrency%20y%20Parallelism.md), no como práctica adicional.

**Investiga fuera solo si:** un perfil o una diferencia entre versiones exige abrir los mecanismos JIT de este archivo o la [unidad 2 de RECURSOS](../RECURSOS.md#2--runtime-procesos-y-concurrencia).

## Modelo mínimo del event loop

### Call stack y colas

El call stack ejecuta JavaScript síncrono hasta devolver el control al runtime. Los callbacks listos se programan como tareas; las Promises y `queueMicrotask` agregan microtasks que se drenan en checkpoints definidos por el entorno.

Browser y Node.js no comparten una sola secuencia abstracta. El browser integra tareas, render y APIs Web. Node.js añade `process.nextTick` y las fases de libuv —timers, pending callbacks, poll, check y close callbacks—, además de comportamiento que puede variar entre versiones. Cuando el orden observado dependa del runtime, registra versión, código y salida en vez de convertir un ejemplo en regla general.

Una Promise coordina la continuación de trabajo; no vuelve paralelo el JavaScript CPU-bound. `async`/`await` tampoco mueve el cuerpo síncrono a otro hilo.

### Qué ocurre fuera del stack

Node.js delega según la operación:

- el I/O de red suele esperar mecanismos asíncronos del sistema operativo;
- el pool de libuv ejecuta filesystem, parte de DNS, crypto y las operaciones que Node documente para la versión usada;
- un callback vuelve al event loop cuando el resultado está disponible;
- el JavaScript CPU-bound permanece en el hilo que lo ejecuta salvo que se mueva explícitamente a un Worker Thread o proceso.

Que una API entregue una Promise no revela por sí solo si usa el sistema operativo, el pool de libuv o trabajo síncrono. Compruébalo con documentación y medición.

### Predicción útil

Dentro del ejercicio de `2.7`, para razonar sobre el fragmento CPU-bound:

1. identifica el JavaScript síncrono y cuánto tarda;
2. separa `process.nextTick`, microtasks y callbacks de las fases relevantes;
3. señala qué operación espera fuera del stack;
4. escribe el orden esperado y la condición que podría cambiarlo;
5. ejecútalo con la versión registrada y explica cualquier diferencia.

La predicción es una hipótesis, no evidencia hasta compararla con la ejecución.

## Repaso JIT de lenguaje

Closures retienen el entorno léxico que usan y pueden mantener referencias vivas. La prototype chain resuelve propiedades ascendiendo por `[[Prototype]]`. El valor de `this` depende de cómo se invoca una función; las arrow functions capturan el `this` léxico. Revisa estos mecanismos cuando expliquen un bug concreto, sin convertirlos en requisito de cierre de la unidad.

V8, hidden classes, deoptimizations y paquetes duales CJS/ESM quedan JIT ante un perfil o problema real de interoperabilidad. Para módulos, consulta la documentación de la versión de Node y evita publicar dos formatos si el consumidor no lo exige.
