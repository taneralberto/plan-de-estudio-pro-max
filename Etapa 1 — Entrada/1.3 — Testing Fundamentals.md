# 1.3 — Testing Fundamentals

> "Testing desde el día 1" solo funciona si sabes QUÉ testear, CÓMO, y CUÁNDO es suficiente. Este tema es el fundamento mínimo para que cada línea de código que escribas tenga un test que la respalde.

- [ ] **Qué es un test y por qué existe**

Un test no es "para pasar CI" ni "para llegar al 80% de coverage". Un test es una **pregunta que le haces a tu código** antes de que un usuario la haga por ti. Cada test responde a una pregunta: "¿qué pasa si...?" — ¿qué pasa si el input es null? ¿qué pasa si el array está vacío? ¿qué pasa si el usuario no está autenticado? Los tests existen porque tu cerebro no puede sostener todos los casos edge de un sistema al mismo tiempo — los tests los documentan en código ejecutable.

**Por qué importa:** Sin tests, cada cambio que haces al código es una apuesta. "Creo que esto no rompe nada" no es ingeniería — es fe. Los tests convierten esa fe en evidencia. Y en la era de AI, donde generas código que parece correcto pero puede tener edge cases ocultos, los tests son tu red de seguridad más confiable.

- [ ] **Estructura AAA (Arrange-Act-Assert) — El patrón universal**

Todo test bien escrito tiene tres partes: **Arrange** (preparas el escenario — datos, mocks, estado inicial), **Act** (ejecutas la acción que quieres verificar), **Assert** (verificas que el resultado es el esperado). Este patrón es universal — aplica en Jest, Vitest, Pytest, Go testing, cualquier framework. Si un test no sigue AAA, probablemente está haciendo más de una cosa o está mal estructurado.

```javascript
// Arrange
const user = { name: 'Tana', role: 'admin' };
const article = { title: 'Test', authorId: user.id };

// Act
const canEdit = canUserEditArticle(user, article);

// Assert
expect(canEdit).toBe(true);
```

**Por qué importa:** La estructura AAA hace que un test sea legible para otro humano (incluyendo a tu yo futuro). Si lees "Arrange" y ves datos de setup, "Act" y ves la llamada, "Assert" y ves la verificación — entiendes el test en 10 segundos. Sin AAA, un test es código que hace algo pero no se sabe qué.

**<span style="color: #29B6F6">Ejercicio:</span>** Reescribe 3 tests que hayas escrito (o que encuentres en un proyecto) usando AAA explícito con comentarios `// Arrange`, `// Act`, `// Assert`. Si alguno no encaja limpiamente en AAA, es probable que el test esté haciendo más de una cosa.

**Done cuando:** Todo test que escribes sigue AAA sin esfuerzo. Puedes leer un test ajeno y identificar las tres secciones en 10 segundos.

- [ ] **Qué testear vs qué no testear**

No todo necesita un test. **Testea:** lógica de negocio (cálculos, transformaciones, reglas), edge cases (null, vacío, límites), integraciones críticas (auth, pagos, permisos). **No testees:** getters/setters triviales, código generado automáticamente, detalles de implementación internos que pueden cambiar sin afectar comportamiento. La regla: testea el QUÉ hace el código (comportamiento observable), no el CÓMO lo hace (implementación interna).

**Por qué importa:** Testear lo incorrecto es peor que no testear nada. Un test que verifica el internals de una función (ej: que llama a un helper privado específico) se rompe cuando refactorizas — aunque el comportamiento sea el mismo. Estos "tests frágiles" hacen que el equipo odie los tests y los ignore. Un test que verifica comportamiento sobrevive refactors.

**<span style="color: #29B6F6">Ejercicio:</span>** Mira los tests de un proyecto que conozcas. Clasifica cada test en: (1) testeando comportamiento — ✅, (2) testeando implementación — ⚠️ frágil, (3) testeando algo trivial — ❌ innecesario. ¿Cuántos caen en cada categoría?

- [ ] **Mocks básicos: cuándo usarlos, cuándo son un smell**

Un mock reemplaza una dependencia real (base de datos, API externa, servicio) por una versión controlada que tú defines. Útil para aislar la unidad que estás testeando. Pero los mocks tienen un costo: cada mock es un contrato implícito entre el test y la implementación. Si la implementación cambia y el mock no, el test pasa pero el código real falla. **Regla:** mockea dependencias externas (APIs, DBs, servicios de terceros). NO mockees dependencias internas del mismo módulo — eso es testeando implementación.

**Por qué importa:** Un test con demasiados mocks no está testeando el código real — está testeando que los mocks funcionan como tú los configuraste. Es una ilusión de cobertura. En la era de AI, esto es especialmente peligroso: la AI genera mocks que hacen pasar el test pero no verifican el comportamiento real.

- [ ] **Coverage como guía, no como meta**

Coverage mide qué líneas de código se ejecutaron durante los tests. 80% coverage significa que el 20% del código nunca se ejecutó en un test — pero NO significa que el 80% funcione correctamente. Una función puede tener 100% coverage y tener un bug que ningún test verifica (porque el test ejecuta la línea pero no verifica el resultado correcto). **Coverage te dice dónde FALTA un test, no dónde hay uno bueno.**

**Por qué importa:** Perseguir un número de coverage genera tests triviales que ejecutan código pero no verifican nada significativo. "Llegamos al 90%" es una victoria de métrica, no de calidad. Lo correcto: usa coverage para identificar código NO testeado, y escribe tests significativos para esas zonas.

**<span style="color: #29B6F6">Ejercicio:</span>** Ejecuta `jest --coverage` (o el coverage de tu test runner) en un proyecto. Identifica los 3 archivos con menor coverage. ¿Son zonas críticas (auth, lógica de negocio) o zonas triviales (config, utils genéricos)? Escribe tests significativos solo para las zonas críticas.

**<span style="color: #FFA726">FreePress:</span>** Ejecuta coverage en FreePress y mira qué archivos tienen menor cobertura. Los endpoints de auth y la lógica de permisos son las zonas críticas — esos son los que merecen tests, no los archivos de config.

**Done cuando:** Entiendes que 100% coverage no significa 0 bugs. Usa coverage como mapa ("¿dónde me falta testear?") no como meta ("¿cuánto me falta para el 80%?").

**Recursos:**

- [ ] **Testing de endpoints con supertest**

En la Etapa 1, FreePress usa Express. Supertest permite testear endpoints HTTP sin levantar un servidor real — monta la app Express y le dispara requests como si fuera un cliente. Es la forma más directa de verificar que tu API hace lo que debería: status codes correctos, response bodies esperados, headers apropiados, y manejo de errores.

```javascript
const request = require('supertest');
const app = require('../app'); // tu Express app

test('GET /api/articles returns 200 and array', async () => {
  // Arrange & Act
  const res = await request(app).get('/api/articles');

  // Assert
  expect(res.status).toBe(200);
  expect(Array.isArray(res.body)).toBe(true);
});
```

**Por qué importa:** Los tests de endpoint son tests de integración — verifican que el código funciona de punta a punta (request → router → controller → DB → response). Son más valiosos que los unit tests puros porque prueban que las piezas encajan. En la Etapa 1 con Express + SQLite, puedes escribir tests de integración reales sin mockear nada.

**<span style="color: #29B6F6">Ejercicio:</span>** Escribe tests de integración para los endpoints de una API: (1) `GET /api/articles` devuelve 200 con array, (2) `POST /api/articles` sin auth devuelve 401, (3) `POST /api/articles` con auth devuelve 201 y el artículo creado. Usa SQLite in-memory para la DB.

**<span style="color: #FFA726">FreePress:</span>** Estos son exactamente los endpoints de FreePress — escribe los tests directamente ahí. Es el primer aporte real al proyecto: tests que protegen la funcionalidad.
