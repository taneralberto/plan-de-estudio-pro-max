# 1.3 — Testing y Oracles Externos

> **Estado:** `ACTIVO ★` · Unidad 3 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** una spec con comportamiento observable; usa la de [1.7](1.7%20—%20Documentación%20Técnica%20Profesional.md) si no tienes otra.
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Diseñar evidencia ejecutable que detecte una implementación plausible pero incorrecta. Un test aporta confianza cuando su resultado esperado proviene del contrato, una invariante o una fuente independiente; no cuando repite la lógica que pretende verificar.

## Orientación

**Qué debes lograr:** dada una spec y una implementación plausible pero incorrecta, escribir un test cuyo esperado provenga de un oracle independiente y demostrar que falla antes del arreglo y pasa después.

**Cómo abordarlo:** intenta primero falsar la implementación: extrae una invariante de la spec, imagina el defecto mínimo que un test feliz no detectaría y convierte esa diferencia en un assert. Vuelve al modelo de oracles solo si no puedes justificar el esperado sin mirar la implementación.

**Investiga fuera solo si:** no sabes expresar el test con el runner actual → Jest; necesitas cruzar el límite real de PostgreSQL de forma aislada → Testcontainers, ambos desde la unidad 3 de [RECURSOS](../RECURSOS.md#3--testing-y-oracles-externos).

## Ejemplo mínimo — idempotencia de una reserva

> Este ejemplo explica el razonamiento; no es otro ejercicio ni otro Done.

```javascript
// Spec: repetir la misma clave produce un solo efecto.
await reserve({ sku: 'A', quantity: 1 }, 'key-1'); // la versión defectuosa ignora la clave
expect(await reserved('A')).toBe(1);              // test ingenuo: pasa

await reserve({ sku: 'A', quantity: 1 }, 'key-1');
expect(await reserved('A')).toBe(1);              // oracle: invariante de la spec
// Defecto: recibe 2 (rojo). Arreglo: deduplica clave + efecto atómicamente (verde).
```

## Modelo mínimo

### Empieza por riesgo y comportamiento

Antes de elegir framework o nivel de test, pregunta:

1. ¿Qué comportamiento importa al usuario o sistema consumidor?
2. ¿Qué invariante causaría daño si se rompe?
3. ¿Qué límite —datos, red, reloj, proceso o base de datos— puede contradecir tus supuestos?
4. ¿Qué implementación incorrecta podría pasar un test ingenuo?

Prioriza por impacto y probabilidad. Coverage indica código ejecutado, no corrección; úsalo para encontrar huecos, nunca como porcentaje objetivo.

### Oracle antes que implementación

Un **oracle** decide cuál debería ser el resultado. Puede venir de:

- ejemplos y contraejemplos de la spec;
- invariantes del dominio;
- constraint o comportamiento documentado de una dependencia;
- una implementación de referencia suficientemente independiente;
- relaciones metamórficas: al transformar la entrada, el resultado debe conservar o cambiar una propiedad conocida.

Fija el oracle antes de ver la solución del agente. Si calculas el esperado copiando el mismo algoritmo del código, ambos pueden compartir el defecto.

### Estructura legible, sin ceremonia

Arrange–Act–Assert o Given–When–Then ayudan a separar escenario, acción y resultado. Los comentarios son opcionales: el nombre, datos y asserts deben dejar visible un comportamiento. Si un test necesita varias acciones no relacionadas, probablemente contiene más de un caso.

### El nivel más bajo que cruza el riesgo

| Nivel | Úsalo para | Evita |
|---|---|---|
| Función/unidad | reglas puras, combinaciones y casos límite | mockear internals para comprobar llamadas |
| Integración | SQL, transacciones, serialización y dependencias reales | sustituir PostgreSQL por SQLite cuando sus semánticas importan |
| API/contrato | status, headers, body, auth/idempotencia y compatibilidad | probar cada permutación por HTTP |
| E2E | uno o pocos flujos cuyo riesgo atraviesa el sistema completo | duplicar toda la suite o depender de UI frágil |

No existe una proporción universal. Elige el nivel en el que el fallo puede aparecer con el menor costo de setup y diagnóstico.

### Doubles con contrato explícito

- **Stub:** devuelve una respuesta controlada.
- **Spy:** registra una interacción observable relevante.
- **Fake:** implementación simplificada con comportamiento funcional.
- **Mock:** verifica expectativas de interacción.

Úsalos para reloj, red o servicios externos que no puedes controlar. Un double es peligroso si inventa un contrato distinto al real; valida ese límite con al menos un test de integración o documentación primaria. No mockees una dependencia interna solo para hacer pasar el diseño actual.

### Property-based testing y fuzzing

Un example-based test protege un caso conocido. Un property test genera muchos inputs y verifica una invariante; no demuestra corrección exhaustiva. Fuzzing prueba entradas inesperadas para encontrar crashes, hangs o violaciones de seguridad; necesita límites de tiempo y una propiedad observable.

Empieza con una propiedad pequeña sobre una función pura. Mantén la semilla del fallo para poder reproducirlo.

### Flakiness es un defecto

Un retry puede recopilar evidencia, pero no vuelve correcto un test no determinista. Controla reloj, aleatoriedad, estado compartido y servicios externos; cuando falle, conserva seed, logs y artifacts suficientes para reproducir.

## Ejercicio único — Proteger una reserva

**Timebox:** hasta 120 minutos sobre un backend cuyo comando de tests y base de datos ya funcionen. No implementes un endpoint ni montes infraestructura nueva para empezar esta unidad. Cuando esté disponible, puedes usar `POST /reservations` de [`safe-change-api`](../PROYECTOS.md#proyecto-a--safe-change-api); antes, usa un endpoint equivalente de un proyecto existente.

1. Extrae de la spec las invariantes y escribe primero los casos esperados.
2. Prueba como función pura que cantidades no positivas se rechazan. Si una invariante admite generación útil, añade una propiedad reproducible con la herramienta ya disponible; si no, déjala JIT.
3. Prueba por HTTP contra PostgreSQL real que repetir la misma clave de idempotencia no duplica el efecto; el mismo test establece primero el caso válido.
4. Siembra o pide a un agente una implementación plausible que omita idempotencia o acepte cantidad cero sin revelar cuál caso ocultaste.
5. Demuestra que al menos un test falla con el defecto y pasa al corregirlo.
6. Revisa el diff de tests: cada assert debe derivar de la spec/invariante, no de la estructura interna.
7. Documenta qué fallo importante todavía no cubre la suite y en qué unidad lo abordarás.

Si Testcontainers no está ya disponible, usa una instancia PostgreSQL local aislada. No reemplaces el motor cuando el comportamiento depende de constraints, transacciones o SQL.

## Qué dejar JIT

- Pact u otro contract testing entre servicios, hasta que exista un consumidor independiente.
- Playwright/Cypress para un flujo de UI real; Testing Frontend vive en la ruta Web.
- suites de performance, caos o seguridad completas; cada disciplina define su oracle en su unidad.
- snapshots masivos que alguien debe aprobar sin entender el cambio.

## Done cuando

- [ ] Los resultados esperados provienen de spec, invariantes o fuente independiente.
- [ ] La suite combina solo los niveles necesarios; usa PostgreSQL real cuando cruza ese límite.
- [ ] Incluye un caso negativo; si usaste una propiedad generada, el fallo conserva una semilla reproducible.
- [ ] Un test detecta una solución plausible defectuosa: falla antes y pasa después del arreglo.
- [ ] Puedes justificar cada double y mostrar cómo se valida su contrato real.
- [ ] Coverage se usa como señal de huecos, no como objetivo de calidad.
- [ ] Registraste un riesgo no cubierto en lugar de afirmar que la suite prueba todo.
- [ ] Cumpliste artefacto, evidencia independiente y la recuperación del cierre crítico.
