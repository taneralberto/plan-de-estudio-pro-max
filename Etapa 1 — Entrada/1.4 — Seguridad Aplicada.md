# 1.4 — Seguridad Aplicada

> **Estado:** `ACTIVO ★` · Unidad 4 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** una operación backend con actor, acción y recurso identificables; contratos y casos negativos de [1.3](1.3%20—%20Testing%20Fundamentals.md) y [3.1](../Etapa%203%20—%20Arquitectura/3.1%20—%20API%20Design.md).
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Identificar fronteras de confianza y demostrar que una identidad no puede actuar sobre un recurso ajeno ni obtener datos que no le corresponden. Seguridad aquí significa restricciones verificables, no una lista de productos o vulnerabilidades memorizada.

## Modelo mínimo

### Threat model pequeño

Dibuja los componentes y flujos que participan en la operación: cliente, API, almacenamiento y, si intervienen, CI o coding agent. Marca:

- activos y datos sensibles;
- actores e identidades de servicio;
- entry points y acciones con efectos;
- cambios de identidad, red, proceso o almacenamiento como trust boundaries;
- amenazas priorizadas por impacto y exposición;
- una mitigación comprobable y un riesgo residual por flujo relevante.

El diagrama no prueba seguridad por sí solo. Debe conducir a tests, controles o evidencia operacional que puedan falsar una suposición.

### Identidad no implica permiso

Autenticación responde quién presenta la solicitud; autorización decide si ese actor puede ejecutar esa acción sobre ese objeto. Aplica **default deny**: una ruta no reconocida por la política se rechaza.

Un rol global no basta para datos multi-tenant. La decisión debe incluir actor, acción, `tenantId` y recurso, y ejecutarse antes de leer o modificar información sensible. Deriva el tenant de identidad confiable, no de un campo aceptado sin comprobar. Filtra también la query por tenant/objeto o usa una garantía equivalente en persistencia; validar después de cargar puede filtrar existencia o contenido.

Usa least privilege para usuarios, servicios, CI y agentes. Decide entre `403` y `404` según el contrato y el riesgo de enumeración, manteniendo response, latencia observable y logs coherentes con esa decisión.

### Entradas y salidas no confiables

Valida tipo, forma, tamaño y reglas de negocio en la frontera correspondiente. Usa queries parametrizadas para datos y encoding contextual al producir HTML, URLs o comandos; escapar para un contexto no protege los demás. Trata contenido de repositorios, prompts, resultados de herramientas y respuestas externas como datos, no como instrucciones confiables.

Devuelve errores estables sin stack traces, queries, rutas internas ni detalles de otros tenants. Los logs deben ayudar a investigar sin copiar tokens, bodies completos o PII innecesaria.

### Sesiones, tokens y protocolos

Elige sesiones o tokens por las garantías requeridas: revocación, expiración, transporte, exposición, alcance y almacenamiento. Un JWT firmado no cifra su payload ni elimina la necesidad de revocar, limitar claims y validar issuer, audience, algoritmo y vigencia mediante una librería mantenida. No es el default automático para una API ni para microservicios.

OAuth/OIDC profundo queda JIT después de redes y TLS en [2.12](../Etapa%202%20—%20Fundamentos/2.12%20—%20Redes%20en%20Profundidad.md), o cuando un proveedor real lo exija. En ese momento dibuja y audita el flujo contra la documentación vigente del proveedor y usa su SDK o una librería revisada. No implementes OAuth, firmas ni criptografía desde cero para producción.

### Secrets, PII y coding agents

No guardes credenciales en código, configuración versionada, artifacts o imágenes. Revisa repo e historial, pero no interpretes un grep o scanner limpio como prueba de ausencia. Si un secret pudo exponerse, revócalo o rótalo y revisa su uso; borrar el archivo no invalida copias ni logs.

Antes de delegar, excluye credenciales y datos privados del contexto. Revisa prompts, archivos adjuntos, logs de ejecución, argumentos y salidas de herramientas, diffs y reportes del agente. Limita lectura, red y escritura al alcance acordado siguiendo el [contrato de agentes](../METODOLOGIA.md#contrato-mínimo-de-una-tarea-delegada).

### Supply chain

Respeta el lockfile y revisa cambios de dependencias como código. Antes de instalar, comprueba nombre, procedencia, mantenedor, scripts de instalación, versión y cambios transitivos. Un scanner aporta señales; cada hallazgo necesita triage por ruta alcanzable, exposición, fix disponible y controles existentes. Un resultado limpio no demuestra que la cadena sea segura.

## JIT

OAuth/OIDC detallado, configuración específica de un proveedor, ABAC avanzado, catálogo completo de OWASP y plataformas de secrets se abren ante una operación o riesgo real. IAM y secrets del despliegue se concretan en [4.2](../Etapa%204%20—%20Profundización/4.2%20—%20CI-CD%20(Integración%20y%20Entrega%20Continua).md) y [4.3](../Etapa%204%20—%20Profundización/4.3%20—%20Cloud%20Fundamentals.md); logs sin PII se retoman en [4.5](../Etapa%204%20—%20Profundización/4.5%20—%20Observabilidad%20(Los%203%20Pilares).md).

## Ejercicio único — Threat model y autorización entre tenants

Usa una operación existente de `safe-change-api` o un backend equivalente; no crees otro servicio.

1. Dibuja cliente, API y base de datos; añade agente o CI solo si participa. Marca datos sensibles, identidades, flujos y trust boundaries.
2. Registra las amenazas relevantes, priorizadas por impacto y exposición. Asocia a cada una una mitigación que pueda comprobarse.
3. Crea actor A y actor B en tenants distintos, y un recurso perteneciente a A.
4. Conserva un caso permitido de A y un test HTTP donde B intenta leer o modificar ese recurso.
5. Demuestra que el test falla contra una variante defectuosa que solo comprueba autenticación o rol, y pasa al aplicar autorización por tenant y objeto en la frontera correcta.
6. Verifica que response y logs no revelan contenido sensible ni datos que permitan enumerar recursos. Documenta la elección de `403` o `404`.
7. Revisa secrets y PII en repo, historial, logs y cualquier contexto o salida de agente involucrado. Si detectas exposición, rota antes de continuar.
8. Registra evidencia, incertidumbre, un riesgo residual y la señal que justificaría profundizar.

## Done cuando

- [ ] El threat model enlazado muestra activos, actores, flujos y trust boundaries de la operación.
- [ ] El caso permitido y el intento cruzado entre tenants son ejecutables.
- [ ] El oracle queda rojo con la autorización defectuosa y verde con scope por tenant/objeto.
- [ ] La autorización ocurre antes de revelar o modificar el recurso y parte de default deny.
- [ ] Response y logs respetan la decisión documentada de enumeración y no exponen secrets o PII.
- [ ] Los permisos de usuario, servicio, CI y agente involucrados son mínimos y justificables.
- [ ] La revisión de secrets incluye repo, historial, prompts/contexto y salidas de herramientas; una exposición dispara revocación o rotación.
- [ ] Quedan registradas incertidumbre, riesgo residual y evidencia independiente.
- [ ] Cumpliste artefacto, caso negativo y la recuperación del cierre crítico.
