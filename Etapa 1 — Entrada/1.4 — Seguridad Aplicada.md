- [ ]  **Autenticación — OAuth 2.0, PKCE y OpenID Connect**

Autenticación es responder "quién eres". OAuth 2.0 flows: Authorization Code (con PKCE para clientes públicos — SPAs y apps móviles), Client Credentials (para servicio a servicio). PKCE: por qué es obligatorio para clientes públicos, qué falla si se omite (el authorization code intercept attack). OpenID Connect como capa de identidad sobre OAuth 2.0: `id_token` (información del usuario) vs `access_token` (permiso para actuar). El flujo completo paso a paso: authorization server, redirect, code exchange, token response.

**Por qué importa:** Auth mal implementada es la vulnerabilidad #1 en aplicaciones reales. Si no entiendes el protocolo, vas a cometer errores que ningún linter te va a detectar — como omitir PKCE en una SPA y dejar la puerta abierta al authorization code intercept attack.

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa un flujo OAuth 2.0 Authorization Code + PKCE desde cero (sin librerías) para ENTENDER el protocolo. Documenta cada paso con los requests y respuestas HTTP que ocurren: `GET /authorize`, `POST /token`, los parámetros en cada request, y el flujo completo del code_verifier/code_challenge.

**<span style="color: #FFA726">FreePress:</span>** El OAuth desde cero hazlo aparte — es un ejercicio de comprensión, no de producción. Para FreePress, configura un Identity Provider (Auth0 o similar) que implemente estos flujos correctamente.

**Done cuando:** Puedes dibujar en una pizarra el flujo completo de OAuth 2.0 Authorization Code con PKCE, explicar qué hace cada paso y por qué, y señalar qué falla si se omite el PKCE en una SPA.

**Recursos:**

- [OAuth 2.0 RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749) — la especificación original, vale leerla
- Libro: *OAuth 2 in Action* de Justin Richer — si quieres ir en profundidad en los flujos y sus implicaciones de seguridad

- [ ]  **Autorización — JWT, Sesiones y RBAC**

Autorización es responder "qué puedes hacer". JWT: estructura (`header.payload.signature`), qué va en el payload (claims estándar: `sub`, `iat`, `exp`, `scope`), qué NO va (datos sensibles, passwords, información personal innecesaria — el payload es base64, no encriptado). Por qué `alg: none` es una vulnerabilidad crítica. Refresh tokens y rotación — por qué los access tokens son de corta duración y los refresh tokens necesitan rotación para detectar theft. Sesiones server-side vs JWT: sesiones para aplicaciones web tradicionales (invalidación inmediata, sin exposición del state), JWT para APIs stateless y microservicios (sin round-trip a la base). RBAC (Role-Based Access Control): roles y permisos — admin, editor, autor, lector. ABAC (Attribute-Based Access Control): autorización basada en atributos del usuario, del recurso y del contexto — cuándo RBAC no alcanza (reglas como "un autor solo puede editar sus propios artículos publicados en las últimas 24 horas").

**Por qué importa:** JWT no es magia — es un token firmado con claims, y si no entiendes qué claims incluir y cuáles omitir, vas a filtrar datos o crear tokens explotables. "Usar JWT para sesiones" es uno de los errores más comunes en la industria: JWT no se puede invalidar sin infraestructura adicional, el payload es legible por cualquiera, y revocar un token requiere el mismo state que una sesión server-side. Entender cuándo usar cada enfoque es la diferencia entre auth sólida y auth frágil.

**<span style="color: #29B6F6">Ejercicio:</span>** (1) Implementa RBAC en un proyecto Express con roles: admin, editor, autor, lector usando middleware. Cada rol tiene permisos distintos sobre los recursos — verifica que un lector no pueda crear artículos y que un autor no pueda eliminar artículos de otros. (2) Implementa refresh token rotation con almacenamiento seguro. (3) Analiza para tu proyecto: ¿usarías sesiones server-side o JWT? Justifica la decisión.

**<span style="color: #FFA726">FreePress:</span>** Implementa los roles de FreePress (admin, editor, autor, lector) con middleware de Express como parte del proyecto.

**Done cuando:** Puedes explicar qué datos van y qué datos NO van en un JWT, por qué `alg: none` es peligroso, y cuándo usar sesiones server-side vs JWT sin dudar. Puedes implementar RBAC con middleware en Express sin consultar la documentación.

**Recursos:**

- [jwt.io](https://jwt.io) — decodifica y entiende la estructura de un JWT real
- Artículo: *"Stop using JWT for sessions"* de joepie91 — perspectiva crítica necesaria sobre el uso indebido de JWT

- [ ]  **Supply Chain Security**

Dependencias maliciosas en npm, lockfiles, `npm audit`, Dependabot/Renovate. Qué es un ataque de typosquatting (publicar `lodahs` esperando que alguien escriba mal `lodash`). Qué es un ataque de dependency confusion. Por qué `npm install` puede ejecutar código arbitrario en tu máquina.

**Por qué importa:** El ataque a SolarWinds comprometió miles de organizaciones sin tocar su código — atacó sus dependencias. Tu `node_modules` tiene miles de paquetes que no controlas.

**<span style="color: #29B6F6">Ejercicio:</span>** Ejecuta `npm audit` en un proyecto real. Revisa cada vulnerabilidad encontrada y clasifícala: ¿es explotable en tu contexto? ¿Cómo la mitiges? Configura Dependabot o Renovate en el repo.

**<span style="color: #FFA726">FreePress:</span>** Ejecuta `npm audit` en FreePress — un proyecto real con dependencias reales es mucho más revelador que un proyecto de práctica. Instala Dependabot en el repo de FreePress.

**Done cuando:** Puedes explicar la diferencia entre un ataque de typosquatting y uno de dependency confusion, y tienes Dependabot o Renovate corriendo en tu proyecto con al menos una PR de actualización resuelta.

**Recursos:**

- [npm audit docs](https://docs.npmjs.com/cli/v10/commands/npm-audit) — documentación oficial
- Artículo: *"Dependency Confusion: How I Hacked Into Apple, Microsoft and Dozens of Other Companies"* de Alex Birsan — el paper original del ataque, lectura obligatoria
- [Dependabot docs](https://docs.github.com/en/code-security/dependabot) — configuración en GitHub

- [ ]  **Secrets Management**

La diferencia entre configuración y secretos. Por qué `.env` en el repo es un desastre esperando pasar. HashiCorp Vault, AWS Secrets Manager, Doppler como alternativas reales. Rotación de secrets: por qué importa y cómo automatizarla. Qué hacer cuando se filtran credentials (y van a filtrarse).

**Por qué importa:** GitHub escanea repos públicos buscando API keys y las revoca automáticamente — porque pasa TODO el tiempo. Un secret en el historial de git existe para siempre aunque lo "borres".

**<span style="color: #29B6F6">Ejercicio:</span>** Audita un proyecto por secrets filtrados: usa `git log -p | grep -i "secret\|password\|key\|token"` para verificar el historial. Configura Doppler o variables de entorno en tu CI/CD pipeline. Documenta en un ADR cómo se manejan los secrets en el proyecto.

**<span style="color: #FFA726">FreePress:</span>** Audita FreePress — verifica que no haya secrets en el código ni en el historial de git, y configura el manejo de secrets como parte del proyecto. Este ADR cuenta para el tema 1.7 (Documentación Técnica).

**Done cuando:** Tu proyecto no tiene ningún secret en el código ni en el historial de git, y tienes un proceso documentado para rotar credentials si se filtran.

**Recursos:**

- [Doppler](https://www.doppler.com/) — secrets manager con free tier, el más simple para empezar
- [HashiCorp Vault](https://www.vaultproject.io/) — el estándar enterprise
- Artículo: *"How to handle secrets in git"* — busca el de GitGuardian, tienen guías excelentes
- [git-secrets](https://github.com/awslabs/git-secrets) — herramienta de AWS para prevenir commits con secrets
