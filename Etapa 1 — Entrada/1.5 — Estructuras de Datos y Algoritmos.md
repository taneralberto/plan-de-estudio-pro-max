# 1.5 — Complejidad y Estructuras Cotidianas

> **Estado:** `DIAGNÓSTICO` · unidad 5 del [ROADMAP](../ROADMAP.md).
>
> **Prerrequisito:** poder leer, ejecutar y modificar una función que procese una colección.
>
> **Cierre:** aplica el [diagnóstico antes de estudiar](../METODOLOGIA.md#diagnóstico-antes-de-estudiar): 30–60 minutos con documentación y estudia después solo el hueco observado.

## Propósito

Predecir cómo crecen tiempo y espacio y elegir una estructura por sus operaciones, no por costumbre.

## Orientación

**Qué debes lograr:** justificar Big O y elegir solo las estructuras pertinentes para un caso cotidiano.
**Cómo abordarlo:** predice desde operaciones y contrasta con un contador en dos escalas reproducibles.
**Entregarás:** informe breve con función, predicción, mediciones, decisión y límite.
**Investiga fuera solo si:** el diagnóstico revela un hueco concreto del modelo mínimo.

## Modelo mínimo

### Costo y entradas

Antes de asignar Big O, define qué representa `n` y, si hay dos colecciones, `m`. Cuenta las operaciones dominantes y distingue tiempo de espacio auxiliar. Las constantes se omiten al describir crecimiento, aunque pueden importar con datos pequeños.

Debes reconocer O(1), O(log n), O(n), O(n log n) y O(n²). Un loop anidado es O(n²) solo cuando ambos límites crecen de forma independiente con `n`; si recorren colecciones distintas puede ser O(n·m), y si el loop interior tiene un límite fijo puede seguir siendo O(n).

### Promedio, amortizado y peor caso

En las implementaciones habituales, `Map` y `Set` ofrecen lookup o membership esperado promedio cercano a O(1), con operaciones de crecimiento amortizadas; no es una garantía universal por operación. Construir un `Map` o `Set` desde `n` elementos cuesta O(n) tiempo y O(n) espacio adicional. Explicita los supuestos y al menos un peor caso relevante.

### Elección cotidiana

- **Array:** conserva orden, facilita iteración y acceso por índice; buscar membership es O(n).
- **Map:** representa asociaciones clave→valor y evita búsquedas lineales repetidas. Los objetos usados como claves se comparan por identidad.
- **Set:** representa membership y unicidad en memoria; no reemplaza un constraint `UNIQUE` en la base de datos.
- **Queue:** expresa FIFO. Analiza la implementación real: en un Array de JavaScript, `shift()` desplaza elementos y no debe asumirse O(1).

Elige considerando accesos, escrituras, orden, unicidad, tamaño y costo de mantener la estructura. No compares ni implementes Array, Map, Set y Queue por rutina: evalúa únicamente las opciones pertinentes al caso.

### Medición como contraste

Usa un contador de operaciones y al menos dos escalas de datos para contrastar la predicción. El tiempo medido complementa el análisis, pero no demuestra por sí solo una clase de complejidad; registra entorno y ruido. El benchmark de un sistema completo pertenece a la [unidad 12](../Etapa%202%20—%20Fundamentos/2.3%20—%20Performance%20Engineering.md).

## Diagnóstico único — reducir lookups repetidos

**Timebox:** 30–60 minutos; si aparece un hueco, extiende la práctica hasta 90 minutos.

**Contexto de partida:** aporta una función real o sanitizada que cruce dos colecciones o repita `includes`/`find` dentro de un loop; no necesitas una aplicación de proyecto.

**Decisiones que debes tomar:** variables de entrada, costo esperado, escalas, estructura pertinente —incluido conservar Array—, peor caso y dato que cambiaría la elección.

1. Antes de editar, define `n` y `m`, deriva tiempo y espacio, y predice qué ocurrirá al multiplicar los datos por 10.
2. Añade un contador de comparaciones y ejecuta dos tamaños reproducibles.
3. Si corresponde, construye una vez un `Set` o `Map`; recalcula el costo total, incluida su construcción y memoria. Si no corresponde, conserva el Array y justifica la decisión. Queue solo entra si el caso exige FIFO.
4. Compara contador y tiempos como evidencia complementaria; registra tamaños, entorno y ruido.
5. Documenta un peor caso o supuesto, el límite de la elección y qué dato la cambiaría.

## Entregable y evidencia

- **Artefacto:** informe breve con la función o enlace, predicción, mediciones, decisión y límite.
- **Evidencia:** contador de operaciones en dos escalas; tiempos, entorno y ruido como contraste complementario.
- **Caso negativo:** crecimiento observado que pueda falsar la predicción o una estructura descartada por las operaciones reales.
- **Límite:** peor caso o supuesto y dato que cambiaría la elección.

Puede provenir de código propio o laboral sanitizado; no añade otra aplicación de proyecto.

## Done cuando

- [ ] El informe define cada variable de entrada.
- [ ] El tiempo se deriva desde las operaciones dominantes.
- [ ] El espacio auxiliar se deriva desde las estructuras usadas.
- [ ] La predicción de crecimiento se contrasta con un contador en al menos dos escalas.
- [ ] Solo se comparan las estructuras pertinentes al caso.
- [ ] La elección se apoya en accesos, escrituras, orden, unicidad y tamaño reales.
- [ ] Si se introdujo Map o Set, se contabiliza su construcción.
- [ ] Si se introdujo Map o Set, se contabiliza su memoria adicional.
- [ ] Si se conserva Array, se justifica la decisión.
- [ ] Se documenta al menos un peor caso o supuesto.
- [ ] Se declara qué dato cambiaría la elección.
- [ ] Puede explicar problema, decisión, evidencia e incertidumbre consultando documentación.
