# 1.5 — Estructuras de Datos y Algoritmos

No es para entrevistas. Es para saber que un HashMap te da O(1) y un array lineal te da O(n) — y entender POR QUÉ.

- [ ] **Complejidad algorítmica — Big O**

Qué es O(1), O(log n), O(n), O(n log n), O(n²). Cómo analizar el tiempo y espacio de tu propio código. Dos loops anidados son O(n²) solo si ambos recorren n elementos de forma independiente; la complejidad depende del número total de iteraciones y de sus límites.

**Por qué importa:** Sin Big O, eliges estructuras de datos por intuición o por costumbre. Eso funciona con 100 registros — explota con 100.000. Cuando una feature de FreePress empieza a tardar segundos en producción y no sabes por dónde empezar a buscar, la respuesta casi siempre está en una complejidad que nunca analizaste.

**<span style="color: #29B6F6">Ejercicio:</span>** Toma 5 funciones de un proyecto real (idealmente en el backend, donde se procesa data) y analiza su complejidad temporal y espacial. Documenta el análisis en comentarios en el código.

**<span style="color: #FFA726">FreePress:</span>** Toma funciones del backend de FreePress — los endpoints que procesan listas de artículos son el caso perfecto para analizar complejidad (filtros, ordenamientos, búsquedas).

**Done cuando:** Puedes analizar una función, definir qué representa n y justificar su complejidad a partir del número total de operaciones, sin asumir que todo loop anidado es O(n²).

**Big O — En producción**

| Situación real                                                          | Qué está pasando                                                          | Cómo lo diagnosticas                                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Un endpoint tarda 2s con 1000 usuarios, pero 200s con 10.000            | Probablemente O(n²) — cada usuario se procesa contra todos los demás      | Miras loops anidados, llamadas a DB dentro de loops                          |
| La búsqueda de artículos es instantánea con 100, pero lenta con 100.000 | O(n) vs O(log n) o O(1) — falta índice o estructura optimizada            | Verificas si hay índice en la DB, si usas Set en lugar de Array para lookups |
| Una feature funciona perfecto en dev, explota en producción             | La diferencia de escala reveló complejidad oculta — O(n) que parecía O(1) | Profiles con datos reales, no con datos de test                             |

- [ ] **Arrays, Linked Lists, Stacks, Queues**

No "qué son" sino CUÁNDO usar cada uno y por qué. Un array tiene O(1) de acceso pero O(n) de inserción al principio. Una linked list es al revés: O(1) de inserción pero O(n) de acceso por índice.

**Por qué importa:** Cada vez que eliges el contenedor incorrecto para tu data, estás pagando un costo de performance invisible. El Stack es la estructura que el motor de JavaScript usa para la call stack — entenderlo explica por qué un stack overflow es un stack overflow y no un "error raro".

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa un Stack y una Queue desde cero en TypeScript usando arrays internamente. Después implementa la Queue usando una linked list y compara la complejidad de `enqueue` en ambas implementaciones.

**Done cuando:** Te dan un problema nuevo y puedes justificar en 1 minuto qué estructura de datos usarías y por qué — no solo "usaría un array" sino "usaría un array porque el acceso es por índice y no necesito inserciones frecuentes al principio".

**Recursos:**
- Libro: *Grokking Algorithms* (capítulos 2 y 3) — cubre arrays y linked lists con ilustraciones claras

**Arrays vs Linked Lists — En producción**

| Situación | Estructura correcta | Por qué |
|-----------|---------------------|---------|
| Necesitas acceder al elemento 5000 de una colección | Array | O(1) de acceso por índice |
| Necesitas insertar al principio frecuentemente | Linked List | Array es O(n) para insertar al principio (shift) |
| Implementas undo/redo en un editor | Stack | LIFO es exactamente lo que necesitas |
| Procesas tareas en orden de llegada | Queue | FIFO es el modelo natural |
| Una cola de tareas tiene 10.000 items y remover del medio es lento | Array es el problema | Linked List o heap según el caso |

- [ ] **Hash Tables (Maps/Dictionaries)**

LA estructura de datos más importante en programación del día a día. Cómo funciona el hashing internamente, qué son las colisiones y cómo se resuelven (chaining, open addressing), por qué un `Map` en JS es diferente a un objeto plano, y cuándo esa diferencia importa.

**Por qué importa:** El 80% del código que escribes usa alguna forma de hash map — objetos JS, Maps, diccionarios, caches. Sin entender cómo funcionan internamente, no puedes debuggear comportamientos raros (como por qué dos objetos con los mismos valores no son iguales como keys) ni justificar por qué O(1) no es siempre O(1) (amortized vs worst case).

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa tu propio HashMap desde cero en TypeScript con chaining para colisiones. Tiene que soportar `set`, `get`, y `delete`. Después compáralo con el `Map` nativo de JS en términos de API.

**<span style="color: #FFA726">FreePress:</span>** Usa `Map` para crear un índice de artículos por slug en FreePress — es el caso de uso clásico: necesitas lookup O(1) por slug en lugar de O(n) buscando en un array.

**Done cuando:** Puedes explicar qué pasa conceptualmente cuando haces `map.set(key, value)` y qué ocurre con una colisión. También puedes explicar que un objeto plano convierte sus keys a string (`{}` termina como `"[object Object]"`), mientras `Map` conserva objetos como keys por identidad.

**Recursos:**
- Libro: *Grokking Algorithms* (capítulo 5) — la mejor explicación visual de hash tables
- [JavaScript Map vs Object — When and how to use them](https://www.zhenghao.io/posts/js-map-vs-object) — diferencias concretas con ejemplos de código

**Hash Tables — En producción**

| Situación real | Qué está pasando | Cómo lo sabes |
|----------------|------------------|---------------|
| `getUser(id)` es instantáneo pero `getUsersByRole("admin")` tarda 5s | La primera es O(1) hash lookup por PK, la segunda es O(n) full scan | Entiendes inmediatamente qué índice falta en la DB |
| Tu caché en Redis funciona perfecto hasta que ciertos keys colisionan | Hash collision degrada O(1) a O(n) en el bucket | Sabes por qué el rendimiento se degrada y no es "Redis roto" |
| Dos objetos con los mismos campos son keys distintas en un `Map` | `Map` compara objetos por identidad, no por contenido | Usas un identificador estable si necesitas igualdad por valor |
| Dos usuarios con mismo email se crean cuando "no debería pasar" | El Set o Map está usando referencia en lugar de valor como key | Entiendes que `{email: "a@b.com"}` !== `{email: "a@b.com"}` para JS |
| Un Map de JS es más lento que un objeto plano para lookups simples | Estás usando la herramienta incorrecta | Object es más rápido para strings como keys, Map es mejor para keys variables |

- [ ] **Árboles y Grafos**

Binary trees, Binary Search Trees (BST), tree traversal (BFS y DFS — sus diferencias y cuándo usar cada uno). Por qué el DOM es un árbol, por qué las rutas de tu app son un grafo, por qué PostgreSQL usa B-Trees para índices.

**Por qué importa:** Los árboles están en todas partes sin que lo notes: el DOM, el AST del compilador de TypeScript, los índices de tu base de datos, el sistema de carpetas de tu OS. Entender BFS vs DFS no es teoría — es saber si conviene buscar "en anchura" (BFS, útil para el camino más corto) o "en profundidad" (DFS, útil para recorrer jerarquías completas).

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa BFS y DFS sobre un árbol binario. Después usa DFS para escribir una función que recorra una estructura de carpetas anidadas y retorne todos los archivos `.md` — directamente aplicable a cualquier sistema de archivos o categorías jerárquicas.

**<span style="color: #FFA726">FreePress:</span>** Si FreePress tiene categorías jerárquicas o un sistema de archivos de artículos, implementa el traversal directamente ahí. Si no, cualquier estructura de carpetas anidadas funciona.

**Done cuando:** Dado un problema nuevo, puedes decidir si necesitas BFS o DFS y justificar el porqué. Puedes explicar por qué PostgreSQL usa B-Trees (no BST) para índices y cuál es la diferencia entre ambos.

**Recursos:**
- Curso: MIT 6.006 Introduction to Algorithms (gratis en YouTube/OCW) — las lectures de grafos son especialmente buenas
- [Visualgo](https://visualgo.net/en) — visualizaciones interactivas de BFS, DFS y otras estructuras

**Árboles y Grafos — En producción**

| Situación | Estructura subyacente | Cómo se manifiesta |
|-----------|----------------------|-------------------|
| Tu DB tiene un índice en una columna y las queries son rápidas | B-Tree (no BST) | Los índices de PostgreSQL/MySQL usan B-Trees para balancear acceso a disco |
| El DOM de tu página es una jerarquía de elementos | Árbol | `document.querySelector` recorre el árbol |
| Las rutas de tu app web definen navegación | Grafo | El router resuelve cuál componente mostrar basado en el path |
| Necesitas el camino más corto entre dos puntos | BFS sobre grafo | GPS, redes sociales (grados de separación) |
| Recorrer todas las carpetas de un proyecto | DFS sobre árbol de archivos | `find`, `grep -r` usan traversal de árbol |
| Una query recursiva en SQL (employees → manager → CEO) | Árbol/grafo en la DB | `WITH RECURSIVE` en PostgreSQL |

- [ ] **Algoritmos de ordenamiento**

QuickSort, MergeSort y los trade-offs entre algoritmos. ECMAScript exige que `Array.prototype.sort()` sea estable, pero no prescribe TimSort ni otro algoritmo: la implementación depende del motor. El objetivo es entender por qué O(n log n) es el límite teórico inferior del caso general para ordenamiento basado en comparaciones.

**Por qué importa:** Cada vez que llamas a `.sort()` en JS sin pasarle una función comparadora, el comportamiento es distinto entre strings y números — y hay un bug clásico esperándote. Entender los algoritmos de ordenamiento te explica por qué ese bug existe y cómo evitarlo.

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa MergeSort en TypeScript. Después mide con `performance.now()` la diferencia entre tu MergeSort, `.sort()` nativo, y un BubbleSort (O(n²)) sobre un array de 10.000 elementos. Documenta los resultados.

**Done cuando:** Puedes explicar por qué O(n log n) es el mejor que se puede hacer con comparaciones (sin memorizar la demostración formal, pero entendiendo la intuición). Puedes explicar qué pasa si haces `[1, 10, 2, 20].sort()` en JS y por qué da `[1, 10, 2, 20]` en lugar de `[1, 2, 10, 20]`.

**Recursos:**
- [Sorting Algorithms Visualized](https://www.toptal.com/developers/sorting-algorithms) — compara visualmente cómo opera cada algoritmo

**Ordenamiento — En producción**

| Situación | Qué está pasando | Lección |
|-----------|------------------|---------|
| `[3, 10, 2].sort()` devuelve `[10, 2, 3]` en JavaScript | `.sort()` convierte a strings por defecto | Siempre pasar comparador para números |
| El frontend ordena 1000 items y tarda poco | El motor usa una implementación optimizada de `sort` | Mide antes de reemplazarla por código propio |
| Ordenar por múltiples criterios (nombre, luego fecha) | Stable sort importa | ECMAScript exige estabilidad, sin fijar el algoritmo |
| Tienes que ordenar datos que casi ya están ordenados | Algunos algoritmos aprovechan mejor ese patrón | La implementación depende del motor; mide con tus datos |

- [ ] **Recursión y Programación Dinámica**

Entender la call stack, base case, cómo evitar stack overflow. Memoización como técnica de optimización. Cuándo un problema recursivo se puede resolver con DP y cuándo no vale la pena la complejidad extra.

**Por qué importa:** La recursión no es solo un truco de entrevista — aparece en tree traversal, en parsers, en el modelo de componentes de frameworks. Y la memoización es el concepto detrás de `useMemo` en React y de las funciones de caching. Entender uno te da el otro gratis.

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa Fibonacci de forma recursiva naive, luego con memoización, y mide la diferencia de performance para `fib(40)`. Documenta cuántas llamadas hace cada versión usando un contador interno.

**Done cuando:** Puedes explicar por qué la versión recursiva naive de Fibonacci es O(2^n) y la versión con memoización es O(n). Puedes identificar cuándo un problema tiene "subproblemas superpuestos" (el requisito para aplicar DP) versus cuándo la recursión simple alcanza.

**Recursos:**
- Libro: *Grokking Algorithms* (capítulo 9 — Dynamic Programming) — accesible sin ser superficial
- [Recursion visualizer](https://recursion.vercel.app/) — para ver la call stack en acción

**Recursión y DP — En producción**

| Situación | Concepto aplicado | Ejemplo |
|-----------|-------------------|---------|
| Tu componente de Angular/React tiene componentes anidados | Recursión en el render | El tree de componentes se recorre recursivamente |
| `useMemo` o `useCallback` en React | Memoización | Guardar resultados para no recalcular |
| Un parser de JSON/XML | Recursión natural | La estructura anidada se procesa recursivamente |
| Cálculo de Fibonacci en tu app es lento | Sin memoización, es O(2^n) | Con memoización pasa a O(n) |
| Algoritmos de pathfinding en un juego | DP o memoización | No recalcular caminos ya explorados |
| Maximum call stack size exceeded | Recursión sin base case o muy profunda | Convertir a iteración o aumentar stack limit |
