## Propósito

Usar modelos y coding agents como sistemas probabilísticos con permisos, no como oráculos. Debes poder anticipar fallos, elegir evidencia externa y limitar el impacto antes de delegar.

## Modelo mínimo

### Modelo, sistema y agente no son lo mismo

- **Modelo:** recibe tokens de contexto y produce una distribución para los siguientes tokens.
- **Sistema de AI:** añade instrucciones, retrieval, memoria, filtros, herramientas y una interfaz alrededor del modelo.
- **Agente:** ejecuta un ciclo de observar, decidir y actuar mediante herramientas hasta detenerse o agotar un límite.

Una mejora o fallo puede provenir de cualquiera de esas capas. No atribuyas al modelo algo causado por contexto omitido, una herramienta, permisos o el harness.

### Contexto no es memoria ni verdad

La ventana de contexto contiene instrucciones, código, conversación y resultados de herramientas visibles en esa ejecución. Tiene capacidad limitada y compite por atención. Más contexto puede ayudar, distraer o introducir instrucciones no confiables.

Antes de delegar, distingue:

- fuente autoritativa y versión vigente;
- datos necesarios frente a “por si acaso”;
- contenido no confiable que podría contener prompt injection;
- secretos, datos personales o código que no debe salir del límite permitido.

### La salida plausible necesita un oracle externo

El objetivo generativo no garantiza verdad, compatibilidad ni seguridad. En código aparecen patrones como:

- API, parámetro o versión inexistente;
- happy path correcto y edge case omitido;
- cambio que ignora una convención o invariante del repositorio;
- tests modificados para aceptar el resultado en vez de proteger comportamiento;
- dependencia o abstracción innecesaria;
- afirmación de que un check pasó sin evidencia de ejecución.

El oracle adecuado puede ser un test, typecheck, compilador, constraint de base de datos, benchmark, documentación primaria, diff o revisión humana. El propio modelo no valida de forma independiente su salida.

### Variación y sampling

Temperature y top-p modifican cómo se elige entre tokens probables. Su efecto y rango dependen del proveedor; una configuración baja puede reducir variación, pero no garantiza corrección ni reproducibilidad. Registra modelo, fecha, configuración, contexto y herramientas cuando compares resultados.

### Riesgo determina autonomía

| Impacto y verificación | Autonomía razonable |
|---|---|
| Local, reversible y con oracle fuerte | actuar en sandbox y presentar diff/evidencia |
| Reversible pero con oracle parcial | proponer o actuar con revisión antes de integrar |
| Externo, sensible o difícil de revertir | pedir aprobación antes de ejecutar |
| Alto impacto y sin oracle fiable | no delegar todavía; mejorar contrato y controles |

Nunca entregues permisos amplios solo para evitar escribir el alcance.

## Preparación de la eval

Elige cuatro cambios diminutos que un agente pueda resolver de forma aislada y que tengan un resultado ejecutable. Dos deben ser casos normales y dos deben contener un límite probable: input vacío, duplicado, autorización, concurrencia, versión de API o error de red.

Antes de pedir soluciones, registra para cada caso:

```md
Tarea:
Archivos permitidos:
Comportamiento esperado:
Caso adversarial oculto:
Checks:
Permisos y stop condition:
```

No ejecutes una práctica adicional aquí: esta preparación alimenta el único experimento de [4.13](../Etapa%204%20—%20Profundización/4.13%20—%20Fundamentos%20de%20ML-AI%20que%20necesitas%20como%20Dev.md).

## Primera pasada completa cuando

- [ ] Puedes distinguir modelo, sistema y agente sin atribuirles capacidades intercambiables.
- [ ] Para una tarea real identificaste contexto autoritativo, datos sensibles, permisos, oracle y rollback.
- [ ] Puedes explicar por qué fluidez, baja temperature o afirmaciones del agente no garantizan corrección.
- [ ] Preparaste cuatro casos y fijaste aceptación antes de ver las respuestas.
