# 2.11 — Sistemas Operativos (Profundizar)

> **Estado:** `ACTIVO` · Componente de la unidad 2 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** event loop de [1.2](../Etapa%201%20—%20Entrada/1.2%20—%20JavaScript%20Internals.md).
> **Cierre:** procesos, memoria y streams informan el diagnóstico; la evidencia de la unidad se concentra en [2.7](2.7%20—%20Concurrency%20y%20Parallelism.md).

## Propósito

Relacionar el proceso Node.js con su memoria e I/O para distinguir una referencia retenida, una carga sin backpressure y un cálculo que bloquea. El sistema operativo aporta aislamiento y recursos; el runtime administra el heap de JavaScript sobre ese proceso.

## Proceso y memoria observable

Un proceso tiene espacio de direcciones, threads, file descriptors y estado gestionado por el sistema operativo. En Node.js conviene separar:

- **heap de JavaScript:** objetos administrados por el garbage collector;
- **stack de cada thread:** frames de llamadas y datos de ejecución;
- **external/array buffers:** memoria asociada al runtime u objetos nativos fuera del heap administrado;
- **RSS:** páginas residentes del proceso, que incluyen más que el heap;
- **memoria virtual:** direcciones reservadas o mapeadas, no equivalente a RAM consumida.

Una subida de RSS no demuestra un leak. Compara heap usado, external memory, patrón de carga, garbage collection y estabilización después de retirar carga. El sistema puede conservar páginas o el allocator puede no devolverlas de inmediato.

Procesos y Worker Threads se eligen en [2.7](2.7%20—%20Concurrency%20y%20Parallelism.md). Estados del scheduler, zombies, context switching fino, IPC avanzado y `strace` quedan JIT ante un diagnóstico que los necesite.

## Leaks por referencias retenidas

El garbage collector libera objetos inalcanzables; no puede liberar un objeto que sigue referenciado aunque ya no sea útil. Fuentes comunes:

- caches y colecciones sin política de descarte;
- listeners, timers o subscriptions sin cleanup;
- closures que capturan estructuras grandes;
- requests o Promises retenidas por trabajo que no termina;
- handles nativos y buffers que no se liberan.

Reproduce con una carga controlada y compara snapshots o perfiles bajo las mismas condiciones. Busca una ruta de retención desde una raíz y confirma el arreglo repitiendo la carga; el tamaño de un objeto aislado no identifica la causa.

Tomar un heap snapshot puede pausar el proceso, aumentar mucho la memoria y copiar datos sensibles. Hazlo en laboratorio o réplica con inputs sanitizados y acceso restringido, no sobre la única instancia que atiende tráfico.

## Streams y backpressure

Leer todo un archivo o response en memoria hace que el consumo crezca con el input. Un stream procesa chunks y puede acotar memoria, siempre que respete **backpressure**: cuando el destino no puede seguir el ritmo, el productor debe pausar o limitar lo pendiente.

En Node.js, `stream.pipeline` o `node:stream/promises` `pipeline` conectan etapas y propagan error/cierre para facilitar cleanup. Maneja abort y errores de cada fuente/destino; un pipe incompleto puede dejar file descriptors o requests abiertos.

Streaming no vuelve barato el trabajo: un `Transform` CPU-bound ejecutado en el event loop todavía puede bloquear. Muévelo según la evidencia y el modelo de [2.7](2.7%20—%20Concurrency%20y%20Parallelism.md).
