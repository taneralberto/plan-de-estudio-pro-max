- [ ] **Procesos y el Modelo de Ejecución del SO**

Qué es un proceso desde la perspectiva del sistema operativo: un programa en ejecución con su propio espacio de memoria, stack, heap, y file descriptors. Process states: running, ready, blocked, zombie — y cómo pasa un proceso de un estado a otro. Context switching: lo que el OS hace cuando cambia de un proceso a otro (guardar y restaurar registros, page tables, caches). Scheduling: cómo el OS decide qué proceso corre en cada instante. Threads como unidades de ejecución dentro de un proceso — comparten espacio de memoria pero tienen stack propio. La diferencia entre kernel-level threads y user-level threads, y por qué importa.

**Por qué importa:** Cuando ejecutas `top` o `htop` y ves tu proceso en estado R, S, o Z, estás viendo el scheduler del OS en acción. Cuando Kubernetes mata un pod por OOM o throttlea CPU, está usando el mismo modelo de procesos y cgroups. Los procesos zombie en Docker no son una metáfora — son procesos reales cuyo padre nunca llamó `wait()`. Entender el modelo de ejecución del SO es lo que te permite diagnosticar por qué tu app se comporta distinto en producción que en desarrollo, leer métricas correctamente, y entender los límites de lo que un runtime puede hacer por encima del SO.

**<span style="color: #29B6F6">Ejercicio:</span>** Abre `top` o `htop` y observa los process states en la columna STATUS. Identifica procesos en estado R (running), S (sleeping), y Z (zombie). Crea un proceso zombie a propósito (un proceso hijo que termina antes de que el padre llame `wait()`) y verifica que aparezca como Z. Luego crea un programa que genere múltiples procesos y observa cómo el OS hace context switching usando `strace` o `pidstat -w`.

**<span style="color: #FFA726">FreePress:</span>** Observa los procesos del backend de FreePress en Docker con `docker stats` y `htop` — identifica cuántos procesos crea, en qué estados están, y verifica que el graceful shutdown no deje procesos zombie.

- [ ] **Memory Management — Stack vs Heap**

Qué es el stack y qué es el heap, y cómo el motor de JavaScript decide dónde va cada valor. Por qué JavaScript tiene garbage collection y C no. Qué es un memory leak en JS (sí, existen aunque haya GC), cómo se producen, y cómo detectarlos con Chrome DevTools.

**Por qué importa:** Los memory leaks en Node.js son más comunes de lo que parece — event listeners no removidos, closures que retienen referencias, caches que crecen sin límite. Si el servidor crece en memoria con el tiempo y eventualmente cae, la causa es casi siempre un leak. Sin saber buscarlos, no puedes arreglarlos.

**<span style="color: #29B6F6">Ejercicio:</span>** Crea un memory leak a propósito en Node.js (pista: usé un event emitter que nunca limpia sus listeners, o un array global que crece sin límite). Luego debuggealo con `node --inspect` y Chrome DevTools — toma un heap snapshot, identifica el leak, arreglalo, y toma otro snapshot para confirmar.

**<span style="color: #FFA726">FreePress:</span>** Inspecciona el backend de FreePress en busca de memory leaks: identifica event listeners que no se limpian, caches sin límite, y closures que retienen referencias innecesarias.

**Done cuando:** Puedes abrir Chrome DevTools en la sección Memory, tomar un heap snapshot de una app Node.js, e identificar qué objetos están creciendo entre snapshots. Puedes explicar por qué `let x = []` en el scope global de un módulo ES6 puede ser un leak si nunca se vacía.

- [ ] **File Systems y I/O**

Cómo funciona el I/O por debajo: syscalls, buffers, streams. Por qué `fs.readFileSync` bloquea el event loop y `fs.createReadStream` no — y qué significa eso en producción. Streams en Node.js: Readable, Writable, Transform, Duplex.

**Por qué importa:** Si tu backend maneja uploads de archivos, exportaciones, o cualquier lectura de archivos en el servidor, la diferencia entre blocking y streaming es la diferencia entre una API que responde en 200ms y una que bloquea todos los requests durante 3 segundos mientras lee un archivo grande.

**<span style="color: #29B6F6">Ejercicio:</span>** Procesa un archivo de 1GB con `fs.readFileSync` y mide el consumo de RAM y el tiempo de bloqueo. Luego haz lo mismo con `fs.createReadStream` y un Transform stream para procesar el contenido línea por línea. Documenta la diferencia en memoria y tiempo de respuesta.

**<span style="color: #FFA726">FreePress:</span>** Si FreePress maneja uploads de archivos o exportaciones, verifica que usen streams y no `readFileSync`. Reemplaza cualquier uso de `readFileSync` en endpoints por streaming.

- [ ] **Signals e IPC (Inter-Process Communication)**

Qué pasa cuando haces `Ctrl+C` (SIGINT) o cuando un proceso recibe `SIGTERM`. Cómo se comunican procesos entre sí: pipes, sockets Unix, shared memory. Por qué Docker y Docker Compose usan SIGTERM para graceful shutdown y por qué ignorarlo es un bug en producción.

**Por qué importa:** En producción, cuando haces un deploy nuevo, el proceso viejo recibe SIGTERM y tiene que terminar limpiamente — cerrar conexiones a la DB, terminar requests en curso, limpiar caches. Si no manejas SIGTERM, tu app corta conexiones a mitad de un request y corrompes data. Esto no es avanzado: es lo básico de cualquier backend en producción.

**<span style="color: #29B6F6">Ejercicio:</span>** Agrega graceful shutdown a tu backend — maneja `SIGTERM` y `SIGINT` para cerrar la conexión a PostgreSQL y Redis correctamente antes de que el proceso termine. Verifica que funciona corriendo la app con Docker y haciendo `docker stop` (que envía SIGTERM).

**<span style="color: #FFA726">FreePress:</span>** Agrega graceful shutdown al backend de FreePress — maneja SIGTERM y SIGINT para cerrar conexiones a PostgreSQL y Redis limpiamente antes de que el proceso termine. Verifica con `docker stop`.

**Done cuando:** Puedes explicar la diferencia entre `SIGTERM` y `SIGKILL` — por qué uno se puede capturar y el otro no. Puedes mostrar el código de graceful shutdown y explicar qué pasaría si ese código no existiera durante un deploy con zero-downtime.
