# 2.12 — Redes para Backend

> **Estado:** `ACTIVO ★` · unidad 11 del [ROADMAP](../ROADMAP.md).
>
> **Prerrequisitos:** un backend accesible localmente o en un sandbox y una terminal con `curl`, `dig` y `openssl`.
>
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Localizar si un request falla en resolución, conexión, identidad TLS o semántica HTTP y producir evidencia reproducible sin confundir capas.

## Orientación

**Qué debes lograr:** reproducir y diagnosticar un solo fallo de DNS, TLS o HTTP con herramientas de terminal.

**Cómo abordarlo:** predice la capa, conserva un baseline y usa el probe mínimo que falsifique una hipótesis alternativa antes de corregir.

**Entregarás:** un informe corto y las salidas exactas de terminal que demuestran baseline, fallo y corrección.

**Investiga fuera solo si:** los probes mínimos no separan las capas o necesitas confirmar comportamiento en la documentación de la herramienta.

## Modelo mínimo

1. **Flujo:** URL → resolver y caché DNS → IP y ruta → conexión TCP al puerto → handshake TLS cuando aplica → request y response HTTP. El render del browser queda fuera.
2. **DNS:** un resolver recursivo consulta o reutiliza respuestas de servidores autoritativos. Distingue registros A, AAAA y CNAME, TTL y caché. Un cambio se observa cuando expiran o se renuevan cachés según sus TTL; no existe una “propagación global” uniforme.
3. **TCP:** ofrece una conexión ordenada y confiable entre puertos. Distingue timeout, reset y connection refused; UDP sirve aquí solo como contraste.
4. **TLS:** negocia parámetros y claves y aporta confidencialidad, integridad y autenticación del endpoint cuando se validan CA, cadena, SAN/hostname y fechas. SNI comunica el hostname durante el handshake. HTTPS no demuestra que la aplicación sea segura.
5. **HTTP:** separa método, status, headers y body; redirects, timeouts y retries cambian el comportamiento observable. Un 4xx o 5xx es una respuesta HTTP, no un fallo de red. Reconocer el protocolo negociado (`http/1.1` o `h2`) basta.

## Ejercicio único — fallo reproducible en una capa

**Timebox:** aplica la [regla antiatasco canónica](../METODOLOGIA.md#regla-antiatasco); el tiempo es una alarma y no sustituye la evidencia.

**Contexto proporcionado:** un backend local o sandbox y `dig`, `curl` y `openssl`; usa solo la herramienta necesaria para cada probe.

**Decisiones que debes tomar:** elige un único fallo controlado de DNS, TLS o HTTP, la hipótesis alternativa que falsarás y la corrección que mantenga las garantías esperadas.

1. Captura el baseline de una URL válida con `curl`, su resolución y, cuando aplique, su certificado y protocolo.
2. Elige **un** fallo controlado: un hostname bajo `.invalid` o registro de laboratorio incorrecto; un certificado local autofirmado o con SAN distinto; o un endpoint de laboratorio que redirija, demore o devuelva 503.
3. Antes de ejecutarlo, predice la capa, la salida esperada y una hipótesis alternativa.
4. Guarda el comando y la salida exacta. Usa `dig`, `curl -v --trace-time`/`--write-out` u `openssl s_client -connect host:443 -servername host -verify_return_error` según sea necesario para distinguir las fases.
5. Corrige el hostname, certificado o comportamiento y repite el mismo probe. `curl -k` puede aislar un fallo de verificación TLS, pero no cuenta como arreglo.
6. Redacta el informe con baseline, fallo, capa, evidencia, hipótesis descartada, corrección, prueba negativa y límite de la observación.

## Entregable y evidencia

- **Artefacto:** informe corto con problema, decisión, corrección, límite e incertidumbre.
- **Evidencia independiente:** comandos y salidas exactas del baseline, fallo y mismo probe corregido.
- **Caso negativo:** el único fallo controlado elegido.
- **Límite:** qué no permiten concluir esos probes.

## Done cuando

- [ ] El baseline y su salida quedaron conservados.
- [ ] La predicción de capa y salida se registró antes de provocar el fallo.
- [ ] Se reprodujo un solo fallo de DNS, TLS o HTTP.
- [ ] El comando del fallo es ejecutable.
- [ ] La salida exacta del fallo quedó conservada.
- [ ] La evidencia distingue resolución, conexión, TLS y respuesta HTTP.
- [ ] La explicación no confunde un 5xx con un fallo de red.
- [ ] Una hipótesis alternativa fue falsada con `dig`, `curl` u `openssl`.
- [ ] La corrección pasa el mismo probe.
- [ ] La corrección no desactiva la validación TLS cuando aplica.
- [ ] El informe explica que TLS aporta confidencialidad, integridad y autenticación del endpoint.
- [ ] El informe separa esas garantías de los riesgos de aplicación que TLS no cubre.
- [ ] El límite de la observación quedó documentado.
- [ ] El artefacto y la evidencia independiente están enlazados.
- [ ] Explicaste problema, decisión, evidencia e incertidumbre.
- [ ] Completaste R1 sin apuntes.
