# 2.12 — Redes en Profundidad

> **Cierre 🔴:** además de los checks locales, cumple el [cierre de un tema crítico](../METODOLOGIA.md#cierre-de-un-tema-crítico).

DNS, TCP, TLS, HTTP — cada request pasa por múltiples capas. Sin entenderlas, debuggear es adivinanza.

---

- [ ] **Modelo TCP/IP capa por capa**

No memorizar las 7 capas OSI — entender las 4 que importan: Link (Ethernet, WiFi), Internet (IP, routing), Transport (TCP vs UDP — cuándo cada uno), Application (HTTP, DNS, TLS). Qué pasa REALMENTE cuando escribes una URL en el browser: DNS lookup, TCP handshake, TLS handshake, HTTP request/response.

**Por qué importa:** Cuando un request falla con un error de red, hay varias capas donde puede estar el problema. Si no sabes qué capa hace qué, no sabes dónde buscar. ¿Es un problema de DNS? ¿De certificado TLS? ¿De timeout TCP? La respuesta cambia completamente el debugging.

**<span style="color: #29B6F6">Ejercicio:</span>** Usa Wireshark para capturar un request HTTP a un servidor local. Identifica los paquetes del TCP handshake (SYN, SYN-ACK, ACK), los paquetes TLS, y el HTTP request/response. Documenta qué ves en cada capa.

**<span style="color: #FFA726">FreePress:</span>** Captura con Wireshark un request completo al backend de FreePress: DNS lookup, TCP handshake, TLS handshake, y HTTP request/response.

**Done cuando:** Puedes explicar, sin mirar notas, qué pasa en la red cuando alguien accede a tu sitio — desde el DNS lookup hasta que el browser renderiza la página. Puedes identificar en qué capa del modelo TCP/IP ocurre cada paso.

**Recursos:**

- [ ] **DNS — El sistema telefónico de internet**

Cómo funciona la resolución DNS de punta a punta: DNS recursivo, root servers, TLD servers, authoritative nameservers. TTL y por qué el caching importa. Por qué cambiar un registro DNS tarda horas (propagación). Registros A, CNAME, MX, TXT — cuándo se usa cada uno.

**Por qué importa:** Cuando deployas a producción, vas a configurar DNS. Cuando algo falla, la primera sospecha siempre es "¿será el DNS?". Sin entender TTL y propagación, vas a esperar horas sin saber si el cambio llegó o no. Y si configuras mal un CNAME, tu dominio puede quedar roto silenciosamente.

**<span style="color: #29B6F6">Ejercicio:</span>** Usa `dig` para resolver un dominio paso a paso — primero consulta un root server, luego el TLD, luego el authoritative. Después configura un dominio custom (o usa un subdominio de prueba) y verifica con `dig` que los registros A y CNAME apuntan donde corresponde.

**<span style="color: #FFA726">FreePress:</span>** Configura los registros DNS para deployar FreePress a un proveedor de hosting y verifica con `dig` que apuntan correctamente.

**Done cuando:** Puedes explicar por qué `dig google.com` puede darte una respuesta diferente a `dig @8.8.8.8 google.com`. Puedes explicar qué significa un TTL de 300 segundos y cuándo tiene sentido bajar el TTL antes de migrar un dominio.

- [ ] **TLS/SSL — Cómo funciona HTTPS**

El handshake TLS: cómo el cliente y el servidor negocian una clave de sesión sin que nadie en el medio pueda leerla (Diffie-Hellman key exchange). Qué son los certificados digitales y las Certificate Authorities. Encriptación simétrica vs asimétrica — por qué TLS usa ambas y cuál es el rol de cada una. Por qué Let's Encrypt cambió internet. Qué es certificate pinning y cuándo tiene sentido.

**Por qué importa:** Cualquier proyecto en producción necesita HTTPS. Sin entender TLS, vas a seguir tutoriales de Certbot sin saber qué estás haciendo — y cuando algo falle (certificado expirado, error de cadena de confianza, handshake failure), no vas a saber por dónde empezar. Además, las entrevistas senior siempre preguntan sobre HTTPS.

- [ ] **Latencia, Throughput y Bandwidth — No son lo mismo**

La diferencia entre latencia (tiempo hasta el primer byte), throughput (datos por segundo), y bandwidth (capacidad máxima del canal) — y por qué optimizar uno no necesariamente mejora los otros. CDNs y cómo reducen latencia acercando los datos al usuario. Edge computing. Cómo medir latencia real de una API.

**Por qué importa:** "La API está lenta" no es suficiente información para arreglar nada. Necesitas saber si es latencia (tarda en responder el primer byte) o throughput (responde rápido pero transfiere poco a poco). Un CDN resuelve latencia geográfica pero no resuelve queries lentas en la base de datos. Sin estas distinciones, las optimizaciones son a ciegas.

**<span style="color: #29B6F6">Ejercicio:</span>** Mide la latencia y el throughput de los principales endpoints de tu backend con `k6` o `wrk`. Después agrega un header de caché a las respuestas de contenido estático y mide de nuevo. Documenta qué cambió y por qué.

**<span style="color: #FFA726">FreePress:</span>** Mide latencia y throughput de los endpoints de FreePress con k6. Luego agrega headers de caché para contenido estático y compara los resultados.

**Done cuando:** Puedes mirar los resultados de una prueba de carga y distinguir si el cuello de botella es latencia o throughput. Puedes explicar por qué servir assets estáticos desde un CDN reduce la latencia para usuarios en otro país, pero no cambia el tiempo de una query a la DB.

**Recursos:**
- [High Performance Browser Networking](https://hpbn.co/) — de Ilya Grigorik (Google), gratis online. El capítulo de latencia es el mejor que existe
- [k6](https://k6.io/) — herramienta moderna de load testing para medir throughput y latencia de APIs

- [ ] **HTTP/2 y HTTP/3 (QUIC) — La evolución del protocolo**

HTTP/2 trajo multiplexing: una binary framing layer que reemplaza el protocolo texto de HTTP/1.1, permitiendo múltiples requests sobre una sola conexión TCP sin el límite de 6 conexiones paralelas por dominio. Sumale compresión de headers con HPACK. HTTP/2 también definió Server Push, pero los navegadores principales lo deshabilitaron o retiraron y no debe tratarse como una optimización recomendada. Pero HTTP/2 tiene un problema: head-of-line blocking a nivel TCP — si se pierde un paquete TCP, TODOS los streams que comparten esa conexión se bloquean hasta que se recupere ese paquete.

HTTP/3 resuelve esto con QUIC — un protocolo de transporte construido sobre UDP donde cada stream es independiente: un paquete perdido solo afecta ese stream, no los demás. Además, QUIC hace 0-RTT para establecer la conexión (vs TCP handshake + TLS handshake = múltiples RTTs en HTTP/2) y soporta connection migration: si pasás de WiFi a datos móviles, la conexión no se corta porque el Connection ID se mantiene.

**Por qué importa:** Los browsers ya usan HTTP/2 por default, y HTTP/3 está creciendo rápido. Si no entiendes cómo funcionan, no entiendes por qué tu API puede ser más lenta de lo esperado en connections inestables — y no puedes configurar tu infraestructura para sacarles provecho. La buena noticia: a nivel de aplicación, nada cambia — los métodos HTTP, headers, y status codes son los mismos. Lo que cambia es la infraestructura: load balancers, CDNs, y reverse proxies necesitan soportar HTTP/2 o HTTP/3 para terminar la conexión correctamente.

**<span style="color: #29B6F6">Ejercicio:</span>** Inspecciona una request HTTP/2 en Chrome DevTools (Network tab → Protocol column, o usa `curl --http2 -v`). Identifica los streams multiplexados y compara con una request HTTP/1.1. Después, habilita HTTP/3 con `curl --http3` (o verifica el header `Alt-Svc` en la response) y compara los tiempos de conexión.

**<span style="color: #FFA726">FreePress:</span>** Verifica que el servidor de FreePress soporte HTTP/2 (ALPN en la negociación TLS). Si es posible, configura soporte para HTTP/3 y verifica que los clientes se conecten vía QUIC usando `curl --http3` o el indicador de protocolo en DevTools.

**Done cuando:** Puedes explicar por qué HTTP/2 multiplexing no elimina el head-of-line blocking (es a nivel TCP, no a nivel stream) y por qué QUIC lo resuelve. Puedes identificar si una request usa HTTP/1.1, HTTP/2, o HTTP/3 en DevTools, y sabes qué configurar en un load balancer o CDN para habilitar cada protocolo.

**Recursos:**

- [QUIC and HTTP/3](https://http3-explained.haxx.se/) — del mismo autor, explica QUIC y HTTP/3 paso a paso
