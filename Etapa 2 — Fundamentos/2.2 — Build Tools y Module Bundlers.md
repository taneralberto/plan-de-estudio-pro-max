# 2.2 — Build Tools y Module Bundlers

> **Ruta Web/Frontend:** aprende el build que usa tu proyecto. Monorepos y packaging dual CJS/ESM son 🟢 JIT, no migraciones obligatorias.

El código que escribes no es exactamente el que se ejecuta. Entender transpilación, bundling, minificación y tree shaking permite diagnosticar el build.

---

- [ ] **Qué hace un bundler y POR QUÉ existe**

El problema original: los browsers no soportaban módulos (`import`/`export`) y cargar 200 archivos JavaScript por separado era lento (una request HTTP por archivo en la era de HTTP/1.1). La solución: tomar todos los módulos y empaquetarlos en uno (o pocos) archivos. La evolución incluye Webpack (configurable y amplio), Rollup (orientado a librerías), esbuild (compilado y enfocado en velocidad) y Vite (servidor de desarrollo y build de producción). Conceptos que todo bundler implementa: **tree shaking** (eliminar código que nunca se usa — solo funciona con ESM estático), **code splitting** (dividir el bundle en chunks que se cargan bajo demanda), **lazy loading** (cargar un chunk solo cuando se necesita, no al inicio).

**Por qué importa:** Cuando el bundle de tu proyecto pesa demasiado, cuando el build tarda 3 minutos, o cuando una librería que removiste sigue apareciendo en el output, necesitas entender el pipeline para diagnosticar. Sin este conocimiento, esas situaciones se vuelven cajas negras y los cambios se hacen por ensayo y error.

- [ ] **Vite en profundidad**

Por qué Vite es dramáticamente más rápido que Webpack en desarrollo: en dev usa ESM nativo del browser — no bundlea nada, el browser pide cada módulo directamente al servidor, y Vite solo transpila lo que se pide (on-demand). En producción usa Rollup para generar un bundle optimizado. Hot Module Replacement (HMR): cómo Vite reemplaza solo el módulo que cambió sin recargar la página, preservando el estado de la aplicación. Plugin system: cómo extender Vite con plugins de Rollup (compatibles) y plugins propios. Configuración para casos reales: proxy para APIs, variables de entorno, configuración de paths, optimización de dependencias.

**Por qué importa:** Los frameworks modernos usan esbuild como transpilador en dev — entender el modelo de Vite (ESM nativo + transpilación on-demand) te permite diagnosticar problemas de build, configurar el entorno correctamente, y entender por qué el dev server es tan rápido comparado con Webpack clásico.

Documenta cada configuración con el motivo.

- [ ] **Monorepos — Turborepo, Nx, pnpm workspaces**

El problema que resuelven: cuando tienes múltiples paquetes o aplicaciones relacionadas, mantenerlos en repos separados genera fricción — cambios que afectan a varios paquetes requieren PRs coordinados, versionado sincronizado a mano, y `npm link` para desarrollo local. Un monorepo los pone todos en el mismo repo con herramientas que los gestionan. **pnpm workspaces:** la base — define los paquetes del monorepo, gestiona dependencias compartidas evitando duplicados. **Turborepo:** task orchestration — corre builds, tests y lints en paralelo respetando dependencias entre paquetes, con caché inteligente. **Nx:** similar a Turborepo pero con más herramientas integradas — generators, affected analysis (solo corre tests de lo que cambió), visualización del grafo de dependencias.

**Por qué importa:** Cualquier proyecto que crece más allá de una sola aplicación necesita compartir tipos, utilidades y configuraciones entre sus partes. Sin un monorepo, compartir tipos requiere publicar un paquete npm para cada cambio. Con un monorepo, los tipos compartidos son un paquete interno que cualquier parte del proyecto puede importar directamente.

**<span style="color: #29B6F6">Ejercicio:</span>** Convierte tu proyecto en un monorepo con pnpm workspaces y Turborepo. La estructura mínima: `packages/shared` (tipos TypeScript compartidos entre frontend y backend), `apps/frontend`, `apps/backend`. Configura Turborepo para que `turbo build` buildee los tres en el orden correcto (shared primero, luego las apps) y con caché.

**<span style="color: #FFA726">FreePress:</span>** FreePress tiene tipos compartidos entre frontend y backend, y proyectos satélite (`freepress-cli`, `fp-ui`, `fp-ai-assistant`). Convierte la estructura en un monorepo con pnpm workspaces y Turborepo, manteniendo la estructura actual de `packages/shared`, `apps/frontend`, `apps/backend`.

**Done cuando:** Puedes crear un monorepo con pnpm workspaces desde cero, configurar Turborepo para que las tareas respeten el orden de dependencias entre paquetes, y hacer que un tipo definido en `packages/shared` sea importable en ambas apps sin publicarlo a npm.
