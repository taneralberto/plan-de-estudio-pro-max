# 2.3 — Performance y Elección de Datos

> **Estado:** `ACTIVO` · unidad 12 del [ROADMAP](../ROADMAP.md).
>
> **Prerrequisitos:** transacciones y `EXPLAIN` de la [unidad 9](2.4%20—%20SQL%20y%20Modelado%20Relacional.md) y un backend reproducible; reutiliza el probe de la [unidad 11](2.12%20—%20Redes%20en%20Profundidad.md) si existe. El dataset y el script de carga se crean en la práctica.

## Propósito

Medir un baseline comparable, localizar el cuello y elegir el cambio mínimo —incluido no cambiar— sin introducir caché o almacenamiento por intuición.

## Orientación

**Qué debes lograr:** localizar un cuello con percentiles y una señal independiente, y decidir si intervenir.
**Cómo abordarlo:** fija condiciones, ejecuta tres corridas comparables y cambia una sola variable o ninguna.
**Entregarás:** benchmark reproducible e informe de decisión de una página.
**Investiga fuera solo si:** una señal medida exige una herramienta o almacenamiento especializado.

## Modelo mínimo

1. **Pregunta y baseline:** define operación, workload, resultado y umbral antes de medir. Fija entorno, versión, dataset, concurrencia, warm-up y duración; conserva throughput, error rate y la distribución de latencia.
2. **Percentiles y variabilidad:** p50, p95 y p99 son percentiles de las observaciones registradas, no de usuarios. Registra el tamaño de la muestra y al menos tres corridas comparables. Un promedio o una sola corrida no bastan para concluir.
3. **Localización por evidencia:** separa CPU, memoria, I/O, base de datos y red. Aplica USE —utilización, saturación y errores— a recursos; usa el profiler del runtime para CPU y logs o traces si existen. Reutiliza `EXPLAIN` y los tiempos de red sin volver a enseñar esos mecanismos.
4. **Cambio mínimo y experimento:** cambia una variable y repite bajo las mismas condiciones; conserva script y raw output. Distingue una diferencia útil para el umbral del ruido entre corridas.
5. **Caché después de medir:** considérala solo si la evidencia demuestra reutilización y puedes definir key y scope, freshness/TTL, invalidación, stampede, comportamiento ante fallos y tratamiento de datos sensibles. Redis no es requisito.
6. **Almacenamiento por operación:** compara patrón de lectura y escritura, modelo, consistencia y durabilidad, volumen, latencia y throughput, costo operativo y reversibilidad de la migración. PostgreSQL es el default por menor complejidad hasta que una necesidad medida justifique otra opción.

## Ejercicio único — benchmark y decisión

**Timebox:** hasta 8 horas de primera pasada. Si no alcanzas el resultado, aplica la [regla antiatasco](../METODOLOGIA.md#regla-antiatasco): reduce al caso mínimo, conserva evidencia parcial y continúa; el tiempo no sustituye la evidencia.

**Contexto proporcionado:** usa [`reliable-worker`](../PROYECTOS.md#proyecto-b--reliable-worker), [`safe-change-api`](../PROYECTOS.md#proyecto-a--safe-change-api) o un caso sanitizado sobre un entorno que puedas repetir.

**Decisiones que debes tomar:** operación, workload, umbral, dataset, hipótesis, señal de diagnóstico, un único cambio —o ninguno— y decisión de almacenamiento.

1. Define la operación, el workload y el umbral antes de medir.
2. Siembra un dataset representativo y crea un único script de k6. Ejecuta warm-up y al menos tres corridas; guarda p50, p95, p99, throughput, errores, tamaño de muestra y entorno.
3. Formula dos hipótesis y localiza el cuello con una señal independiente del load test: profile, USE, trace/log o `EXPLAIN` ya aprendido.
4. Aplica **un** cambio mínimo de código, query/índice o configuración, o ninguno si no hay señal suficiente, y repite bajo las mismas condiciones.
5. Escribe una decisión de una página: optimizar, cachear, cambiar almacenamiento o no cambiar. Compara PostgreSQL, caché y como máximo una alternativa especializada en garantías, costo operativo, migración y señal que cambiaría la decisión. Declara un límite de la medición y no instales la alternativa solo para cerrar la unidad.

## Entregable y evidencia

- **Artefacto:** dataset, script, descripción del entorno, raw outputs e informe de decisión de una página.
- **Evidencia:** tres corridas comparables con percentiles, throughput, errores y tamaño de muestra; señal independiente y before/after si hubo cambio.
- **Caso negativo:** una hipótesis descartada por la señal o ausencia de evidencia suficiente para justificar un cambio.
- **Límite:** incertidumbre de la medición y evidencia que cambiaría la decisión.

## Done cuando

- [ ] Script, dataset y entorno permiten repetir la medición.
- [ ] Los raw outputs conservan al menos tres corridas comparables.
- [ ] Se reportan p50, p95, p99, throughput, errores, tamaño de muestra y variabilidad.
- [ ] El cuello está respaldado por una señal distinta del load test.
- [ ] El before/after modifica una sola variable, si hubo cambio.
- [ ] Si no hubo cambio, se documenta por qué ninguna intervención es justificable.
- [ ] La decisión compara garantías y costo de las opciones pertinentes; conservar PostgreSQL puede ser correcto.
- [ ] Se declara un límite de la medición y qué evidencia cambiaría la decisión.
- [ ] Puede explicar problema, decisión, evidencia e incertidumbre.
