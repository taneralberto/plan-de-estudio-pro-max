# 2.3 — Performance y Elección de Datos

> **Estado:** `ACTIVO` · unidad 12 del [ROADMAP](../ROADMAP.md).
>
> **Prerrequisitos:** unidad 9, un backend reproducible y un dataset y script de carga; reutiliza el probe de unidad 11 si existe.

**Propósito:** medir un baseline comparable, localizar el cuello y elegir el cambio mínimo —incluido no cambiar— sin introducir caché o almacenamiento por intuición.

## Modelo mínimo

1. **Pregunta y baseline:** define operación, workload, resultado y umbral antes de medir. Fija entorno, versión, dataset, concurrencia, warm-up y duración; conserva throughput, error rate y la distribución de latencia.
2. **Percentiles y variabilidad:** p50, p95 y p99 son percentiles de las observaciones registradas, no de usuarios. Registra el tamaño de la muestra y al menos tres corridas comparables, o explica por qué no fue posible. Un promedio o una sola corrida no bastan para concluir.
3. **Localización por evidencia:** separa CPU, memoria, I/O, base de datos y red. Aplica USE —utilización, saturación y errores— a recursos; usa el profiler del runtime para CPU y logs o traces si existen. Reutiliza `EXPLAIN` de la unidad 9 y los tiempos de red de la unidad 11 sin volver a enseñar esos mecanismos.
4. **Cambio mínimo y experimento:** cambia una variable y repite bajo las mismas condiciones; conserva script y raw output. Distingue una diferencia útil para el umbral del ruido entre corridas.
5. **Caché después de medir:** considérala solo si la evidencia demuestra reutilización y puedes definir key y scope, freshness/TTL, invalidación, stampede, comportamiento ante fallos y tratamiento de datos sensibles. Redis no es requisito.
6. **Almacenamiento por operación:** compara patrón de lectura y escritura, modelo, consistencia y durabilidad, volumen, latencia y throughput, costo operativo y reversibilidad de la migración. PostgreSQL es el default por menor complejidad hasta que una necesidad medida justifique otra opción.
7. **JIT:** Core Web Vitals y Lighthouse pertenecen a la ruta Web; MongoDB, Elasticsearch, Redis avanzado, wide-column, graph y time-series se abren ante un caso medido; CAP detallado pertenece a la unidad 14; N+1 e índices, a la unidad 9; soak, stress y capacity extensos, a las unidades 15/17 cuando hagan falta.

## Ejercicio único — benchmark y decisión

Usa [`reliable-worker`](../PROYECTOS.md#proyecto-b--reliable-worker), [`safe-change-api`](../PROYECTOS.md#proyecto-a--safe-change-api) o un caso sanitizado.

1. Define la operación, el workload y el umbral antes de medir.
2. Siembra un dataset representativo y crea un único script de k6. Ejecuta warm-up y al menos tres corridas; guarda p50, p95, p99, throughput, errores, tamaño de muestra y entorno.
3. Formula dos hipótesis y localiza el cuello con una señal independiente del load test: profile, USE, trace/log o `EXPLAIN` ya aprendido.
4. Aplica **un** cambio mínimo de código, query/índice o configuración, o ninguno si no hay señal suficiente, y repite bajo las mismas condiciones.
5. Escribe una decisión de una página: optimizar, cachear, cambiar almacenamiento o no cambiar. Compara PostgreSQL, caché y como máximo una alternativa especializada en garantías, costo operativo, migración y señal que cambiaría la decisión. No instales la alternativa solo para cerrar la unidad.

## Done cuando

- [ ] Script, dataset, entorno y raw outputs permiten repetir baseline y variante.
- [ ] Se reportan p50/p95/p99, throughput, errores, tamaño de muestra y variabilidad; no solo un promedio.
- [ ] El cuello está respaldado por una señal distinta del load test y no por intuición.
- [ ] El antes/después cambia una variable o documenta por qué no hay un cambio justificable.
- [ ] La decisión de optimizar, cachear, cambiar o no cambiar compara garantías y costo; conservar PostgreSQL puede ser el resultado correcto.
- [ ] Se declara un límite de la medición y qué evidencia cambiaría la decisión.
- [ ] Puede explicar problema, decisión, evidencia e incertidumbre.
