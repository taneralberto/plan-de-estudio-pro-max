- [ ] **Normalización y Desnormalización**

1NF (sin grupos repetidos, cada celda tiene un valor atómico), 2NF (sin dependencias parciales — cada columna depende de toda la PK, no solo parte), 3NF (sin dependencias transitivas — ninguna columna no-clave depende de otra columna no-clave), BCNF (la forma estricta de 3NF). Cuándo normalizar hasta 3NF (consistencia de datos, sin redundancia, escrituras confiables). Cuándo desnormalizar a propósito (reportes pesados, analytics, lecturas frecuentes que necesitan JOINs costosos). La tensión entre las dos no se resuelve con una regla fija — se resuelve entendiendo el patrón de acceso de la app.

**Por qué importa:** El esquema de cualquier proyecto evoluciona con el tiempo. Si el modelo está bien normalizado, agregar una nueva relación (ej: un artículo puede tener múltiples autores) es un ALTER TABLE limpio. Si está desnormalizado por conveniencia, esa misma evolución implica migrar datos y coordinar múltiples tablas. Pero un esquema sobre-normalizado puede generar queries con 6 JOINs para mostrar un listado simple. Conocer las formas normales no es saber teoría — es saber cuándo romperlas con criterio y cuándo no.

**<span style="color: #29B6F6">Ejercicio:</span>** Toma el esquema de un proyecto real y analiza cada tabla: ¿está en 3NF? ¿Hay columnas que dependen de algo que no es la PK? Identifica al menos un caso de desnormalización que tendría sentido para performance (ej: una columna `view_count` desnormalizada en la tabla principal para evitar un COUNT costoso en cada listado) y uno que sería un error (ej: guardar `author_name` en la tabla de artículos además del `author_id`). Justifica cada decisión.

**<span style="color: #FFA726">FreePress:</span>** Analiza el esquema de FreePress y verifica qué tablas están en 3NF y cuáles podrían beneficiarse de una desnormalización controlada.

Puedes también tomar un modelo 3NF y proponer una desnormalización específica para un patrón de lectura particular, articulando qué consistencia sacrificás y cómo la compensás (ej: trigger, job periódico, actualización en la escritura).

- [ ] **Transactions y ACID**

Atomicity (la transacción completa o no pasa nada — no hay estados intermedios), Consistency (la transacción lleva la base de un estado válido a otro estado válido — los constraints se verifican al final), Isolation (las transacciones concurrentes no se interfieren entre sí — con grados configurables), Durability (una vez committed, los datos sobreviven a crashes). Isolation levels: Read Uncommitted (lee datos sin commitear — dirty reads), Read Committed (solo lee datos commiteados — el default de PostgreSQL), Repeatable Read (garantiza que los mismos datos leídos dos veces en la misma transacción son iguales), Serializable (como si las transacciones corrieran en serie, una por una — el más seguro, el más caro). Fenómenos: dirty read, non-repeatable read, phantom read — cuál nivel previene cuál.

**Por qué importa:** Cualquier sistema con escrituras concurrentes necesita transacciones. Publicar un artículo actualiza el estado en la tabla principal, crea un registro en la tabla de versiones, e incrementa un contador — las tres cosas deben pasar o ninguna. Sin una transacción, si el proceso muere después del primer UPDATE, el estado queda inconsistente. Y el isolation level incorrecto en un sistema con escrituras concurrentes genera race conditions que son difíciles de reproducir y depurar en producción.

**<span style="color: #29B6F6">Ejercicio:</span>** Crea en PostgreSQL un escenario real de race condition: dos usuarios simultáneos intentan aplicar un descuento al mismo artículo (ej: precio actual → precio con descuento, pero solo si no fue descontado ya). Ejecuta las transacciones con `Read Committed` y demuestra que se produce el bug. Luego arreglalo con `SELECT FOR UPDATE` y con `Serializable`, y compara el comportamiento y el costo de cada solución.

**<span style="color: #FFA726">FreePress:</span>** Implementa el escenario de race condition con los endpoints de FreePress: dos usuarios intentando publicar el mismo artículo simultáneamente o aplicar un descuento al mismo recurso.

Puedes explicar por qué PostgreSQL usa Read Committed como default (balance entre concurrencia y seguridad para la mayoría de los casos) y en qué situaciones específicas necesitarías subir a Repeatable Read o Serializable.

- [ ] **SQL avanzado**

Window functions: `ROW_NUMBER()` (número de fila dentro de una partición), `RANK()` y `DENSE_RANK()` (ranking con y sin gaps), `LAG()` y `LEAD()` (acceder a la fila anterior o siguiente dentro de la partición), `SUM() OVER()` (agregados.cumulativos). CTEs (Common Table Expressions): queries nombradas reutilizables dentro de una query más grande — hacen legible lo que de otra forma sería un subquery anidado ilegible. Recursive CTEs para estructuras jerárquicas (ej: categorías con subcategorías). EXPLAIN y EXPLAIN ANALYZE: leer el query plan, entender Seq Scan vs Index Scan vs Bitmap Heap Scan, identificar el nodo más costoso. Materialized views: pre-calcular y almacenar el resultado de una query costosa para leerlo rápido.

**Por qué importa:** El 80% de los problemas de performance de base de datos en producción son queries SQL mal escritas o queries que no usan índices. Un developer que solo conoce `SELECT`, `JOIN` y `WHERE` va a escribir queries que funcionan en desarrollo con 100 registros y explotan en producción con 1 millón. Window functions pueden reemplazar algunos subqueries correlacionados y mejorar el plan, pero no siempre son equivalentes ni más rápidas; hay que medir con `EXPLAIN ANALYZE`. EXPLAIN ANALYZE te muestra exactamente dónde la base de datos gasta tiempo. Materialized views te permiten responder preguntas analíticas en milisegundos que de otra forma tomarían segundos.

**<span style="color: #29B6F6">Ejercicio:</span>** Escribe tres queries usando SQL avanzado: (1) Con window function — rankear los artículos más leídos por semana, usando `ROW_NUMBER() OVER (PARTITION BY week ORDER BY views DESC)`. (2) Con CTE recursivo — obtener el árbol completo de categorías (categoría → subcategoría → subsubcategoría) en una sola query. (3) Con EXPLAIN ANALYZE — encuentra la query más lenta de tu proyecto (la que hace Seq Scan en tablas grandes), agrega el índice faltante, y muestra la mejora en el query plan antes y después.
