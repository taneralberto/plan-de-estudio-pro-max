# 2.4 — SQL y Modelado Relacional

> **Estado:** `DIAGNÓSTICO ★` · unidad 9 del ROADMAP.
>
> **Prerrequisitos:** SQL CRUD y joins básicos; PostgreSQL local con dos sesiones concurrentes.
>
> **Cierre:** aplica el [diagnóstico antes de estudiar](../METODOLOGIA.md#diagnóstico-antes-de-estudiar) y el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Hacer que las invariantes sobrevivan entradas inválidas, concurrencia y crecimiento mediante un modelo, constraints, una transacción y un índice justificables.

## Orientación

**Qué debes lograr:** demostrar que el esquema rechaza un estado inválido, que dos sesiones reproducen una carrera y que un único mecanismo preserva la invariante; justificar después un índice con planes comparables.

**Cómo abordarlo:** intenta el diagnóstico antes de leer el modelo completo: escribe la invariante, el DDL mínimo y la secuencia concurrente que crees que la rompe. Consulta aislamiento, locks o índices solo para el hueco que revele esa ejecución.

**Investiga fuera solo si:** necesitas confirmar semántica de PostgreSQL para un nivel de aislamiento, constraint, lock o plan → la sección correspondiente de su documentación; te bloquea sintaxis de joins, aggregates o ventanas → PGExercises, desde la [unidad 9 de RECURSOS](../RECURSOS.md#9--sql-y-modelado-relacional).

## Ejemplo mínimo — dos reservas sobre una unidad

> Este ejemplo explica el razonamiento; no es otro ejercicio ni otro Done.

```text
Inicial: available(A)=1; T1 y T2 piden quantity=1.
T1 lee 1; T2 lee 1. Ambas deciden que pueden reservar.
T1 escribe 0, inserta R1 y confirma.
T2 escribe 0, inserta R2 y confirma: dos reservas consumieron una unidad (fallo).
Correcto: UPDATE ... SET available = available - $quantity
          WHERE sku = 'A' AND available >= $quantity RETURNING available.
Solo la transacción que recibe una fila inserta la reserva; la otra rechaza.
```

## Modelo mínimo

### Modelo desde invariantes y accesos

Mantén una fuente por hecho y elige una PK estable. Usa FK para referencias y `NOT NULL`, `UNIQUE` y `CHECK` para impedir estados locales inválidos. Normaliza para evitar anomalías de actualización; desnormaliza únicamente ante una lectura medida y con un mecanismo explícito de consistencia. El objetivo no es recitar 1NF→BCNF, sino traducir invariantes y patrones de acceso a un esquema defendible.

### Transacción, aislamiento y carrera

Agrupa cambios relacionados en una transacción para que sean atómicos. En PostgreSQL, `READ COMMITTED` es el nivel por defecto y `READ UNCOMMITTED` se comporta como `READ COMMITTED`; PostgreSQL no permite dirty reads bajo ese nombre. Su `REPEATABLE READ` también evita anomalías más allá del mínimo exigido por el estándar SQL.

Una invariante concurrente puede requerir un lock explícito, un update condicional atómico o `SERIALIZABLE`, según el conflicto. `SERIALIZABLE` puede abortar una transacción con un fallo de serialización: la operación debe tener una política de retry acotada y segura, no limitarse a cambiar el isolation level.

### Índice desde una query

Diseña el índice desde el predicado y el orden del workload, considerando selectividad y orden de columnas. Todo índice ocupa espacio y añade costo a escrituras y mantenimiento.

`EXPLAIN (ANALYZE, BUFFERS)` ejecuta la consulta; úsalo únicamente en un laboratorio o entorno donde sus efectos y carga sean seguros. Compara estimaciones, filas reales, costos, tiempos y buffers con datos representativos. Un `Seq Scan` puede ser el plan correcto para una tabla pequeña o un predicado poco selectivo; el objetivo no es forzar un `Index Scan`.

### JIT y destinos

Window functions, CTE recursivos, materialized views, BCNF formal, particionado e índices especializados quedan JIT. [PGExercises](https://pgexercises.com/) se abre solo si el diagnóstico muestra un hueco de sintaxis en joins, aggregates o windows.

La migración de constraints e índices pertenece a la [unidad 10](2.6%20—%20Data%20Migrations%20y%20Schema%20Evolution.md); el benchmark del servicio, a la unidad 12. La carrera se reutiliza conceptualmente desde la unidad 2, sin repetir su trabajo.

## Ejercicio único — modelo, carrera y plan antes/después

Usa el flujo de reservas de [`safe-change-api`](../PROYECTOS.md#proyecto-a--safe-change-api) o un equivalente sanitizado.

1. Crea el DDL mínimo para `stock` y `reservations`. Justifica PK, FK, `UNIQUE`, `NOT NULL` y `CHECK`, y demuestra con SQL que la base rechaza un insert inválido.
2. Implementa una reserva con dos cambios atómicos: reducir disponibilidad y crear la reserva.
3. Con dos sesiones o scripts, reproduce en `READ COMMITTED` una implementación read→decide→write que permita una actualización perdida o viole la invariante.
4. Corrige con **un** mecanismo: `SELECT … FOR UPDATE`, `UPDATE … WHERE available >= $quantity RETURNING`, o `SERIALIZABLE` con retry. Justifica por qué basta; no implementes los tres.
5. Siembra un volumen reproducible y elige una query real, por ejemplo reservas por `sku` y fecha. Guarda `EXPLAIN (ANALYZE, BUFFERS)` antes y después de un índice, usando el mismo dataset y entorno. Compara filas estimadas/reales, costo, tiempo, buffers y costo de escritura; acepta `Seq Scan` si la evidencia lo favorece.
6. Entrega `schema.sql`, el script concurrente, ambos planes y una nota breve de decisión y riesgo.

## Done cuando

- [ ] El DDL expresa identidad, relaciones y estados inválidos, y un caso negativo demuestra que la base rechaza un dato.
- [ ] Dos ejecuciones concurrentes reproducen el fallo inicial de forma observable.
- [ ] La corrección preserva la invariante y documenta aislamiento, lock o atomicidad, además de la política de retry si aplica.
- [ ] Los planes antes/después usan el mismo dataset, query y entorno, sin presuponer que `Index Scan` gana.
- [ ] Se justificó el costo del índice en lectura, escritura y espacio.
- [ ] El artefacto registra un supuesto o límite y permite explicar problema, decisión y evidencia.
- [ ] Se completaron el caso negativo y la recuperación del cierre crítico.
