# 2.5 — Bases de Datos No-Relacionales

---

- [ ] **Cuándo NO usar SQL**

Las familias de bases de datos no-relacionales y el problema específico que cada una resuelve: Document stores (MongoDB, CouchDB — datos semiestructurados o con schema variable, como perfiles de usuario con campos opcionales), Key-Value (Redis, DynamoDB — acceso por clave con latencia sub-milisegundo, caching, sessions), Wide-column (Cassandra, ScyllaDB — escrituras masivas distribuidas, series temporales, alta disponibilidad geográfica), Graph (Neo4j, Amazon Neptune — relaciones complejas y traversals, redes sociales, detección de fraude), Time-series (InfluxDB, TimescaleDB — métricas y eventos con componente temporal), Search (Elasticsearch, Typesense — búsqueda full-text, faceting, relevance ranking).

**Regla fundamental:** Usa PostgreSQL por default. Solo usa otra cosa cuando PostgreSQL NO pueda resolver tu problema eficientemente — y "no pueda" significa benchmarks reales, no intuición o "escalará mejor".

**Por qué importa:** La decisión de qué base de datos usar es una de las más difíciles de revertir en un sistema en producción. Migrar de PostgreSQL a MongoDB una vez que tienes datos en producción es meses de trabajo. La mayoría de los proyectos que usan MongoDB "porque es más flexible" terminan reimplementando manualmente las garantías que PostgreSQL da gratis (transacciones, foreign keys, joins). Conocer cuándo cada familia tiene sentido real te evita acumular deuda técnica por decisiones de base de datos tomadas sin criterio.

**<span style="color: #29B6F6">Ejercicio:</span>** Para un proyecto con el que estés familiarizado, identifica qué datos podrían tener sentido en una base de datos no-relacional y cuáles definitivamente no. Específicamente: (1) ¿Los metadatos flexibles de un contenido (campos custom que cada usuario puede definir) justifican un document store o PostgreSQL JSONB resuelve el problema igual de bien? (2) ¿El sistema de búsqueda full-text justifica Elasticsearch o PostgreSQL FTS (`tsvector`) es suficiente para el volumen esperado? Para cada caso, documenta el criterio de decisión con datos concretos (volumen estimado, tipo de queries, latencia requerida).

**<span style="color: #FFA726">FreePress:</span>** Analiza el caso de FreePress: ¿Los metadatos flexibles de artículos justifican un document store? ¿La búsqueda de artículos justifica Elasticsearch? Documenta con datos concretos.

**Done cuando:** Puedes recibir un requerimiento de un sistema nuevo (ej: "necesitamos guardar las métricas de visualización por artículo en tiempo real") y determinar si PostgreSQL alcanza o si necesitas una base de datos especializada — con argumentos técnicos basados en el volumen, el patrón de acceso y los requisitos de latencia, no en preferencias personales.

- [ ] **CAP Theorem, Consistencia y Trade-offs Distribuidos**

El CAP Theorem: un sistema distribuido puede garantizar solo dos de tres propiedades durante una partición de red — Consistency (todos los nodos ven el mismo dato al mismo tiempo), Availability (cada request recibe una respuesta, no un error), Partition Tolerance (el sistema sigue funcionando aunque la red se parta). Pero la formulación práctica es: cuando hay una partición (que va a pasar), eliges entre consistencia y disponibilidad. PACELC: la extensión de CAP que incluye el trade-off cuando NO hay partición — latencia vs consistencia incluso en operación normal. Consistencia fuerte (linearizable): lees lo último que se escribió, siempre — PostgreSQL lo da por default con transacciones ACID. Consistencia eventual: si nadie escribe nuevo, todas las réplicas convergen al mismo estado — pero NO garantizaron que leas lo último. Ejemplos: Cassandra (tunable consistency por query), DynamoDB (configurable por tabla — strong o eventual), MongoDB (read concerns `majority` vs `local`). La decisión de consistencia no es teórica: si tu dashboard de analytics muestra "10 vistas" cuando el contador ya está en 15, ¿eso es aceptable? Si es un balance de cuenta bancaria, no lo es — y consistencia eventual es peligrosa.

**Por qué importa:** Si usas una base de datos NoSQL sin entender su modelo de consistencia, estás decidiendo entre consistencia y disponibilidad SIN saberlo. Un sistema que usa Cassandra con consistencia eventual para datos financieros, o MongoDB con read concern `local` para un carrito de compras que calcula el total, tiene bugs silenciosos que solo aparecen bajo carga — cuando las réplicas se desincronizan.

**<span style="color: #29B6F6">Ejercicio:</span>** Para cada base de datos que conocés (PostgreSQL, Redis, MongoDB, DynamoDB), clasifica su comportamiento en términos de CAP: ¿qué garantiza cuando hay partición de red? ¿Qué modelo de consistencia ofrece por default? ¿Se puede configurar? Para un caso concreto (ej: contador de vistas de artículos), documenta qué pasaría si: (1) dos nodos reciben escrituras simultáneas durante una partición, (2) la partición se resuelve, (3) el sistema aplica resolución de conflictos. ¿Qué datos se pierden y cuáles se preservan?

- [ ] **Document Stores — MongoDB como Contraste con SQL**

Schema design en document stores: documentos embebidos (todo en un solo documento — `user` con su `address` adentro) vs referencias (documento separado que se vincula por ID — `user` referencia a `address`). Cuándo embeber (datos que se leen juntos, 1:a-1, el embebido no crece sin límite) y cuándo referenciar (datos que se mutan independientemente, relaciones N:N, documentos que crecen sin acotar). MongoDB específicamente: indexing (compound indexes, text indexes, TTL indexes), aggregation pipeline (`$match`, `$group`, `$lookup` — el equivalente de `JOIN` pero más limitado), change streams para eventos. PostgreSQL JSONB como alternativa: si el 90% de los datos son relacionales y el 10% es semiestructurado, JSONB dentro de PostgreSQL te da ACID, joins, foreign keys Y flexibilidad de schema — sin agregar otra base de datos. Cuándo MongoDB tiene sentido real: datos genuinamente schemaless donde la estructura cambia por tipo de entidad (ej: catálogo de productos donde cada categoría tiene campos distintos), escribir mucho y leer por ID con queries simples, prototipado rápido donde el schema evoluciona constantemente. La trampa más común: usar MongoDB "porque JSON" y terminar reimplementando manualmente joins, transacciones y foreign keys que PostgreSQL da gratis.

**Por qué importa:** La mayoría de los proyectos que eligen MongoDB podrían usar PostgreSQL JSONB y tener una base de datos menos, un modelo de consistencia más fuerte, y joins nativos. MongoDB es la herramienta correcta cuando los datos son genuinamente schemaless — no cuando "es más fácil empezar sin schema" porque ese schema se va a cristalizar en producción y vas a necesitar migraciones igual.

**<span style="color: #29B6F6">Ejercicio:</span>** Diseña el schema de una colección de productos en MongoDB donde cada categoría tiene campos distintos (un libro tiene ISBN y autor, una zapatella tiene talle y color, un teléfono tiene RAM y almacenamiento). Implementa: (1) un aggregation pipeline que cuente productos por categoría con `$group`, (2) un `$lookup` para traer datos del usuario que creó cada producto. Después implementa el mismo caso en PostgreSQL con una tabla base `products` + una columna JSONB para los campos variables, y compara: ¿cuántas queries necesitas en cada caso? ¿Cuál te da transacciones ACID?

**<span style="color: #FFA726">FreePress:</span>** Los artículos de FreePress con metadata variable son el ejemplo perfecto: ¿usarías una colección MongoDB con campos variables, o PostgreSQL con JSONB para la metadata? Implementa ambas versiones y compara.

**Done cuando:** Puedes argumentar con criterio técnico cuándo MongoDB resuelve un problema que PostgreSQL JSONB no puede resolver eficientemente (y viceversa). Puedes diseñar un schema en MongoDB decidiendo embebido vs referencia para cada relación, y puedes traducir un aggregation pipeline de MongoDB a SQL equivalente (y viceversa).

**Recursos:**
- [PostgreSQL Docs — JSON Types](https://www.postgresql.org/docs/current/datatype-json.html) — JSONB: cómo indexar campos JSON, operadores `@>`, `?`, `->>`, y cuándo es suficiente vs MongoDB. Leerlo ANTES de decidir que necesitas MongoDB.
- [MongoDB Docs — Aggregation Pipeline](https://www.mongodb.com/docs/manual/core/aggregation-pipeline/) — referencia completa de `$match`, `$group`, `$lookup`, `$unwind`. El equivalente de SQL `JOIN` y `GROUP BY` en MongoDB.

- [ ] **Redis — Más que un cache**

Redis es una base de datos en memoria con persistencia opcional — no es solo un cache. Estructuras de datos que ofrece: Strings (cache simple, contadores), Lists (colas FIFO/LIFO), Sets (colecciones sin duplicados, intersecciones), Sorted Sets (leaderboards, cola con prioridad), Hashes (objetos), Streams (event log append-only, similar a Kafka en escala pequeña). Casos de uso más allá del cache: Pub/Sub para mensajería ligera entre servicios, rate limiting con sliding window usando Sorted Sets, session storage, distributed locks con `SET NX PX`, job queues con BullMQ (construido sobre Redis).

**Por qué importa:** Si tu proyecto usa Redis, probablemente solo lo use como cache de queries. Eso es dejar el 90% del valor de Redis sobre la mesa. Rate limiting de API, sistema de notificaciones en tiempo real, cola de jobs para procesamiento asíncrono, y sesiones de usuarios autenticados son todos casos de uso que Redis resuelve de forma nativa, sin agregar otra dependencia de infraestructura.

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa dos features usando Redis más allá del cache: (1) Rate limiting con sliding window — la API pública no puede recibir más de 100 requests por IP por minuto. Usa un Sorted Set de Redis donde el score es el timestamp del request. (2) Job queue con BullMQ — cuando se crear un recurso costoso (ej: generar thumbnail de una imagen), encolar un job. El job debe reintentarse automaticamente si falla, con backoff exponencial.

**<span style="color: #FFA726">FreePress:</span>** Implementa rate limiting para la API pública de FreePress con Redis Sorted Sets, y una job queue con BullMQ para el procesamiento de thumbnails de artículos.

**Done cuando:** Puedes mirar un requerimiento nuevo (notificaciones push, búsqueda de usuarios online, cooldown entre publicaciones) y determinar qué estructura de datos de Redis resuelve el problema y cómo. Puedes explicar cuándo Redis Streams es una alternativa válida a RabbitMQ/Kafka para mensajería y cuándo no escala lo suficiente.

**Recursos:**

- [BullMQ Docs](https://docs.bullmq.io/) — la librería de job queues más completa para Node.js construida sobre Redis. Tiene ejemplos de retry, backoff, y concurrencia.
- [*"Redis in Action"*](https://www.amazon.com/Redis-Action-Josiah-L-Carlson/dp/1617290858) de Josiah Carlson — el libro de referencia. Cada capítulo es un caso de uso real construido con Redis (analytics, social features, ad targeting). Muy práctico.
