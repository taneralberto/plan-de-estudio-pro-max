# 2.6 — Migraciones Seguras y Evolución de Schema

> **Estado:** `ACTIVO` · unidad 10 del [ROADMAP](../ROADMAP.md).
> **Prerrequisito:** schema, constraints e invariante de la [unidad 9](2.4%20—%20SQL%20y%20Modelado%20Relacional.md), sin repetir su ejercicio, y una herramienta de migración ya usada por el proyecto.

## Propósito

Cambiar código, schema y datos manteniendo compatibilidad entre versiones y una vía de recuperación comprobada. Esta unidad es el dueño canónico del backup/restore verificable; Observabilidad enlaza esta evidencia en vez de repetirla.

## Orientación

**Qué debes lograr:** ejecutar un cambio expand-contract compatible y demostrar una sola vía de recuperación.

**Cómo abordarlo:** reutiliza el schema y la invariante de la unidad 9; separa expansión, backfill, validación y contract para comprobar cada transición.

**Entregarás:** migraciones o deploys separados, backfill reanudable y un informe con compatibilidad, restore, análisis de DDL/locks y rollback o roll-forward.

**Investiga fuera solo si:** el DDL concreto exige confirmar locks o reescrituras en tu versión de PostgreSQL, o tu herramienta oculta SQL necesario para decidir.

## Modelo mínimo

### Expand → migrate → contract

1. **Expand:** añade un schema compatible con las versiones vieja y nueva del código.
2. **Migrate:** despliega código que tolera ambos estados y ejecuta un backfill idempotente, observable y acotado.
3. **Contract:** valida primero; retira la estructura o compatibilidad anterior cuando ya no quedan lectores ni escritores viejos.

Cada fase debe poder desplegarse y verificarse por separado. Un laboratorio local demuestra compatibilidad y recuperación, no garantiza zero downtime en producción.

### Locks y versión

La duración, reescritura, compatibilidad con un transaction block y los locks adquiridos o esperados dependen del DDL y de la versión de PostgreSQL desplegada. Un DDL llamado “concurrente” también toma o espera locks; su interferencia y comportamiento dependen de la operación, el tráfico y la versión.

`CREATE INDEX CONCURRENTLY` permite que continúen las escrituras, pero realiza varias fases, espera transacciones o conflictos, no puede ejecutarse dentro de un transaction block y puede dejar un índice inválido si falla. Verifica `pg_index.indisvalid` y define cómo reintentar o limpiar.

Para `CHECK` y FK compatibles, `NOT VALID` reduce la comprobación inicial de filas existentes, pero `ALTER TABLE` todavía adquiere locks; `VALIDATE CONSTRAINT` es otra fase. Su aplicabilidad y nivel de lock se verifican contra la versión real, en vez de extrapolarlo a cualquier constraint.

### Datos

Ejecuta backfills por lotes, con condición de reanudación, progreso observable y verificación final. Hazlos idempotentes para que una interrupción no duplique ni corrompa datos. Los seeds de producción deben ser mínimos e idempotentes y existir solo cuando el caso los requiera.

### Recuperación

Si el schema expandido sigue siendo compatible, suele ser menos destructivo revertir primero el código y conservar ese schema. Para datos ya transformados puede convenir una migración correctiva roll-forward. Un `DOWN` destructivo no recupera la información perdida.

Un backup cuenta como vía de recuperación únicamente después de restaurarlo en un destino temporal y verificar datos mediante conteos, checksums o invariantes. La estrategia debe incluir criterio de parada y comprobar compatibilidad entre código, schema y datos.

### Herramienta

Usa la herramienta ya instalada y revisa el SQL generado. TypeORM, Prisma y Flyway son referencias JIT ante un cambio real de stack, no una comparación requerida.

## Ejercicio único — añadir `expires_at` de forma compatible

**Timebox:** aplica la [regla antiatasco canónica](../METODOLOGIA.md#regla-antiatasco); el tiempo es una alarma y no sustituye la evidencia.

**Contexto proporcionado:** [`safe-change-api`](../PROYECTOS.md#proyecto-a--safe-change-api) o un equivalente sanitizado, su schema e invariante de la unidad 9, y la herramienta de migración ya instalada.

**Decisiones que debes tomar:** si un contrato previo no fija la semántica de `expires_at`, defínela y justifícala para poder construir el oracle; decide tamaño y checkpoint de lotes, gate de contract, si una query justifica índice y cuál de las dos vías de recuperación demostrar.

1. Guarda un baseline y crea un `pg_dump` acotado. Restáuralo en una base o schema temporal y verifica un conteo, checksum o invariante.
2. Para cada DDL, consulta la documentación de la versión desplegada y registra duración esperada, reescritura, transaction block, locks adquiridos o esperados y riesgo operativo.
3. **Expand:** añade `expires_at` nullable y demuestra que la versión anterior todavía arranca, lee y escribe.
4. Despliega o simula una versión nueva que escribe `expires_at` según la semántica documentada y tolera `NULL` durante la transición.
5. **Migrate:** ejecuta un backfill idempotente por lotes con `WHERE expires_at IS NULL`; interrúmpelo tras un lote, reanúdalo y verifica cero pendientes y la semántica definida o recibida del contrato.
6. Añade y valida la invariante por fases. Si una query del flujo de expiración lo justifica, crea el índice concurrente fuera de la transacción automática y verifica `indisvalid`; no agregues un índice sin query.
7. **Contract:** si puedes demostrar ausencia de versiones viejas y datos nulos, endurece `NOT NULL` o retira el fallback. Si no hay rolling deploy real, documenta esa gate sin afirmar que se ejecutó.
8. Inyecta un defecto controlado y demuestra **una** vía: rollback de código conservando el schema expandido, o una migración correctiva roll-forward. Registra la condición para detener o continuar.

## Entregable y evidencia

- **Artefacto:** migraciones o deploys separados, backfill reanudable e informe de decisiones y recuperación.
- **Evidencia:** baseline, restore verificado, compatibilidad de la versión vieja, interrupción/reanudación y checks finales.
- **Caso negativo:** defecto controlado recuperado mediante un solo rollback o roll-forward.
- **Límite o riesgo:** locks dependientes de versión, gate de contract y criterio para detener o continuar.

## Done cuando

- [ ] Las fases están en migraciones o deploys separados.
- [ ] La versión vieja funciona con el schema expandido.
- [ ] La semántica de `expires_at` recibida o definida está documentada.
- [ ] El backfill se interrumpe y reanuda sin duplicar ni corromper datos.
- [ ] Conteos, checks o la invariante prueban completitud y semántica.
- [ ] La validación ocurre después de comprobar los datos.
- [ ] Contract ocurre solo después de comprobar datos y consumidores, o su gate condicional queda documentada.
- [ ] Si hay índice concurrente, se ejecuta fuera de transaction block.
- [ ] Si hay índice concurrente, se verifica su estado válido o fallo.
- [ ] Se ejecutó un rollback o un roll-forward.
- [ ] La recuperación dejó código, schema y datos compatibles.
- [ ] El backup se restauró en un destino temporal.
- [ ] El restore se verificó; crear el archivo no basta.
- [ ] El análisis de DDL registra locks y riesgos dependientes de versión.
- [ ] Está registrado el criterio para detener o continuar.
