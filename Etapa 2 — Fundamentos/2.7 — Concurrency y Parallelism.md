# 2.7 — Concurrency y Parallelism

> **Estado:** `ACTIVO` · Cierre de la unidad 2 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** modelo del event loop de [1.2](../Etapa%201%20—%20Entrada/1.2%20—%20JavaScript%20Internals.md); memoria y streams de [2.11](2.11%20—%20Sistemas%20Operativos%20(Profundizar).md) se consultan cuando el diagnóstico los señale.

## Propósito

Distinguir espera, bloqueo y saturación con evidencia, y sacar trabajo CPU-bound del event loop cuando esa sea la causa. Concurrencia permite que varias tareas progresen; paralelismo ejecuta trabajo simultáneo en más de una unidad de ejecución.

## Modelo mínimo

### I/O-bound frente a CPU-bound

Una operación I/O-bound pasa buena parte de su vida esperando red, disco u otro sistema. Una operación CPU-bound consume tiempo ejecutando cálculo. El nombre de una función o que devuelva Promise no decide la categoría.

Observa al menos:

- event-loop delay y latencia de un endpoint liviano;
- utilización y saturación de CPU;
- throughput y cola pendiente;
- perfiles o trazas que localicen el tiempo.

CPU alta no prueba por sí sola que el event loop esté bloqueado, y latencia alta también puede venir de una dependencia. Relaciona la señal con el código y repite bajo condiciones comparables.

### Thread, Worker y proceso

Un proceso tiene memoria y recursos aislados por el sistema operativo; sus threads comparten memoria del proceso. Node.js ejecuta cada isolate de JavaScript en un thread, aunque el runtime y librerías puedan usar otros threads.

Usa un Worker Thread para cálculo CPU-bound cuando el costo de serializar y coordinar sea aceptable. Reutilízalo y limita el trabajo pendiente: crear un Worker por request añade startup, memoria y presión bajo carga. Determina tamaño y política de cola midiendo el workload, el entorno y el overhead; el número de cores visible es una señal, no una configuración automática.

Usa un proceso separado cuando importen más el aislamiento de memoria, permisos, fallos o lifecycle. `spawn` permite tratar stdout/stderr como streams; `fork` añade un canal IPC entre procesos Node. Un Worker o proceso puede fallar, colgarse o terminar: maneja error/exit, cancela o rechaza el trabajo y cierra recursos.

### Carreras y consistencia

Puede haber carreras aunque el JavaScript de cada callback se ejecute de forma secuencial: dos requests pueden intercalar lectura, espera y escritura sobre el mismo estado. Evita estado mutable compartido o protege la invariante donde vive.

Entre Workers, usa `SharedArrayBuffer` y `Atomics` solo si compartir memoria aporta una ventaja medida; el paso de mensajes reduce superficie de sincronización. Para persistencia, la solución suele ser un constraint o transacción y pertenece a la [unidad 10](2.4%20—%20SQL%20y%20Modelado%20Relacional.md), no a un mutex en memoria.

`cluster`, IPC avanzado, deadlocks académicos y comparaciones con otros runtimes quedan JIT ante un sistema que los use.

## Ejercicio único — Bloquear y liberar el event loop

Usa un backend pequeño existente con `/health` o endpoint liviano equivalente y agrega una operación CPU-bound controlada. No añadas framework ni pool externo.

1. Registra versión de Node, hardware/entorno, comandos, carga y una predicción sobre qué señal cambiará.
2. Ejecuta la carga CPU junto con probes del endpoint liviano. Conserva latencia y event-loop delay, además de la señal de CPU disponible.
3. Confirma con perfil o instrumentación que el cálculo, y no una dependencia, explica el bloqueo observado.
4. Mueve solo el cálculo a un Worker Thread reutilizable, con trabajo pendiente acotado y manejo de error/exit.
5. Repite los mismos comandos, carga y mediciones en el mismo entorno.
6. Conserva evidencia before/after y explica causalidad, ruido, costo de coordinación y cualquier cambio de throughput.
7. Registra un riesgo residual y qué medición faltante podría cambiar la decisión entre event loop, Worker o proceso.

## Done cuando

- [ ] La reproducción registra versión, entorno y comandos ejecutables.
- [ ] Hay una predicción previa y un baseline de latencia liviana y event-loop delay.
- [ ] La evidencia relaciona cálculo CPU-bound → bloqueo del event loop → latencia de trabajo no relacionado.
- [ ] La comparación before/after usa la misma carga y conserva la salida relevante.
- [ ] El Worker es reutilizable, limita trabajo pendiente y propaga fallo o terminación sin dejar requests colgadas.
- [ ] Puedes explicar por qué `Promise.all` no saca ese cálculo del thread que ejecuta JavaScript.
- [ ] La elección entre I/O asíncrono, Worker y proceso cita aislamiento, overhead y medición.
- [ ] Quedan documentados ruido, riesgo residual y una señal no medida.
