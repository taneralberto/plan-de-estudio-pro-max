# 2.7 — Concurrency y Parallelism

---

- [ ] **Concurrencia vs Paralelismo — La distinción que importa**

Concurrencia: manejar múltiples tareas que progresan al mismo tiempo, no necesariamente ejecutándose simultáneamente — el event loop de Node.js es un ejemplo perfecto de concurrencia sin paralelismo real. Paralelismo: ejecutar múltiples tareas literalmente al mismo tiempo en distintos cores de CPU. Node.js ejecuta JavaScript en un solo hilo, pero usa el thread pool de libuv para operaciones de I/O — el event loop hace concurrencia, pero todo el JavaScript corre en un solo hilo. Para I/O-bound work (requests de red, lectura de archivos) la concurrencia del event loop es suficiente y muy eficiente. Para CPU-bound work (criptografía, procesamiento de imágenes, parsing de archivos grandes) el event loop se bloquea — necesitas paralelismo real.

**Por qué importa:** Si un endpoint hace una operación CPU-intensiva (ej: generar un PDF, redimensionar una imagen, calcular un hash criptográfico pesado) en el request handler, bloquea el event loop entero — ninguna otra request puede ser procesada mientras tanto. Con 100 requests concurrentes, una sola operación CPU-bound de 200ms convierte tu API de sub-10ms a potencialmente 20 segundos de latencia para todos. Entender cuándo el event loop es suficiente y cuándo necesitas Worker Threads es la diferencia entre un backend que escala y uno que se degrada bajo carga.

- [ ] **Worker Threads y child_process en Node.js**

Worker Threads (`worker_threads` module): hilos reales que comparten memoria con el hilo principal a través de `SharedArrayBuffer` y se comunican via `postMessage`. Útiles para CPU-bound work que necesita compartir datos eficientemente. `child_process`: módulo para lanzar procesos separados — `spawn` (streaming de stdout/stderr), `exec` (captura el output completo), `fork` (proceso hijo Node.js con canal IPC). Cluster module: lanzar múltiples instancias del proceso de Node.js (una por core) que comparten el mismo puerto — horizontal scaling en una sola máquina. La diferencia entre los tres: Worker Threads comparten memoria (rápido pero con riesgo de race conditions), child_process son completamente aislados (más seguro, más overhead), cluster es child_process especializado para servidores HTTP.

**Por qué importa:** Cualquier backend que procese archivos (resize de imágenes, generación de PDFs, encoding de video) necesita delegar ese trabajo fuera del event loop. Sin Worker Threads, esa operación bloquea el event loop durante cada upload. Con Worker Threads, el procesamiento ocurre en paralelo sin afectar la disponibilidad del servidor. Y cuando el proyecto necesite escalar verticalmente en un servidor de 8 cores, el Cluster module permite usar todos los cores con cambios mínimos de código.

- [ ] **Race conditions, deadlocks y primitivas de sincronización**

Race condition: cuando el resultado de una operación depende del orden no determinístico en que múltiples threads o procesos acceden a un recurso compartido. Deadlock: dos o más threads esperando cada uno un recurso que el otro tiene — se bloquean mutuamente para siempre. Mutex (Mutual Exclusion): primitiva de sincronización que garantiza que solo un thread a la vez puede acceder a una sección crítica. Semaphore: como un mutex pero permite N accesos simultáneos (útil para connection pools, rate limiters). En Node.js con Worker Threads: `SharedArrayBuffer` + `Atomics` para operaciones atómicas sin race conditions. En el mundo de bases de datos: `SELECT FOR UPDATE` como mutex a nivel de fila.

**Por qué importa:** Con Worker Threads, si dos Workers intentan escribir al mismo archivo de log simultáneamente sin sincronización, el resultado es un archivo corrupto. Si el pool de conexiones de PostgreSQL no está correctamente limitado, múltiples requests concurrentes pueden agotar las conexiones disponibles. Estos problemas son notoriamente difíciles de reproducir porque dependen de timing — aparecen en producción bajo carga, no en desarrollo. Entender las primitivas de sincronización te da las herramientas para diseñar código que sea correcto bajo concurrencia, no solo bajo un solo usuario.
