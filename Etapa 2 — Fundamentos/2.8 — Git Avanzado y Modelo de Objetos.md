# 2.8 — Git y Recuperación

> **Estado:** `DIAGNÓSTICO` · Cierre de la unidad 7 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** terminal y manejo de errores de [2.9](2.9%20—%20Linux%20y%20Shell%20Productivo.md); usa un repositorio temporal, nunca el repo de estudio.
> **Diagnóstico:** intenta primero el resultado mínimo con documentación según [METODOLOGIA](../METODOLOGIA.md#diagnóstico-antes-de-estudiar).

## Propósito

Recuperar trabajo materializado en Git o aislar una regresión sin empeorar el incidente. El objetivo es razonar desde objetos y referencias, conservar evidencia y elegir el comando menos destructivo.

## Orientación

**Qué debes lograr:** recuperar un commit perdido con reflog **o** aislar el commit defectuoso con bisect, sin alterar el repositorio principal.

**Cómo abordarlo:** captura estado y hashes, elige una sola ruta según el incidente, inspecciona el candidato y pruébalo por contenido o test.

**Entregarás:** transcript reproducible, check del resultado y, si montas el laboratorio, script seguro de setup/cleanup.

**Investiga fuera solo si:** el diagnóstico revela un hueco sobre objetos, reflog o bisect; hooks, commitlint y rebase avanzado quedan JIT.

## Diagnóstico único — Recuperar trabajo o aislar una regresión

**Timebox:** 30–60 minutos.

**Contexto proporcionado:** un repositorio temporal con un commit que perdió su ref visible, o una regresión entre commits con un check automatizable. No uses el repositorio de este plan.

**Decisiones que debes tomar:** reflog o bisect según el incidente —nunca ambas rutas—, qué evidencia identifica el commit y qué comando conserva o restaura el estado con menor riesgo.

1. Captura `status`, refs, hashes y el check que prueba el estado inicial.
2. Ejecuta **una** ruta:
   - **Reflog:** deja el commit de trabajo sin branch visible mediante borrado de una rama temporal o movimiento controlado de la ref, sin borrar el objeto deliberadamente; localízalo con reflog, inspecciona hash/diff/tree o blob, crea una branch de rescate y prueba su contenido. Ejecuta además una ref o hash inexistente y conserva stderr y exit status no-cero.
   - **Bisect:** marca un commit conocido bueno y uno malo, ejecuta `git bisect run <check>`, conserva el transcript y prueba por contenido o test el commit señalado; termina con `git bisect reset`.
3. Conserva comandos, stdout/stderr relevantes, exit codes, hashes inicial y recuperado o culpable, y la justificación de la herramienta elegida.
4. Si creaste el laboratorio, usa un script de setup/cleanup con variables citadas, directorio temporal y `trap`; comprueba que no pueda apuntar fuera del laboratorio.

## Entregable y evidencia

- **Artefacto:** transcript reproducible y, si aplica, script de setup/cleanup.
- **Evidencia:** hash recuperado o culpable demostrado por contenido o test, no solo por el mensaje del commit.
- **Caso negativo:** en reflog, la ref/hash inexistente; en bisect, el check que clasifica el commit malo frente al bueno.
- **Límite o riesgo:** estado inicial conservado, repositorio principal intacto y cleanup verificable.

## Modelo mínimo

### Worktree, index y object database

El **worktree** contiene los archivos visibles. El **index** prepara el tree del próximo commit. La **object database** almacena contenido direccionado por hash:

- blob: contenido de archivo;
- tree: nombres que apuntan a blobs u otros trees;
- commit: tree raíz, padres y metadata;
- annotated tag: objeto que referencia otro objeto.

Branches y tags ligeros son refs con nombre fuera de esa base; `HEAD` suele ser una ref simbólica. Un commit no desaparece al mover una branch: deja de ser alcanzable desde esa ref, pero puede seguir disponible hasta que Git lo elimine.

### Reflog y límites de recuperación

El reflog registra movimientos locales de refs y `HEAD`; no es “todo lo que hiciste”, no se comparte al hacer push y expira. Puede ayudarte a encontrar un commit, stash u objeto que existió. No recupera texto que nunca fue añadido como objeto, stash o commit, ni garantiza conservar objetos indefinidamente.

Antes de modificar historia, captura `status`, refs y hashes relevantes. Inspecciona candidatos con `git show` o `git cat-file` y crea una ref de rescate antes de seguir.

### Elegir la herramienta mínima

| Necesidad | Herramienta inicial | Límite |
|---|---|---|
| Deshacer públicamente un cambio | `git revert` | Crea un commit inverso; pueden existir conflictos o efectos no reversibles fuera de Git. |
| Encontrar una posición local anterior | `git reflog` | Es local, expira y solo ayuda si hubo un objeto/ref. |
| Conservar un commit encontrado | nueva branch o tag; `cherry-pick` si hace falta aplicarlo | Verifica contenido y padres antes de publicar. |
| Aislar qué commit introdujo una regresión | `git bisect run <check>` | El check debe distinguir de forma fiable bueno/malo y manejar commits no comprobables. |
| Reescribir trabajo privado | `reset` o `rebase` con respaldo entendido | Mueve refs/cambia hashes; no usar por reflejo sobre historia compartida. |

Hooks, commitlint, squash estético y rebase avanzado quedan JIT. Un hook local puede omitirse y nunca sustituye CI.

## Done cuando

- [ ] El trabajo ocurrió en un repositorio temporal y registró hash y estado iniciales.
- [ ] El hash recuperado o culpable está probado por contenido o test.
- [ ] El transcript permite repetir la ruta elegida e incluye stdout, stderr y exit codes relevantes.
- [ ] Si elegiste reflog, una ref/hash inexistente falla de forma observable.
- [ ] Si elegiste reflog, puedes explicar objeto, ref, `HEAD`, reflog y sus límites locales y temporales.
- [ ] Si elegiste bisect, el check distingue el commit bueno del malo y el transcript aísla el culpable.
- [ ] Si elegiste bisect, `git bisect reset` restaura el estado previo al diagnóstico.
- [ ] La elección entre `revert`, reflog, bisect, reset o rebase se justifica por alcance y riesgo.
- [ ] El repositorio principal permanece intacto.
- [ ] Puedes extraer evidencia y hacer cleanup seguro con las herramientas de [2.9](2.9%20—%20Linux%20y%20Shell%20Productivo.md).
