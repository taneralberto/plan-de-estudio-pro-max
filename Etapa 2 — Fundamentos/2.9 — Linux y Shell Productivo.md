# 2.9 — Linux y Shell Productivo

> **Estado:** `DIAGNÓSTICO` · Preparación de la unidad 7 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** una terminal Linux, macOS o WSL y un proceso backend que puedas detener sin riesgo.
> **Cierre:** estas herramientas sostienen el laboratorio de recuperación en [2.8](2.8%20—%20Git%20Avanzado%20y%20Modelo%20de%20Objetos.md); no añaden otro ejercicio ni Done.

## Propósito

Extraer evidencia y operar procesos desde terminal sin ocultar fallos. La meta no es memorizar flags: es poder reconstruir qué comando se ejecutó, qué datos atravesaron el pipeline y por qué terminó con éxito o error.

## Streams, redirección y composición

Todo proceso dispone de `stdin`, `stdout` y `stderr`. Redirige o conecta esos streams de forma explícita:

- `>` reemplaza un archivo y `>>` agrega al final;
- `2>` separa errores; `2>&1` los envía al mismo destino que stdout;
- `|` conecta stdout con stdin del siguiente proceso;
- el exit status `0` indica éxito; cualquier otro valor representa una condición que el caller debe interpretar.

Usa `grep`, `sort`, `uniq`, `wc` y `jq` para responder preguntas concretas sobre texto o JSON. Conserva stderr cuando investigues: un pipeline que produce salida parcial puede haber fallado.

El quoting importa. Expande `"$variable"` y `"$@"` salvo que busques deliberadamente word splitting o globbing. No evalúes texto externo como comando.

## Bash pequeño y comprobable

`set -euo pipefail` ayuda a hacer visibles algunos fallos, pero no sustituye entender excepciones de `errexit`, comandos usados como condiciones ni el exit status de cada etapa. Para un script corto:

1. declara intérprete y opciones;
2. valida argumentos y dependencias;
3. usa directorio temporal y `trap` para cleanup;
4. cita variables;
5. conserva stdout, stderr y exit code relevantes;
6. pasa ShellCheck y prueba también el camino de error.

Cron, systemd, backups remotos, correo y webhooks quedan JIT. Si una práctica futura crea un backup, solo cuenta cuando se restaura en un destino temporal y se verifica.

## Procesos, file descriptors y señales

Un proceso tiene PID, proceso padre, file descriptors y recursos visibles en `/proc` en Linux. `ps`, `pgrep`, `lsof` o `ss` permiten localizar quién escucha un puerto y qué archivos o sockets mantiene abiertos.

`SIGTERM` solicita terminación y permite cleanup cooperativo; `SIGINT` suele representar la interrupción interactiva. `SIGKILL` no puede manejarse y no permite cerrar conexiones ni vaciar buffers. Un backend debe dejar de aceptar trabajo, esperar o cancelar lo pendiente con límite, cerrar recursos y salir con estado observable.

Prueba graceful shutdown con el mismo comando que usará el entorno —por ejemplo `docker stop`— y verifica logs, exit code y ausencia de trabajo corrupto. La explicación de memoria y streams vive en [2.11](2.11%20—%20Sistemas%20Operativos%20(Profundizar).md).
