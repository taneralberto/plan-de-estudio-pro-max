# 3.1 — Contratos de API y Límites de Dominio

> **Estado:** `ACTIVO ★` · Cierre de la unidad 13 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** spec de [1.7](../Etapa%201%20—%20Entrada/1.7%20—%20Documentación%20Técnica%20Profesional.md), oracles de [1.3](../Etapa%201%20—%20Entrada/1.3%20—%20Testing%20Fundamentals.md) y modelo mínimo de [3.3](3.3%20—%20Domain-Driven%20Design%20(DDD).md).
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Publicar un contrato comprensible, verificable y evolutivo que respete los límites del dominio. El objetivo no es memorizar status codes ni implementar varios protocolos: es permitir que cliente y servidor cambien sin adivinarse mutuamente.

## Orientación

**Qué debes lograr:** publicar un contrato HTTP compatible, trazable al dominio y capaz de hacer observables sus casos válidos y negativos.

**Cómo abordarlo:** reutiliza la spec y la hoja de dominio, define primero operaciones y errores, y convierte los tres casos exigidos en contract tests.

**Entregarás:** OpenAPI validado, contract tests para caso válido, negativo y conflicto de idempotencia, y el registro de compatibilidad y trazabilidad.

**Investiga fuera solo si:** OpenAPI no resuelve una decisión concreta o necesitas contrastar compatibilidad, vocabulario o semántica HTTP.

## Modelo mínimo

### Contrato antes que framework

Un contrato debe definir:

- operación y actor autorizado;
- request, response y restricciones de datos;
- efectos observables e invariantes;
- errores estables y recuperabilidad;
- semántica de retry, timeout e idempotencia;
- compatibilidad y deprecación;
- ejemplos y contraejemplos ejecutables.

OpenAPI es el artefacto de la ruta HTTP. Valídalo con tooling, pero no confundas un schema válido con una operación correcta.

### HTTP con semántica explícita

Modela recursos con sustantivos cuando encajen. Una operación de dominio como `/reservations/{id}/cancel` puede ser más clara que forzarla a un CRUD genérico.

Usa métodos y status según el resultado real:

- `GET` lee sin solicitar efectos de negocio;
- `POST` crea o ejecuta una operación no idempotente por defecto;
- `PUT` reemplaza de forma idempotente; `PATCH` aplica un cambio definido por su media type/contrato;
- `201` crea y puede señalar el recurso con `Location`; `202` acepta trabajo pendiente; `204` no devuelve body;
- `400` indica request inválido a nivel de protocolo/sintaxis; `401` falta autenticación válida; `403` niega autorización; `404` oculta o no encuentra recurso; `409` expresa conflicto con estado actual; `422` rechaza contenido sintácticamente válido que no satisface reglas.

No memorices la lista completa: documenta los casos que tu operación puede producir y verifica que clientes puedan decidir si corregir, reintentar o detenerse. Mantén una forma de error estable, por ejemplo Problem Details, sin filtrar internals.

### Idempotencia con efecto atómico

Para una operación que el cliente puede reintentar:

1. el cliente envía una clave única;
2. el servidor la limita por actor y operación;
3. guarda fingerprint del request y resultado;
4. el registro de idempotencia y el efecto se confirman atómicamente cuando comparten transacción; si el efecto es externo, un workflow durable debe poder reconciliar reintentos;
5. la misma clave + mismo request devuelve el resultado previo;
6. la misma clave + otro request produce conflicto.

No requiere Redis. PostgreSQL puede ser la opción más simple si allí ocurre el efecto. La retención depende de la ventana de retries y del negocio, no de un TTL universal.

### Compatibilidad antes que versionado

Clasifica un cambio según consumidores reales:

- añadir un campo opcional suele ser compatible para clientes tolerantes, pero debe comprobarse;
- añadir un request requerido, eliminar/renombrar campos o cambiar significado/tipo suele romper;
- cambiar orden, paginación, defaults o errores también puede romper aunque el schema parezca igual.

Prefiere evolución aditiva, deprecación observable y migración de consumidores. Versiona cuando no puedas mantener ambos contratos con claridad; elige URI, header o media type según tooling y clientes, no por pureza.

### Paginación según datos y UX

Offset es simple y suficiente para conjuntos pequeños o estables. Cursor/keyset evita escanear grandes offsets y reduce anomalías si usa orden total, estable y único. El cursor debe ser opaco para permitir evolución; codificar base64 no lo vuelve secreto ni confiable. Documenta qué sucede ante inserciones, borrados y cambios del campo de orden.

### Dominio dentro, transporte fuera

La API traduce tipos HTTP al lenguaje de [3.3](3.3%20—%20Domain-Driven%20Design%20(DDD).md). No expongas tablas, entidades ORM o modelos de otro contexto como contrato público. La capa de traducción puede ser una función directa; agrega DTOs/adapters adicionales solo si protegen una diferencia real.

REST/HTTP es el default práctico de esta ruta. gRPC y GraphQL quedan JIT para requisitos medidos de streaming, tipado multilenguaje, grafos o clientes con necesidades realmente distintas.

## Ejercicio único — Contrato evolutivo de reservas

**Timebox:** hasta 120 minutos.

**Contexto proporcionado:** la hoja de dominio de [3.3](3.3%20—%20Domain-Driven%20Design%20(DDD).md), la spec de [1.7](../Etapa%201%20—%20Entrada/1.7%20—%20Documentación%20Técnica%20Profesional.md) y las operaciones `POST /reservations` y `GET /stock/{sku}`. Reutiliza esas entradas; no vuelvas a redactarlas.

**Decisiones que debes tomar:** schemas y errores, semántica de idempotencia, evolución compatible, trazabilidad al dominio y, solo si añades un listado, estrategia de paginación.

1. Define en OpenAPI `POST /reservations` y `GET /stock/{sku}` con schemas, ejemplos y errores.
2. Documenta cantidades inválidas, stock insuficiente y recurso no visible/autorizado.
3. Especifica la semántica completa de `Idempotency-Key`, incluida misma clave con payload diferente y atomicidad con el efecto.
4. Añade paginación solo si incluyes un listado; justifica offset o cursor con el orden y tamaño esperados.
5. Simula una evolución: agrega `expiresAt` sin romper un cliente anterior y documenta deprecación/compatibilidad.
6. Genera o escribe contract tests para al menos un caso válido, uno negativo y el conflicto de idempotencia.
7. Traza cada campo y error hasta el término/invariante de dominio que lo origina; elimina lo que filtre persistencia sin necesidad.

No implementes GraphQL, gRPC, Redis ni una segunda versión de la API.

## Entregable y evidencia

- **Artefacto:** documento OpenAPI, contract tests y registro breve de compatibilidad, deprecación y trazabilidad al dominio.
- **Evidencia:** validación del documento y salida de los contract tests para los tres casos pedidos.
- **Caso negativo:** cantidad o stock inválido y conflicto por reutilizar la clave con otro payload.
- **Límite o riesgo:** compatibilidad comprobada con un consumidor anterior y decisiones JIT no implementadas.

- [ ] El contrato documenta los errores pedidos.
- [ ] Cada operación respeta semántica HTTP o documenta por qué usa una acción de dominio.
- [ ] Idempotencia define su scope.
- [ ] Idempotencia define el fingerprint del request.
- [ ] Idempotencia define atomicidad con el efecto.
- [ ] Idempotencia define la repetición válida.
- [ ] Idempotencia define el conflicto por reutilizar la clave con otro payload.
- [ ] El cambio simulado conserva un consumidor anterior o documenta una migración verificable.
- [ ] Los límites y términos de 3.3 se reconocen en el contrato sin exponer persistencia.
- [ ] Un contract test detecta un desvío del caso válido.
- [ ] Un contract test detecta un desvío del caso negativo.
- [ ] Un contract test detecta un desvío del conflicto de idempotencia.
