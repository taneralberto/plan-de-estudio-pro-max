- [ ] **Diseño del contrato de API — REST y gRPC**

El modelo de madurez de Richardson como mapa de progreso: Nivel 0 (un endpoint para todo — RPC sobre HTTP), Nivel 1 (recursos como sustantivos — `/articles`, `/users`), Nivel 2 (verbos HTTP con semántica correcta — GET para leer, POST para crear, PUT/PATCH para actualizar, DELETE para eliminar, con status codes apropiados), Nivel 3 (HATEOAS — las respuestas incluyen links a las acciones disponibles). Naming de recursos: sustantivos en plural, jerarquía que refleja relaciones (`/articles/{id}/comments`), pero sin anidamiento infinito. Status codes correctos y sus diferencias: `200 vs 201 vs 204`, `400 vs 422`, `401 vs 403`, `404 vs 410`. Idempotencia: `GET`, `PUT` y `DELETE` deben ser idempotentes (múltiples llamadas idénticas producen el mismo resultado), `POST` no lo es por defecto.

gRPC para comunicación entre servicios: cuando REST es la opción correcta para APIs públicas (human-readable, cacheable, amplio ecosistema de herramientas) y cuándo gRPC es la opción correcta — comunicación interna entre servicios donde el contrato es fuertemente tipado con Protocol Buffers, el payload es más chico que JSON, el streaming bidireccional es nativo, y la generación de código cliente/servidor es automática. REST, GraphQL y gRPC son opciones contextuales tanto dentro como fuera de la organización. Elige según compatibilidad de clientes, contratos, caching, streaming, latencia, operabilidad y experiencia del equipo; “externo” o “interno” por sí solo no decide el protocolo.

**Por qué importa:** Una API mal diseñada es deuda técnica permanente — porque una vez que tienes clientes externos (plugins, integraciones de terceros, apps móviles), no puedes cambiar los contratos sin coordinación. Un endpoint que devuelve `200` para un error enmascarado, o que usa `POST` para operaciones que deberían ser `GET`, va a generar bugs en todos los clientes que la consuman. Diseñar la API bien desde el principio es 10 veces más barato que migrarla después.

**<span style="color: #29B6F6">Ejercicio:</span>** Diseña la API pública de un proyecto siguiendo el Nivel 2 de Richardson como mínimo. Documenta en un archivo OpenAPI/Swagger: los recursos principales (articles, users, tags, comments), todos los endpoints con sus verbos HTTP, los status codes que devuelve cada uno (incluyendo errores), y los request/response bodies con sus tipos. Verifica que todas tus operaciones de lectura son idempotentes y que los POST de creación devuelven 201 con el header `Location` apuntando al recurso creado. Además, identifica al menos dos boundaries entre servicios internos donde gRPC sería más apropiado que REST y documenta por qué (tipado fuerte, streaming, tamaño del payload).

**<span style="color: #FFA726">FreePress:</span>** FreePress tiene una "API pública documentada" como feature — diseña la API de FreePress como caso de estudio.

**Done cuando:** Puedes revisar una API REST existente e identificar en qué nivel del modelo de Richardson está, qué status codes están mal usados, y qué operaciones no son idempotentes cuando deberían serlo. Puedes diseñar una API nueva para una feature siguiendo las convenciones de naming, verbos y status codes correctamente, sin consultar la documentación. Puedes argumentar cuándo eliges REST vs gRPC para un boundary de servicio dado (público vs interno, human-readable vs binario, caching vs streaming).

- [ ] **Versionado, paginación e idempotency keys**

Versionado de APIs: URI versioning (`/v1/articles` — simple y visible), header versioning (`API-Version: 2024-01`) y content negotiation (`Accept: application/vnd.api.v2+json` — más correcto pero más complejo). Cuándo hacer un breaking change vs un cambio backward-compatible (agregar campos es safe, renombrar o eliminar no lo es). Paginación: cursor-based (más eficiente y consistente para datasets que cambian — usar un cursor opaco como `?after=eyJpZCI6MTIzfQ==`) vs offset-based (`?page=2&limit=20` — simple pero inconsistente si hay inserciones). Idempotency keys: un header `Idempotency-Key: <uuid>` que el cliente genera y el servidor usa para deduplicar requests — crítico para operaciones no idempotentes (pagos, envío de emails) donde el cliente puede reintentar sin saber si el primer intento llegó.

**Por qué importa:** La paginación offset (`?page=2`) puede producir duplicados o saltos cuando el dataset cambia entre requests. La paginación por cursor reduce ese problema si usa un orden total, estable y único; sin ese orden, o ante mutaciones relevantes y sin snapshot, también puede duplicar u omitir resultados. Y las idempotency keys son la diferencia entre "el usuario recibió el email de confirmación dos veces porque reintentó el request" y "el sistema detectó el retry y no lo procesó de nuevo".

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa en la API de tu proyecto: (1) Cursor-based pagination para el listado de artículos — el cursor es el `id` del último artículo recibido, codificado en base64 para que sea opaco. El endpoint acepta `?after=<cursor>&limit=20` y devuelve `{data: [...], nextCursor: "...", hasMore: boolean}`; (2) Idempotency keys para el endpoint de creación de artículos — el servidor guarda el resultado de cada `Idempotency-Key` en Redis por 24 horas y devuelve el mismo resultado para requests duplicados.

**<span style="color: #FFA726">FreePress:</span>** Implementa paginación cursor-based e idempotency keys en la API de FreePress — el caso del listado de artículos es el ejemplo más directo.

**Done cuando:** Puedes explicar las condiciones que necesita cursor pagination — orden total, estable y único — y cuándo tanto cursor como offset pueden producir duplicados o saltos. Puedes implementar idempotency keys en cualquier endpoint no idempotente, con almacenamiento del resultado en Redis y TTL apropiado.

**Recursos:**
- [Stripe API Docs — Idempotency](https://stripe.com/docs/api/idempotent_requests) — el ejemplo más claro de implementación de idempotency keys en producción. Stripe es la referencia de diseño de APIs en la industria.
- [*"Cursor-based Pagination"*](https://use-the-index-luke.com/no-offset) de Markus Winand — por qué offset pagination escala mal y cómo cursor pagination lo resuelve, con ejemplos SQL.
- [*"API Versioning Has No Right Way"*](https://apisyouwonthate.com/blog/api-versioning-has-no-right-way) de APIs You Won't Hate — análisis honesto de los trade-offs de cada estrategia de versionado.

- [ ] **GraphQL — Cuándo sí y cuándo no**

GraphQL resuelve problemas reales: over-fetching (el cliente recibe más datos de los que necesita), under-fetching (el cliente necesita N requests para obtener datos relacionados — el N+1 problem del REST), y la necesidad de que distintos clientes (mobile con ancho de banda limitado, desktop con pantalla grande) consuman la misma API de forma diferente. Los problemas que introduce: N+1 queries en el servidor (sin DataLoader), caching más complejo que REST (cada query puede ser distinta), mayor superficie de ataque (cualquier cliente puede pedir cualquier combinación de datos), y tooling de testing más complejo. Cuándo GraphQL tiene sentido real: múltiples clientes con necesidades de datos distintas, frontend teams que evolucionan rápido y necesitan flexibilidad, sistemas con grafos de datos complejos y relacionados.

**Por qué importa:** Muchos proyectos adoptan GraphQL porque "es moderno" sin evaluar si resuelve sus problemas reales. Un proyecto con un solo frontend probablemente no justifica GraphQL — REST bien diseñado es más simple de implementar, cachear y mantener. Pero si tuviera una app mobile, un widget embebible, y un dashboard de analytics, cada uno consumiendo datos distintos del mismo backend — ahí GraphQL empieza a tener sentido. La decisión debe basarse en los problemas reales, no en la popularidad de la tecnología.

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa el endpoint de artículo en GraphQL usando NestJS + `@nestjs/graphql` con code-first approach (si usas NestJS) o Apollo Server (si usas otro framework). Implementa DataLoader para evitar el N+1 problem al resolver el autor de cada artículo. Luego compara: ¿cuántas queries a la base de datos hace el endpoint REST equivalente vs el GraphQL con DataLoader para cargar 10 artículos con sus autores? Documenta cuánto código adicional requirió GraphQL vs REST para la misma funcionalidad.

**<span style="color: #FFA726">FreePress:</span>** Si usas NestJS, implementa el schema de GraphQL de FreePress con code-first approach y DataLoader.

**Done cuando:** Puedes analizar un proyecto nuevo y determinar con criterio técnico si GraphQL resuelve un problema real o agrega complejidad sin beneficio. Puedes implementar un schema GraphQL básico y elegir una estrategia de batching o precarga para evitar N+1; DataLoader es una opción común, no una obligación universal.

**Recursos:**
- [*"The GraphQL Guide"*](https://graphql.guide/) — guía completa con ejemplos modernos, incluyendo sección sobre cuándo NO usar GraphQL.
- [DataLoader](https://github.com/graphql/dataloader) — una opción común para batching y caching por request; también pueden resolver N+1 la precarga del ORM o resolvers diseñados para consultas agregadas.
- [*"GraphQL is not what you think it is"*](https://bessey.dev/blog/2024/05/24/why-im-over-graphql/) — perspectiva crítica y honesta sobre los trade-offs de GraphQL en producción. Balanceá con los casos de éxito para tener visión completa.
