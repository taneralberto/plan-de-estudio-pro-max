# 3.2 — Patrones de Arquitectura Avanzados

> **Alcance:** empieza por modularidad y un monolito bien delimitado. CQRS, Event Sourcing y microservicios son 🟢 JIT ante complejidad observada.

---

- [ ] **SOLID Principles — La base de código mantenible**

Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. No como acrónimo para entrevistas — como principios que determinan si tu código se puede modificar sin romper todo lo demás.

**Por qué importa:** Sin SOLID, "Clean Architecture" y "DDD" son palabras vacías. La Dependency Rule de Clean Architecture ES el Dependency Inversion Principle aplicado a arquitectura. Cada principio resuelve un problema específico de código que se vuelve inmantenible.

**<span style="color: #29B6F6">Ejercicio:</span>** Toma una clase de tu proyecto que tenga más de una responsabilidad. Identifica qué hace cada método. Separa en clases distintas siguiendo Single Responsibility Principle. Documenta el antes/después.

**<span style="color: #FFA726">FreePress:</span>** El backend de FreePress tiene clases que manejan múltiples responsabilidades (ej: un servicio que valida, transforma y persiste) — son buenos candidatos para este ejercicio.

**Done cuando:** Puedes mirar una clase y decir si viola algún principio SOLID, cuál, y cómo refactorizarla. Puedes explicar por qué "una clase que hace muchas cosas" es un problema de Single Responsibility, no solo "mala práctica".

**Recursos:**
- [*Clean Code*](https://www.amazon.com/Clean-Code-Handbook-Software-Craftsmanship/dp/0132350882) de Robert Martin — capítulos 8-10 cubren SOLID en profundidad
- [SOLID Principles Explained](https://www.baeldung.com/solid-principles) — explicación clara con ejemplos en Java (aplica igual a TypeScript)
- [SOLID en TypeScript](https://khalilstemmler.com/articles/solid-principles/solid-typescript/) — artículos de Khalil Stemmler con ejemplos específicos en TS

- [ ] **Event-Driven Architecture (EDA)**

Eventos de dominio y event bus dentro de los límites de una aplicación. La diferencia entre commands, events y queries. Por qué "cuando un usuario publica un artículo" puede emitir un evento en lugar de llamar directamente al servicio de indexación. Brokers, entrega y schemas distribuidos se estudian aparte en [3.9 — Messaging y Event Streaming](3.9%20—%20Messaging%20y%20Event%20Streaming.md).

**Por qué importa:** Cuando un módulo publica un artículo, ¿quién más necesita saberlo? El indexador de búsqueda, el sistema de notificaciones, el pipeline de analytics, el generador de sitemap. Si cada uno de esos llama directamente al siguiente, el módulo editorial termina dependiendo de la implementación interna de 4 sistemas distintos. Un evento de dominio (`ArticlePublished`) invierte esa dependencia: el publicador no sabe quién escucha, y cada consumidor puede aparecer o desaparecer sin tocar el publicador.

**<span style="color: #29B6F6">Ejercicio:</span>** Diseña el flujo de publicación de un artículo en tu proyecto usando EDA. Lista todos los eventos de dominio que ocurren (`ArticlePublished`, `ArticleUpdated`, etc.), qué información lleva cada evento, y quién los consume. Implementa un EventEmitter interno simple para `ArticlePublished` con al menos un consumidor real (ej: actualizar el índice de búsqueda).

**<span style="color: #FFA726">FreePress:</span>** Implementa en NestJS un EventEmitter interno simple para `ArticlePublished` con al menos un consumidor real (ej: actualizar el índice de búsqueda).

**Done cuando:** Puedes tomar un flujo de negocio con múltiples efectos secundarios (publicar un artículo, procesar un pago, registrar un usuario) y diseñar los eventos de dominio correspondientes — qué emite, qué consume, qué información lleva cada evento. Puedes explicar la diferencia entre un event y un command y por qué importa para el flujo de control.

**Recursos:**
- [*Building Event-Driven Microservices*](https://www.amazon.com/Building-Event-Driven-Microservices-Leveraging-Organizational/dp/1492057894) de Adam Bellemare — el libro más práctico sobre EDA, cubre desde los conceptos hasta Kafka y particionado.
- [Martin Fowler — "What do you mean by Event-Driven?"](https://martinfowler.com/articles/201701-event-driven.html) — artículo fundamental que distingue Event Notification, Event-Carried State Transfer, Event Sourcing y CQRS. Leerlo antes del libro.

- [ ] **CQRS (Command Query Responsibility Segregation)**

Separar el modelo de lectura del de escritura. Cuándo tiene sentido (sistemas con alta lectura y poca escritura, reportes complejos que no encajan en el modelo de escritura) y cuándo es overkill (un CRUD simple donde el mismo modelo sirve para leer y escribir). Event Sourcing + CQRS como combo: el event store como fuente de verdad, las proyecciones como modelos de lectura derivados.

**Por qué importa:** Un panel de analytics que agrega datos de lectura, tiempo en página, dispositivos, referrers — construir esas vistas desde el mismo modelo normalizado que usas para editar es doloroso: queries complejas, joins pesados, modelo que no encaja. CQRS te permite tener un modelo de escritura limpio (DDD) y modelos de lectura optimizados para cada vista — sin comprometer ninguno de los dos.

**<span style="color: #29B6F6">Ejercicio:</span>** Toma un dashboard de analytics de tu proyecto. Diseña un modelo de lectura separado (una tabla desnormalizada o una colección Redis) optimizado específicamente para responder "top 10 artículos por vistas en los últimos 7 días". Define el Command que actualiza ese modelo (ej: `IncrementArticleView`) y la Query que lo consume. No hace falta implementarlo completo — alcanza con el diseño del modelo y los tipos en TypeScript.

**<span style="color: #FFA726">FreePress:</span>** El dashboard de analytics de FreePress es un caso de uso ideal para CQRS — muchas vistas de lectura con queries complejas sobre datos agregados.

**Done cuando:** Puedes analizar una feature nueva y decidir con criterio si CQRS agrega valor o complejidad innecesaria. Puedes diseñar el modelo de escritura y al menos un modelo de lectura para un caso concreto, justificando la desnormalización. Puedes explicar qué problema introduce CQRS que el CRUD clásico no tiene (consistencia eventual entre modelos).

**Recursos:**
- [Martin Fowler — "CQRS"](https://martinfowler.com/bliki/CQRS.html) — artículo conciso que explica cuándo tiene sentido y cuándo no. Empieza acá antes del libro.
- [*Implementing Domain-Driven Design*](https://www.amazon.com/Implementing-Domain-Driven-Design-Vaughn-Vernon/dp/0321834577) de Vaughn Vernon — el capítulo sobre CQRS + Event Sourcing es la referencia técnica más completa.
- [*Designing Data-Intensive Applications*](https://www.amazon.com/Designing-Data-Intensive-Applications-Reliable-Maintainable/dp/1449373321) de Martin Kleppmann — caps. 11-12 sobre stream processing y derived data modelan exactamente el problema que CQRS resuelve desde una perspectiva de sistemas.

- [ ] **Microservicios — Patrones y Anti-patrones**

Saga pattern (cómo manejar transacciones distribuidas sin 2PC), Circuit Breaker (cómo evitar que la falla de un servicio cascade al resto), Service Mesh (Istio, Linkerd — cómo manejar la comunicación entre servicios a nivel de infraestructura), API Gateway (punto de entrada único, auth, rate limiting, routing). Strangler Fig como estrategia de migración. Distributed monolith como el anti-patrón más común: todos los servicios desplegados por separado pero acoplados igual que un monolito.

**Por qué importa:** El 80% de los proyectos que "adoptan microservicios" terminan con un distributed monolith: tienen el costo operacional de microservicios (múltiples deploys, red entre servicios, observabilidad compleja) sin ninguno de los beneficios (deploys independientes, equipos autónomos, escalabilidad granular). Entender los patrones y anti-patrones te permite tomar la decisión correcta antes de comprometerte — y saber cuándo un monolito bien estructurado es la respuesta correcta (casi siempre al principio).

**<span style="color: #29B6F6">Ejercicio:</span>** Analiza tu proyecto como si fuera a migrar de monolito a microservicios. Identifica cuáles módulos serían candidatos naturales a servicios independientes y cuáles no (usando el criterio de cohesión y volatilidad de cambio, no "porque es una feature"). Para el módulo que elegirías separar primero, diseña el Strangler Fig: ¿qué se migra primero, cómo coexisten el monolito y el microservicio durante la transición, cómo se maneja la data?

**<span style="color: #FFA726">FreePress:</span>** FreePress es un buen caso de estudio: tiene módulos con cohesión clara (Editorial, Analytics, Notificaciones) y módulos que deberían quedar juntos (Auth + User management).

**Done cuando:** Puedes revisar una arquitectura de microservicios propuesta e identificar si es un distributed monolith (señales: servicios que no pueden desplegarse independientemente, base de datos compartida, llamadas síncronas en cadena). Puedes explicar cuándo el Saga pattern (coreografía vs orquestación) es preferible sobre 2PC y cuáles son los trade-offs de consistencia eventual que introduce.

**Recursos:**
- [*Building Microservices*](https://www.amazon.com/Building-Microservices-Designing-Fine-Grained-Systems/dp/1492034029) de Sam Newman — la biblia. Segunda edición (2021) incluye lecciones aprendidas de la industria.
- [*Monolith to Microservices*](https://www.amazon.com/Monolith-Microservices-Evolutionary-Patterns-Transform/dp/1492047848) de Sam Newman — la secuela práctica, específicamente sobre el proceso de migración con patrones concretos.
- [Martin Fowler — "Microservices"](https://martinfowler.com/articles/microservices.html) — el artículo original que definió el término. Leerlo para entender las condiciones en las que microservicios tienen sentido real.
