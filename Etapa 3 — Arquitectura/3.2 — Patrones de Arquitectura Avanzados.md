# 3.2 — Diseño Modular y Arquitectura Evolutiva

> **Estado:** `ACTIVO ★` · Unidad 8 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** poder ejecutar tests y fijar un comportamiento observable. Si no puedes, adelanta la práctica mínima de [1.3 — Testing](../Etapa%201%20—%20Entrada/1.3%20—%20Testing%20Fundamentals.md) antes del ejercicio.
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Hacer que un cambio pequeño toque pocos lugares, conserve comportamiento y pueda explicarse. Arquitectura no es aplicar patrones por nombre: es decidir qué ocultar, qué acoplar y qué costo aceptar hoy.

## Orientación

**Qué debes lograr:** reducir el costo observable de un cambio pequeño sin alterar el comportamiento actual.

**Cómo abordarlo:** fija el comportamiento con characterization tests, separa solo el límite que estorba y compara el costo antes y después.

**Entregarás:** un único refactor protegido, su diff y un registro before/after con la decisión y el punto de detención.

**Investiga fuera solo si:** una transformación concreta te bloquea o la evidencia exige un escalón arquitectónico mayor.

## Modelo mínimo

### Cohesión y acoplamiento

- **Cohesión:** elementos que cambian por la misma razón viven juntos.
- **Acoplamiento:** cuánto debe conocer o cambiar un módulo cuando cambia otro.
- **Information hiding:** un módulo expone lo necesario y oculta decisiones que pueden variar.
- **Change amplification:** una decisión es costosa si un cambio local obliga a editar muchos archivos o desplegar componentes sin relación.

Un módulo útil tiene una responsabilidad expresada como capacidad del dominio, una API pequeña y dependencias visibles. “Una carpeta por tipo técnico” no garantiza un límite.

### Estado, efectos y composición

De programación funcional conserva lo que reduce incertidumbre:

- funciones puras para reglas y transformaciones;
- datos inmutables cuando evitan estados intermedios imposibles;
- efectos de red, reloj, filesystem o base de datos en límites explícitos;
- composición de funciones pequeñas cuando mejora el flujo.

De orientación a objetos conserva:

- encapsular invariantes junto al estado que protegen;
- composición antes que jerarquías profundas;
- polimorfismo cuando existen comportamientos sustituibles reales;
- contratos que preservan precondiciones, resultados y errores.

No conviertas cada dependencia en interfaz ni cada `if` en patrón. Una implementación directa es más mantenible mientras no exista variación o límite que ocultar.

### SOLID como preguntas, no como checklist

| Principio | Pregunta útil |
|---|---|
| SRP | ¿Qué razones reales hacen cambiar este módulo? |
| OCP | ¿Existe una variación frecuente que merece extensión sin editar el núcleo? |
| LSP | ¿Una sustitución conserva contrato, errores e invariantes? |
| ISP | ¿Cada consumidor depende solo de operaciones que usa? |
| DIP | ¿La política del dominio depende de infraestructura concreta sin necesidad? |

Nombrar una violación no prueba un problema. Señala el cambio que cuesta, el riesgo o la evidencia de acoplamiento.

### Arquitectura que escala por necesidad

Sube solo cuando el escalón anterior deja evidencia de un límite:

1. función o módulo directo;
2. monolito modular con límites internos;
3. evento interno para efectos secundarios independientes;
4. proceso o servicio separado por despliegue, escala, aislamiento, cumplimiento u ownership realmente independientes.

Antes de subir de escalón debes poder nombrar el problema medido, el nuevo costo operativo y una alternativa más simple descartada. Mensajería y fallos distribuidos se estudian en la unidad 14; la unidad 15 aplica esos trade-offs en System Design.

## Refactor seguro

Un refactor cambia estructura sin cambiar comportamiento observable. Antes de tocar código incierto:

1. identifica el comportamiento que debe conservarse;
2. añade characterization tests si no existe una red confiable;
3. realiza una transformación pequeña;
4. ejecuta tests y revisa el diff;
5. solo entonces implementa el cambio funcional.

Un characterization test captura lo que el sistema hace hoy, incluso si ese comportamiento luego se discute. No lo confundas con afirmar que todo comportamiento actual es correcto.

## Ejercicio único — Reducir el costo de un cambio

**Timebox:** aplica la [regla antiatasco canónica](../METODOLOGIA.md#regla-antiatasco): tras unas 8 horas de primera pasada sin alcanzar el resultado, reduce al caso mínimo, conserva evidencia parcial y continúa. La alarma no aprueba el cierre.

**Contexto proporcionado:** un módulo pequeño que mezcle regla de negocio, persistencia y presentación de errores. Puede ser el flujo de reserva de [`safe-change-api`](../PROYECTOS.md#proyecto-a--safe-change-api) o código propio sanitizado.

**Decisiones que debes tomar:** qué cambio resulta incómodo, qué comportamiento conservar, qué único límite separar y dónde detener el refactor.

1. Define un cambio concreto que hoy resulte incómodo, por ejemplo añadir expiración de reservas.
2. Antes de refactorizar, registra qué archivos y responsabilidades tendrías que tocar.
3. Añade uno o dos characterization tests del comportamiento actual, incluido un caso negativo.
4. Separa únicamente el límite que reduce ese cambio: regla pura, acceso a datos o traducción HTTP.
5. Mantén una API pública pequeña y evita crear una interfaz si solo renombra la implementación.
6. Ejecuta los tests después de cada transformación y revisa que el diff no cambie comportamiento.
7. Reevalúa el cambio inicial: compara lugares tocados, dependencias y riesgo antes/después.
8. Escribe por qué te detuviste y qué evidencia exigiría el siguiente escalón arquitectónico.

No implementes el cambio funcional: esta unidad conserva un solo refactor. El cambio se aplicará después en el proyecto o en otra unidad, no como trabajo duplicado.

## Entregable y evidencia

- **Artefacto:** un único refactor con uno o dos characterization tests y su diff.
- **Evidencia:** inventario before/after de archivos, responsabilidades, dependencias y riesgo, más tests verdes tras cada transformación.
- **Caso negativo:** un comportamiento actual protegido explícitamente.
- **Límite o riesgo:** decisión de parada, consecuencia aceptada y señal que justificaría el siguiente escalón.

## Done cuando

- [ ] Conservaste un único refactor y su diff como artefacto.
- [ ] Fijaste comportamiento con un characterization test que falla si el contrato cambia.
- [ ] Protegiste un caso negativo del comportamiento actual.
- [ ] Identificaste la cohesión del módulo.
- [ ] Identificaste su acoplamiento relevante.
- [ ] Nombraste la decisión que el módulo debe ocultar.
- [ ] El refactor reduce una dificultad de cambio observable, no solo satisface un patrón.
- [ ] Los tests conservaron comportamiento tras cada transformación.
- [ ] El diff contiene transformaciones explicables.
- [ ] Justificaste el límite elegido según la evidencia actual.
- [ ] Registraste la consecuencia aceptada.
- [ ] Registraste la señal que justificaría evolucionar la arquitectura.
- [ ] Explicaste problema, decisión, evidencia e incertidumbre.
- [ ] Completaste la R1 del cierre crítico.
