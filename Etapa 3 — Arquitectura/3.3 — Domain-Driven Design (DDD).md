# 3.3 — Límites de Dominio

> **Estado:** `ACTIVO` · Primera pasada de la unidad 13 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** una necesidad y vocabulario de negocio, aunque todavía sean ambiguos.
> **Cierre:** prepara el modelo; la unidad se demuestra y cierra en [3.1 — API Design](3.1%20—%20API%20Design.md).

## Propósito

Decidir quién es dueño de una regla y qué lenguaje usa antes de exponer un contrato. DDD aporta herramientas para evitar un modelo global que mezcle significados; no obliga a crear microservicios, repositories o una clase por cada sustantivo.

## Orientación

**Qué debes lograr:** delimitar el lenguaje y los dueños de las reglas que deberá respetar el contrato de la unidad 13.

**Cómo abordarlo:** registra solo los términos, invariantes, límites y traducciones necesarios para decidir el contrato.

**Entregarás:** completarás la hoja que se reutiliza dentro del único ejercicio y cierre de la unidad 13 en [3.1](3.1%20—%20API%20Design.md); no es una entrega separada.

**Investiga fuera solo si:** una invariante real exige una táctica DDD que no puedes justificar con el modelo mínimo.

## Modelo mínimo

### Lenguaje ubicuo

Recoge términos que negocio y código deben usar con el mismo significado dentro de un contexto. Para cada término registra:

- definición y ejemplo;
- regla o invariante asociada;
- sinónimos ambiguos que conviene retirar;
- quién puede cambiar su significado.

Si “disponible” significa stock físico para inventario y cupo vendible para reservas, no intentes resolverlo con un campo universal: nombra ambos conceptos.

### Bounded context

Un bounded context delimita un modelo, lenguaje y conjunto de reglas coherentes. No equivale automáticamente a módulo, repositorio, proceso, equipo o microservicio; puede implementarse como un módulo dentro del mismo monolito.

Busca el límite cuando aparecen:

- significados distintos para el mismo término;
- invariantes y ritmos de cambio diferentes;
- ownership claro de datos o decisiones;
- traducción necesaria entre modelos.

No inventes cuatro contextos para un CRUD pequeño. Un solo contexto bien nombrado es válido.

### Relación entre contextos

Para cada integración basta registrar:

1. quién es upstream y publica el contrato;
2. quién es downstream y debe adaptarse;
3. qué datos cruzan;
4. quién traduce el modelo y qué ocurre ante incompatibilidad.

Una anticorruption layer agrega valor cuando protege un modelo de un contrato externo complejo o inestable. Una función de traducción directa basta cuando el límite es pequeño. Shared Kernel y catálogos completos de Context Mapping quedan JIT para colaboración real entre equipos.

### Tácticas solo para proteger reglas

- **Entity:** importa su identidad y ciclo de vida.
- **Value Object:** importa el valor completo; suele ser inmutable.
- **Aggregate:** límite dentro del cual deben preservarse invariantes al aceptar un cambio.
- **Repository:** abstracción de acceso a aggregates cuando evita que persistencia invada las reglas.

No clasifiques cada objeto. Usa una táctica únicamente si aclara identidad, igualdad, consistencia o acceso. Un aggregate grande aumenta contención; uno demasiado pequeño desplaza invariantes a coordinación externa.

## Preparación del ejercicio único de la unidad 13

Esta preparación no tiene timebox ni entrega separados: forma parte del único ejercicio y cierre de la unidad 13 en [3.1](3.1%20—%20API%20Design.md).

**Contexto proporcionado:** `safe-change-api` o el mismo caso propio que usarás para el contrato, más la necesidad y el vocabulario de negocio disponibles.

**Decisiones que debes tomar:** si inventario y reservas comparten un contexto pequeño o requieren modelos distintos, quién posee cada invariante y dónde traducir significados.

Produce una sola hoja:

```md
Contexto y propósito:
Términos: stock disponible, reserva, SKU, expiración…
Invariantes y dueño:
Actores:
Datos que entran/salen del contexto:
Traducciones necesarias:
Tácticas usadas y por qué:
```

Ambas decisiones de contexto son válidas si las reglas y el costo justifican el límite. La hoja se reutiliza en OpenAPI y su evidencia se comprueba con el contrato y los tests de 3.1, no con otro cierre aquí.

## Preparación completa cuando

- [ ] Cada término relevante tiene un significado dentro de un contexto concreto.
- [ ] Cada invariante tiene un dueño.
- [ ] Evitaste depender de un “modelo global” ambiguo.
- [ ] Registraste solo los límites necesarios en la hoja.
- [ ] Registraste cómo se traducen los datos que cruzan cada límite.
- [ ] Cada táctica usada protege una decisión real.
