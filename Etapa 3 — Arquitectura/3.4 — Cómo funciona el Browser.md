- [ ] **Critical Rendering Path**

HTML parsing → DOM tree → CSSOM → Render tree → Layout → Paint → Composite. Por qué un CSS en el `<head>` bloquea el render (render-blocking resource). Por qué un `<script>` sin `defer` bloquea el parsing del HTML. Qué es el reflow (recalcular layout) y por qué es costoso. Qué es el repaint y cuándo se dispara. Cómo el browser decide qué va al GPU compositor thread (transforms, opacity) y qué permanece en el main thread.

**Por qué importa:** Cuando un editor de artículos se siente lento al escribir, o cuando un listado tarda en aparecer, el problema casi siempre está en el Critical Rendering Path mal entendido. Agregar `async` o `defer` mal en un script puede romper el orden de ejecución del código. Poner el CSS en el `<body>` en lugar del `<head>` causa FOUC (Flash of Unstyled Content). Sin entender este modelo, optimizar performance de frontend es disparar al aire.

**<span style="color: #29B6F6">Ejercicio:</span>** Abre Chrome DevTools → Performance → graba la carga de una app web. Identifica: cuánto tiempo tarda el First Contentful Paint (FCP), cuáles son los recursos que bloquean el render (aparecen en rojo), y si hay reflows costosos durante la interacción. Aplica al menos una optimización (defer en scripts, preload en fonts, eliminar CSS bloqueante) y mide el FCP antes y después con Lighthouse.

**<span style="color: #FFA726">FreePress:</span>** Abre Chrome DevTools en FreePress y graba la carga. Identifica los recursos que bloquean el render y optimiza el FCP.

- [ ] **Rendering: CSR vs SSR vs SSG vs ISR**

Client-Side Rendering (todo el HTML lo genera JavaScript en el browser — primera carga lenta, navegación rápida). Server-Side Rendering (el servidor genera el HTML por cada request — primera carga rápida, SEO natural, más carga en el servidor). Static Site Generation (HTML pre-generado en build time — el más rápido, pero los datos deben ser estáticos o tolerar staleness). Incremental Static Regeneration (SSG con revalidación: el HTML se regenera en background cuando envejece, sin rebuild completo). Cuándo usar cada uno y por qué los frameworks modernos los ofrecen todos.

**Por qué importa:** Un CMS tiene artículos que deben ser indexables por Google (SEO) y deben cargar rápido para el lector. CSR puro (una SPA sin SSR) entrega HTML vacío al crawler de Google. Eso es un problema real: el contenido no se indexa bien, o se indexa mal. Entender las diferencias entre estos modos de rendering no es un detalle de framework — es una decisión arquitectónica que impacta directamente en SEO, performance y costo de infraestructura.

**<span style="color: #29B6F6">Ejercicio:</span>** Configura Server-Side Rendering en tu frontend para las páginas públicas de lectura de artículos (no el panel de admin). Verifica el resultado abriendo el source HTML de la página (`Ctrl+U`) — el contenido del artículo debe aparecer en el HTML, no solo un tag raíz vacío. Mide el FCP con Lighthouse antes y después de habilitar SSR.

- [ ] **Web APIs que no conocés (y deberías)**

Intersection Observer (detectar cuándo un elemento entra al viewport, sin scroll events), ResizeObserver (detectar cambios de tamaño de un elemento), MutationObserver (detectar cambios en el DOM), Performance API (medir tiempos reales en el browser con `performance.mark()` y `performance.measure()`), Web Workers (correr JavaScript en un thread separado sin bloquear el main thread), AbortController (cancelar fetch requests y otras operaciones async), Broadcast Channel (comunicación entre tabs del mismo origen).

**Por qué importa:** Muchos bugs de performance en frontend son causados por usar la API incorrecta para el trabajo. Un infinite scroll implementado con `window.scroll` event + `getBoundingClientRect()` ejecuta decenas de cálculos de layout por scroll. El mismo infinite scroll con IntersectionObserver ejecuta cero cálculos en scroll — solo se dispara cuando el elemento entra al viewport. Conocer estas APIs no es trivia — es la diferencia entre código que funciona y código que funciona bien bajo carga.

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa tres features usando las APIs correspondientes: (1) Infinite scroll en un listado con IntersectionObserver — cuando el último elemento visible entra al viewport, cargar más. (2) Un componente de imagen lazy-load con IntersectionObserver — la imagen no se descarga hasta que está cerca del viewport. (3) Cancelación de búsqueda en tiempo real con AbortController — si el usuario escribe rápido, cancelar el fetch anterior antes de hacer el nuevo.
