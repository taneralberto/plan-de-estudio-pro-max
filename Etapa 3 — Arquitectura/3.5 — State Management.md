# 3.5 — State Management

---

- [ ] **El problema del estado — De verdad**

Por qué existe state management, qué problemas concretos resuelve, y por qué la mayoría de apps NO necesitan Redux. Los cuatro tipos de estado que toda app maneja: local state (solo le importa a un componente — input de un form), shared state (varios componentes lo necesitan — el usuario autenticado), server state (datos que viven en el servidor y se sincronizan — los artículos publicados), URL state (lo que está en la URL — el filtro activo, la página actual). Cada tipo tiene herramientas distintas y mezclarlos es el origen de la mayoría de los bugs de estado.

**Por qué importa:** El error clásico es meter todo en un store global (NgRx, Redux) porque "así se hace state management". El resultado: boilerplate enorme, bugs difíciles de trazar, y estado del servidor duplicado en el cliente que queda desincronizado. Los artículos publicados son server state — viven en Postgres, no en el browser. Ponerlos en un store significa sincronizarlos manualmente, gestionar loading/error states, y decidir cuándo invalidar el cache. TanStack Query hace todo eso con menos código y más correctamente.

- [ ] **Patrones de State Management**

Flux/Redux pattern (unidirectional data flow, actions, reducers, store — NgRx en Angular). Signals (Angular 17+, Solid, Preact — fine-grained reactivity sin el overhead de observables). Atoms (Jotai, Recoil — estado atómico y composable). Stores (Zustand, Pinia — stores minimalistas sin boilerplate). Proxy-based (MobX, Valtio — observabilidad automática de objetos mutables). TanStack Query para server state — cache automático, background refetching, optimistic updates, error/loading states out of the box.

**Por qué importa:** Conocer los patrones te permite elegir la herramienta correcta en lugar de usar siempre la misma. Un proyecto grande con múltiples features complejas puede justificar NgRx. Un dashboard con datos del servidor justifica TanStack Query. Un formulario complejo justifica state local con signals. Usar NgRx para todo porque "es el estándar de Angular" es el equivalente a usar Redux para un contador — técnicamente funciona, pero el overhead es desproporcionado al problema.

- [ ] **Signals — El futuro del state management**

Qué son signals: un valor reactivo que notifica automáticamente a sus dependientes cuando cambia, sin subscriptions manuales ni detección de cambios costosa. Fine-grained reactivity: solo se re-renderiza exactamente el componente (o la parte del template) que depende del signal que cambió, no el árbol completo. Por qué Angular, Solid, Preact y Vue los adoptaron y están migrando away de Zone.js y Virtual DOM respectivamente. La diferencia con observables (signals son síncronos y siempre tienen un valor; observables son asíncronos y pueden estar vacíos) y con setState de React (signals actualiza solo los dependientes, setState puede re-renderizar el árbol entero).

**Por qué importa:** Angular históricamente usaba Zone.js para detectar cambios — un monkey-patch de todas las APIs asíncronas del browser que ejecuta change detection en el árbol completo después de cada evento. En una app grande, eso puede significar miles de checks por cada click. Signals elimina ese overhead: solo se actualiza lo que depende del signal que cambió. Si un signal de `currentUser` cambia, solo los componentes que usan ese signal se actualizan — no toda la app. Es una mejora de performance estructural, no una optimización puntual.

**<span style="color: #29B6F6">Ejercicio:</span>** Migra el estado del usuario autenticado en tu proyecto de un BehaviorSubject o un servicio con observable a un Signal. Usa `computed()` para derivar el estado de "¿tiene permisos de editor?" a partir del signal del usuario. Habilita `ChangeDetectionStrategy.OnPush` en los componentes que consumen ese signal y verifica con DevTools que solo se re-renderizan cuando el signal cambia, no en cada evento.
