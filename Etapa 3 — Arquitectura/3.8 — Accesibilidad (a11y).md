# 3.8 — Accesibilidad (a11y)

---

- [ ] **WCAG 2.1 — Lo que necesitas saber**

Los cuatro principios POUR: Perceivable (la información debe ser perceptible — texto alternativo en imágenes, captions en videos), Operable (la UI debe ser operable — navegable por teclado, sin trampas de foco), Understandable (el contenido debe ser comprensible — labels en formularios, mensajes de error claros), Robust (el contenido debe ser interpretable por tecnologías asistivas — HTML semántico, ARIA cuando corresponde). La primera regla de ARIA: "no uses ARIA si el HTML nativo puede hacerlo". Focus management: cuándo mover el foco programáticamente y cómo hacerlo correctamente.

**Por qué importa:** Un CMS tiene una audiencia que incluye lectores con discapacidades visuales, motoras y cognitivas. En muchos países, la accesibilidad web es un requisito legal (ADA en EEUU, EAA en Europa). Pero más allá de lo legal: una app accesible es una app mejor construida. El HTML semántico que beneficia a un screen reader también beneficia al SEO. El contraste de color que ayuda a alguien con baja visión también ayuda a leer en exteriores bajo el sol. Accesibilidad no es una feature — es calidad.

**<span style="color: #29B6F6">Ejercicio:</span>** Navega tu app usando SOLO el teclado durante 10 minutos: tab para avanzar, shift+tab para retroceder, enter/space para activar. Documenta cada punto donde el foco desaparece, donde no puedes llegar, o donde el orden de tab no tiene sentido. Luego instala NVDA (Windows) o activa VoiceOver (Mac) y navega la misma sesión escuchando. Anota al menos 5 problemas concretos que encontraste y propone la corrección HTML/ARIA para cada uno.

**<span style="color: #FFA726">FreePress:</span>** Navega FreePress usando solo el teclado y un screen reader — el editor de artículos es el componente más complejo, empieza por ahí.

**Done cuando:** Puedes abrir Lighthouse en Chrome, correr el audit de Accessibility, y entender qué significa cada error reportado — no solo copiando el fix sugerido, sino sabiendo por qué ese elemento falla. Puedes explicar la diferencia entre `aria-label`, `aria-labelledby` y `aria-describedby` y cuándo usar cada uno, sin necesidad de consultar la documentación.

**Recursos:**
- [web.dev — Learn Accessibility](https://web.dev/learn/accessibility) — el curso más completo y actualizado sobre a11y web. Gratuito, con ejemplos interactivos. Empezar acá.
- [a11y-101.com](https://a11y-101.com/) — referencia rápida y práctica organizada por componente (modals, dropdowns, tabs). Útil como checklist mientras construyes.
- [NVDA (Windows)](https://www.nvaccess.org/) / [VoiceOver (Mac/iOS)](https://support.apple.com/guide/voiceover/welcome/mac) — los screen readers que vas a usar en el ejercicio. Instala NVDA si estás en Windows — es gratis y es el más usado.

- [ ] **Componentes accesibles — Patrones concretos**

Los patrones de componentes que más se rompen en accesibilidad: modals (focus trap, `aria-modal`, `role="dialog"`, cerrar con Escape), dropdowns/selects custom (role de `listbox` o `menu` según el uso, keyboard navigation), tabs (`role="tablist"`, `role="tab"`, `aria-selected`, cambio de tab con flechas), formularios (labels asociados con `for`/`id` o `aria-labelledby`, mensajes de error enlazados con `aria-describedby`, `aria-invalid`). Live regions para anunciar cambios dinámicos sin mover el foco (`aria-live="polite"` para notificaciones, `aria-live="assertive"` para errores críticos).

**Por qué importa:** El 90% de los problemas de accesibilidad en apps web están en componentes custom que reemplazan elementos nativos del browser. Un `<button>` nativo es accesible por defecto — es focusable, activable con Enter/Space, y tiene rol semántico. Un `<div (click)="doSomething()">` no tiene ninguna de esas propiedades. Cada vez que reemplazas un elemento nativo con un div interactivo, estás creando trabajo de accesibilidad. Conocer los patrones ARIA correctos te permite construir componentes custom que funcionen como sus contrapartes nativas.

**<span style="color: #29B6F6">Ejercicio:</span>** Audita el componente más complejo de tu app (un editor, un formulario con validaciones, un modal). Identifica todos los componentes custom que deberían ser accesibles (toolbar de formato, modal de confirmación, dropdown de categorías). Para el modal, implementa el patrón completo: focus trap cuando se abre, cierre con Escape, retorno del foco al trigger cuando se cierra, `role="dialog"` con `aria-labelledby` apuntando al título del modal.

**<span style="color: #FFA726">FreePress:</span>** Audita el editor de artículos de FreePress — el componente más complejo de la app. Para el modal de inserción de imágenes, implementa el patrón completo de accesibilidad.

**Done cuando:** Puedes implementar un modal accesible completo desde cero — con focus trap, cierre con Escape, y gestión correcta del foco — sin usar una librería externa. Puedes explicar cuándo usar `aria-live="polite"` vs `"assertive"` y qué problema causa usar `"assertive"` para notificaciones no urgentes.

**Recursos:**
- [ARIA Authoring Practices Guide (APG)](https://www.w3.org/WAI/ARIA/apg/patterns/) — el estándar W3C con los patrones ARIA correctos para cada tipo de componente (modal, tabs, dropdown, etc.). La referencia definitiva.
- [Angular CDK — a11y module](https://material.angular.io/cdk/a11y/overview) — el módulo de accesibilidad del Angular CDK incluye `FocusTrap`, `LiveAnnouncer`, y `HighContrastMode`. Usarlo en lugar de reinventar la rueda.
- [*"Inclusive Components"*](https://inclusive-components.design/) de Heydon Pickering — el libro más práctico sobre construir componentes accesibles desde cero. Cada capítulo es un componente (toggles, tabs, modals, etc.).
