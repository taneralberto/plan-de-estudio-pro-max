# 3.9 — Messaging y Event Streaming

---

- [ ] **El problema que resuelven los message queues**

Comunicación síncrona (REST, gRPC): el caller espera la respuesta del callee — si el callee está lento o caído, el caller también sufre. Comunicación asíncrona con queues: el producer deposita un mensaje en la queue y continúa sin esperar — el consumer lo procesa cuando puede. Desacoplamiento temporal: producer y consumer no necesitan estar disponibles al mismo tiempo. Desacoplamiento de velocidad: si el producer genera mensajes más rápido de lo que el consumer puede procesar, la queue actúa como buffer. Dead Letter Queue (DLQ): dónde van los mensajes que no pudieron ser procesados después de N reintentos — crítico para no perder mensajes sin saberlo. At-least-once vs exactly-once delivery: los queues distribuidos garantizan que el mensaje llega, pero pueden entregarlo más de una vez — tus consumers deben ser idempotentes.

**Por qué importa:** Cuando un sistema de notificaciones depende de un endpoint síncrono, si el servicio de email está lento, el endpoint que publica también lo está. Con un queue, el endpoint deposita un mensaje y retorna inmediatamente. El servicio de email consume de forma asíncrona. Si el servicio de email falla, el mensaje se reintenta automáticamente. La publicación no se ve afectada.

- [ ] **RabbitMQ vs Kafka — Cuándo usar cada uno**

RabbitMQ: un message broker tradicional. Los mensajes se entregan a consumers y se eliminan una vez procesados (acknowledged). Ideal para: task queues, workflows, RPC asíncrono, cuando el procesamiento de cada mensaje es el objetivo. Kafka: un distributed event log. Los mensajes se guardan indefinidamente (configurable) y múltiples consumer groups pueden leerlos independientemente desde cualquier offset. Ideal para: event sourcing, audit logs, pipelines de datos, cuando necesitas reproducir eventos o múltiples sistemas leen los mismos eventos. Redis Streams: Kafka simplificado sobre Redis — sin las garantías de durabilidad de Kafka pero suficiente para muchos casos de uso y sin infraestructura adicional si ya usas Redis.

**Por qué importa:** Elegir Kafka para un task queue de notificaciones de email es como usar una base de datos distribuida para guardar 3 configuraciones. Kafka tiene overhead operacional significativo: ZooKeeper o KRaft, particionado, replication factor, retention policies. RabbitMQ es mucho más simple de operar para casos de uso de message queue tradicionales. La decisión incorrecta implica meses de operaciones innecesariamente complejas. Para proyectos en sus primeras etapas, RabbitMQ o Redis Streams son casi siempre la respuesta correcta.

- [ ] **Event Schema Design y Versionado**

Los eventos son contratos entre servicios — el schema ES la API del producer. Todo evento debería tener: `event_id` (UUID para idempotencia), `timestamp` (cuándo ocurrió, no cuándo se envió), `event_type` ( qué pasó), `version` (del schema, no del negocio), `correlation_id` (para rastrear el flujo completo), `producer_id` (quién lo emitió). Payload design: fat events incluyen todos los datos relevantes en el evento (consumers no necesitan llamar de vuelta al producer); thin events incluyen solo identificadores y una referencia al dato completo. Fat events cuando el consumer necesita los datos inmediatamente sin round-trip al producer; thin events cuando el producer no es owner del dato o cuando el dato cambia frecuentemente y sería stale para el momento en que el consumer lo procesa. Formatos de schema: JSON Schema (legible, fácil de empezar, sin code generation — ideal para debugging y equipos que arrancan), Avro (binario compacto, schema evolution nativa, ecosistema Kafka — ideal cuando tienes millones de eventos y compatibilidad backwards), Protocol Buffers (code generation, strongly typed, usado con gRPC pero también válido para eventos — ideal cuando quieres type safety y performance). Trade-off central: JSON para simpleza y debuggear, Avro para ecosistemas Kafka y evolución de schemas, Protobuf para type safety y performance. Schema Registry: almacenamiento centralizado de schemas con versionado — evita que un producer cambie el formato de un evento y rompa todos los consumers al mismo tiempo. Con Kafka, Confluent Schema Registry es el estándar de facto. Modos de compatibilidad: BACKWARD (el schema nuevo puede leer datos viejos — agregar campos opcionales), FORWARD (el schema viejo puede leer datos nuevos — campos nuevos tienen defaults), FULL (ambos). Sin registry, un producer puede cambiar el formato de un evento y romper cada consumer simultáneamente — y vas a descubrirlo en producción. Cambios no-breaking: agregar campo opcional, agregar nuevo event type. Cambios breaking: eliminar campo, renombrar campo, cambiar tipo de campo. Para cambios breaking: versiona el evento (`OrderCreatedV1`, `OrderCreatedV2`), usa reglas de evolución de schema, o aplica el patrón expand-contract — publica ambas versiones durante la transición, consumers migran gradualmente, y solo entonces remueve la versión vieja.

**Por qué importa:** Elegiste el broker correcto en el subtema anterior, pero si el formato de tus eventos es un caos, tienes el mismo problema disfrazado. Sin schema design explícito, cada team define eventos diferentes para el mismo dominio. Sin versionado, un deploy del producer rompe todos los consumers. Sin registry, no hay manera de saber qué schemas existen ni quién depende de cuál. El schema del evento es la interfaz pública de un servicio — merece el mismo rigor que una API REST. Ignorar esto te lleva a eventos frágiles, consumers que se rompen en producción sin warning, y un sistema donde nadie se atreve a cambiar un campo porque no sabe qué se va a romper.
