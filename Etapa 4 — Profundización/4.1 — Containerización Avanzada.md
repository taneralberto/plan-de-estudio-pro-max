# 4.1 — Containerización para Entrega

> **Estado:** `DIAGNÓSTICO` · Preparación de la unidad 16 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** un backend que arranque localmente y tenga un smoke test.
> **Cierre:** no genera otro ejercicio; prepara la misma imagen que se desplegará en [4.3](4.3%20—%20Cloud%20Fundamentals.md).

## Propósito

Empaquetar una aplicación reproducible con el menor contenido y privilegio necesarios. El objetivo no es usar todas las funciones de Docker ni alcanzar un tamaño o conteo de CVEs arbitrario.

## Orientación

**Qué debes lograr:** diagnosticar si la imagen está lista para el único despliegue de la unidad 16.
**Cómo abordarlo:** intenta el resultado durante **30–60 minutos**; si falla, corrige solo el hueco observado sobre esa misma imagen.
**Conservarás:** Dockerfile, `.dockerignore`, imagen y registro de verificación como insumos de [4.3](4.3%20—%20Cloud%20Fundamentals.md), no como otra entrega.
**Investiga fuera solo si:** un fallo concreto exige documentación oficial de Docker o del scanner.

## Modelo mínimo

La imagen de runtime debe contener solo lo necesario para arrancar y terminar correctamente con los límites de la plataforma. El orden de instrucciones determina qué cambios invalidan capas y cuánto trabajo puede reutilizar el build.

Alpine o distroless son opciones, no metas. Elige una base que la aplicación y el equipo puedan depurar/actualizar. Una imagen más pequeña no es automáticamente más segura.

## Diagnóstico del Dockerfile

**Contexto proporcionado:** un backend arrancable con smoke test y la imagen que continuará hacia 4.3.

**Decisiones que debes justificar:** imagen base; separación de stages; contenido y privilegios de runtime; orden de capas y caché; tratamiento de vulnerabilidades.

Sobre la imagen real, demuestra:

- build reproducible desde un checkout limpio;
- versión de runtime explícita y lockfile respetado;
- `.dockerignore` que excluye Git, dependencias locales, artifacts y secretos;
- stages separados cuando build y runtime necesitan herramientas distintas;
- solo dependencias y archivos necesarios en runtime;
- usuario non-root y archivos con permisos mínimos;
- `CMD`/entrypoint que recibe `SIGTERM` y permite graceful shutdown;
- configuración y secretos fuera de la imagen;
- proceso que escucha el `PORT` de la plataforma y no depende de disco local persistente;
- orden de instrucciones que aprovecha caché sin ocultar qué capas invalida cada cambio;
- scan registrado y vulnerabilidades triadas por fix disponible, exposición y alcance.

## Entregable y evidencia

- **Artefacto preparatorio:** Dockerfile, `.dockerignore` e imagen que usará 4.3.
- **Evidencia:** salida de build/run y smoke test; baseline de digest/tamaño; explicación del orden de capas y registro del scan.
- **Caso negativo:** contenido o privilegio no permitido, fallo de `SIGTERM` o vulnerabilidad relevante sin tratamiento.
- **Límite:** el diagnóstico alimenta el único despliegue de 4.3; no abras otro laboratorio.

```bash
docker build -t safe-change-api:local .
docker run --rm -e PORT=8080 -p 8080:8080 safe-change-api:local
# smoke test contra /healthz o endpoint equivalente
# scanner disponible en el proyecto/CI
```

Registra digest/tamaño solo como baseline. Un hallazgo sin fix puede aceptarse temporalmente con riesgo y seguimiento; no declares éxito por “cero vulnerabilidades”.

## Diagnóstico aprobado cuando

- [ ] La imagen se construye desde un checkout limpio.
- [ ] La versión de runtime es explícita y la instalación respeta el lockfile.
- [ ] `.dockerignore` excluye Git, dependencias locales, artifacts y secretos.
- [ ] La imagen contiene solo dependencias y archivos necesarios en runtime.
- [ ] El proceso se ejecuta como non-root con permisos mínimos.
- [ ] La configuración y los secretos permanecen fuera de la imagen.
- [ ] El servicio escucha `PORT` sin depender de disco local persistente.
- [ ] El smoke test responde.
- [ ] El proceso termina limpiamente con `SIGTERM`.
- [ ] Explicaste qué capas invalidan caché y por qué el orden actual ayuda.
- [ ] Cada vulnerabilidad relevante tiene fix, mitigación o aceptación registrada.

Si falla un punto, corrige ese hueco sobre la imagen que se desplegará en 4.3.

## JIT y recursos

Docker Compose puede levantar PostgreSQL para desarrollo. `depends_on` no prueba readiness: usa retry acotado o healthcheck real. Profiles, herramientas UI y orquestación de producción quedan JIT.

La base de Docker se aplica mediante la unidad 16 de [RECURSOS.md](../RECURSOS.md) y documentación oficial puntual. No necesitas otro curso si el diagnóstico pasa.
