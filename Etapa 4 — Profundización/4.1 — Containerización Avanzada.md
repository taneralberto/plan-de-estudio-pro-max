# 4.1 — Containerización para Entrega

> **Estado:** `DIAGNÓSTICO` · Preparación de la unidad 17 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** un backend que arranque localmente y tenga un smoke test.
> **Cierre:** no genera otro ejercicio; prepara la misma imagen que se desplegará en [4.3](4.3%20—%20Cloud%20Fundamentals.md).

## Propósito

Empaquetar una aplicación reproducible con el menor contenido y privilegio necesarios. El objetivo no es usar todas las funciones de Docker ni alcanzar un tamaño o conteo de CVEs arbitrario.

## Diagnóstico del Dockerfile

Sobre una imagen real, demuestra:

- build reproducible desde un checkout limpio;
- versión de runtime explícita y lockfile respetado;
- `.dockerignore` que excluye Git, dependencias locales, artifacts y secretos;
- stages separados cuando build y runtime necesitan herramientas distintas;
- solo dependencias y archivos necesarios en runtime;
- usuario non-root y archivos con permisos mínimos;
- `CMD`/entrypoint que recibe `SIGTERM` y permite graceful shutdown;
- configuración y secretos fuera de la imagen;
- proceso que escucha el `PORT` de la plataforma y no depende de disco local persistente;
- scan registrado y vulnerabilidades triadas por fix disponible, exposición y alcance.

Alpine o distroless son opciones, no metas. Elige una base que la aplicación y el equipo puedan depurar/actualizar. Una imagen más pequeña no es automáticamente más segura.

## Verificación mínima

```bash
docker build -t safe-change-api:local .
docker run --rm -e PORT=8080 -p 8080:8080 safe-change-api:local
# smoke test contra /healthz o endpoint equivalente
# scanner disponible en el proyecto/CI
```

Registra digest/tamaño solo como baseline. Un hallazgo sin fix puede aceptarse temporalmente con riesgo y seguimiento; no declares éxito por “cero vulnerabilidades”.

Docker Compose puede levantar PostgreSQL para desarrollo. `depends_on` no prueba readiness: usa retry acotado o healthcheck real. Profiles, herramientas UI y orquestación de producción quedan JIT.

## Diagnóstico aprobado cuando

- [ ] La imagen se construye desde limpio y arranca como non-root.
- [ ] No contiene secretos, devDependencies ni archivos locales innecesarios.
- [ ] El servicio responde al smoke test y termina limpiamente con `SIGTERM`.
- [ ] Puedes explicar qué capas invalidan caché y por qué el orden actual ayuda.
- [ ] Cada vulnerabilidad relevante tiene fix, mitigación o aceptación registrada.

Si no cumples un punto, corrige ese hueco sobre la imagen del ejercicio de 4.3; no abras otro laboratorio.
