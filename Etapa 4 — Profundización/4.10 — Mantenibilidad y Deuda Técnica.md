# 4.10 — Mantenibilidad y Deuda Técnica

> **Estado histórico:** integrado; no es una unidad que debas completar por separado.

El contenido tiene dos destinos:

- complejidad, límites, costo de cambio, characterization tests y refactor pequeño → [3.2 — Diseño Modular y Arquitectura Evolutiva](../Etapa%203%20—%20Arquitectura/3.2%20—%20Patrones%20de%20Arquitectura%20Avanzados.md);
- code smells con evidencia, lectura de legacy, seams, historial y revisión del cambio → [4.7 — Leer Código Ajeno y Code Review](4.7%20—%20Leer%20Código%20Ajeno%20y%20Code%20Review.md).

La deuda técnica no equivale a código viejo o desagradable: es una decisión que aumenta un costo o riesgo relevante en el contexto actual. Registra impacto y opción de pago; no abras un “gran refactor” sin un cambio concreto y tests que protejan comportamiento.

Strangler Fig, Mikado Method y técnicas profundas de seams quedan JIT para una migración o módulo legacy real. No requieren otro ejercicio ni otro Done en la ruta activa.
