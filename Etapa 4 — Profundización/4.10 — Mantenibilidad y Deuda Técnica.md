# 4.10 — Mantenibilidad y Deuda Técnica

> ⚠️ **Práctica continua — no esperes a llegar a la Etapa 4.** "Deja el código mejor de como lo encontraste" es un hábito que se instala desde el principio. Lee esta sección antes de empezar a construir FreePress en serio.

- [ ] **Refactoring — El arte de mejorar código sin cambiar comportamiento**

Cuándo refactorizar: antes de agregar una feature (el código actual no te deja extenderlo limpiamente), durante code review (cuando ves que el código nuevo es correcto pero difícil de leer), y nunca como proyecto separado de semanas ("el gran refactor" que nunca termina). El prerequisito ineludible: tests que confirmen que el comportamiento no cambió. Técnicas concretas: Extract Function (cuando una función hace demasiado, extrae parte en otra con nombre descriptivo), Replace Conditional with Polymorphism (cuando tienes `if type === 'A' / else if type === 'B'` que crece — polimorfismo lo resuelve abierto/cerrado), Introduce Parameter Object (cuando una función recibe 6 parámetros — agruparlos en un objeto con nombre), Rename Variable (el refactor más frecuente y más subestimado — un nombre bueno elimina la necesidad de un comentario).

**Por qué importa:** Todo proyecto crece. El código que escribes hoy lo vas a leer en 6 meses sin contexto, cuando tienes que agregar una feature que no estaba prevista. La deuda técnica no es código malo — es código que fue correcto para el contexto en que se escribió pero que ahora frena el avance. Refactorizar continuamente en pequeños pasos (el modelo del Boy Scout: "deja el código mejor de como lo encontraste") es la única forma de mantener la velocidad de desarrollo a largo plazo. El "gran refactor" no funciona porque nunca hay tiempo para terminarlo y el codebase sigue creciendo mientras tanto.

**<span style="color: #29B6F6">Ejercicio:</span>** Elige el módulo más complejo de tu proyecto que más te cuesta modificar — ese que cada vez que tienes que tocarlo abres el archivo con miedo. Primero escribe characterization tests (tests que documentan el comportamiento actual, correcto o no). Luego aplica al menos tres técnicas de refactoring de Fowler sobre él, en pequeños commits con el test suite verde en cada uno. Al final, pide a alguien (o a un LLM) que lea el código antes y después y evalúe la legibilidad.

**<span style="color: #FFA726">FreePress:</span>** Elige el módulo más complejo de FreePress — el que más te cuesta modificar.

**Done cuando:** Puedes abrir cualquier módulo y aplicar al menos una técnica de refactoring de Fowler sin romper los tests existentes — y sin tardar más de 30 minutos en identificar qué técnica aplica. Podés explicar por qué "el gran refactor" es una antipattern organizacional, no solo técnico.

**Recursos:**
- [*"Refactoring"*](https://www.amazon.com/Refactoring-Improving-Existing-Addison-Wesley-Signature/dp/0134757599) de Martin Fowler — LA referencia absoluta. Segunda edición usa JavaScript. El catálogo de técnicas (capítulos 6-12) es el que más vas a consultar.
- [refactoring.guru](https://refactoring.guru/refactoring) — versión online y gratuita del catálogo de refactorings con ejemplos visuales. Útil como referencia rápida mientras trabajas.
- [*"Clean Code"*](https://www.amazon.com/Clean-Code-Handbook-Software-Craftsmanship/dp/0132350882) de Robert Martin — complemento de Refactoring, más enfocado en principios de escritura que en técnicas de transformación. Leer con espíritu crítico — algunos ejemplos del libro son debatibles.

- [ ] **Legacy Code — Cómo trabajar con código que da miedo**

Qué es legacy code según Michael Feathers: código sin tests — no código viejo. El problema no es la antigüedad sino la imposibilidad de modificarlo con confianza. Characterization tests: cuando no hay tests, antes de tocar nada escribes tests que documentan el comportamiento actual del código (correcto o no) para tener una red de seguridad. Seams: un punto donde puedes cambiar el comportamiento del código sin modificarlo — clave para agregar tests a código no diseñado para serlo. Strangler Fig aplicado a código: envolver gradualmente la funcionalidad legacy con código nuevo hasta poder eliminar el viejo, en lugar de reescribir todo de una vez.

**Por qué importa:** Tu proyecto es hoy nuevo. Pero en 2 años, las partes que escribiste al principio — sin experiencia en DDD, sin tests, con las decisiones de arquitectura que después aprendiste que eran incorrectas — van a ser tu legacy code. Y en cualquier trabajo, el primer día vas a heredar un codebase que nadie entiende completamente. Saber trabajar con legacy code es saber trabajar con el 90% del código que existe en el mundo real.

**<span style="color: #29B6F6">Ejercicio:</span>** Identifica en tu proyecto el módulo más viejo o más complejo que no tiene tests. Sin entender completamente qué hace, escribe characterization tests: ejecuta el código con distintos inputs, observa los outputs, y escribe tests que documenten exactamente esos outputs. Una vez que tienes la red de seguridad, identifica un seam — un punto donde puedes inyectar una dependencia mockeada — y úsalo para hacer el módulo más testeable sin cambiar su comportamiento observable.

**<span style="color: #FFA726">FreePress:</span>** Identifica en FreePress el módulo más viejo o más complejo que no tiene tests.

**Done cuando:** Puedes abrir un módulo sin tests, agregarle characterization tests en menos de una hora sin entender completamente su implementación, y luego hacer un refactor pequeño con la confianza de que los tests te van a avisar si rompiste algo. Puedes explicar la diferencia entre characterization tests y tests de comportamiento esperado, y cuándo cada uno tiene sentido.

**Recursos:**
- [*"Working Effectively with Legacy Code"*](https://www.amazon.com/Working-Effectively-Legacy-Michael-Feathers/dp/0131177052) de Michael Feathers — el clásico absoluto. Cada capítulo es una técnica específica para un tipo de problema de legacy code. Denso y práctico al mismo tiempo.
- [*"Refactoring"*](https://www.amazon.com/Refactoring-Improving-Existing-Addison-Wesley-Signature/dp/0134757599) de Martin Fowler — el capítulo sobre "Code Smells" complementa perfectamente el trabajo de Feathers.
- [*"The Mikado Method"*](https://www.amazon.com/Mikado-Method-Ola-Ellnestam/dp/1617291218) de Ellnestam y Bäckman — técnica para hacer refactors grandes de forma incremental sin bloquearse. Complemento práctico de Feathers para refactors complejos.
