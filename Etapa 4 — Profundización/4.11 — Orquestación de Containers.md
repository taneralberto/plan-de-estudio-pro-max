# 4.11 — Orquestación de Containers y GitOps

- [ ] **Kubernetes — Conceptos fundamentales**

Pods, Services, Deployments, ReplicaSets, ConfigMaps, Secrets, Ingress. La arquitectura del cluster: control plane (API server, etcd, scheduler, controller manager) vs worker nodes (kubelet, kube-proxy). No necesitas ser un cluster admin, pero SÍ necesitas entender qué hace K8s y por qué existe: orquestar containers a escala que Docker Compose no puede manejar.

**Por qué importa:** K8s existe porque cuando tienes 50 containers distribuidos en 10 servidores, necesitas algo que decida dónde corren, los reinicie si fallan, escale bajo carga y haga deploys sin downtime. Sin entender K8s, vas a trabajar en equipos que lo usan sin poder depurar problemas de scheduling, entender por qué un Pod está en CrashLoopBackOff, o configurar recursos y límites correctamente. No es una herramienta opcional en backend moderno a escala.

**<span style="color: #29B6F6">Ejercicio:</span>** Despliega tu proyecto en un cluster local con Minikube o Kind. Escribe los manifiestos YAML para: Deployment del backend con 2 réplicas, Service que lo expone, ConfigMap para variables de entorno no sensibles, Secret para credenciales de base de datos, e Ingress que rutee `/api` al backend. Verifica que el rolling update funciona sin downtime cambiando la imagen del Deployment.

**<span style="color: #FFA726">FreePress:</span>** Desplégá FreePress en un cluster local con Minikube o Kind — el backend es NestJS, usa sus Dockerfiles existentes.

**Done cuando:** Puedes leer el output de `kubectl describe pod` y diagnosticar por qué un Pod no está corriendo (imagen inexistente, recursos insuficientes, liveness probe fallando, secret faltante). Puedes explicar la diferencia entre un Deployment y un StatefulSet y cuándo usarías cada uno.

**Recursos:**
- [KodeKloud — Kubernetes for Developers](https://kodekloud.com/courses/kubernetes-for-application-developers/) — el mejor curso práctico con labs interactivos. Ideal si vienes de Docker pero nunca tocaste K8s.
- [*Kubernetes Up & Running*](https://www.amazon.com/Kubernetes-Running-Dive-Future-Infrastructure/dp/109811020X) de Brendan Burns (co-creador de K8s) — la referencia técnica más sólida. Tercera edición actualizada.
- [kubectl Cheat Sheet oficial](https://kubernetes.io/docs/reference/kubectl/quick-reference/) — tenerlo a mano mientras practicas con Minikube.

- [ ] **GitOps**

> **Prerrequisito:** Kubernetes — Conceptos fundamentales.

Infraestructura y configuración de deploys declaradas en Git como fuente de verdad. ArgoCD y Flux observan el repositorio y reconcilian el cluster para que coincida con lo declarado. En push-based deployment el pipeline empuja cambios; en pull-based GitOps el cluster observa Git y se actualiza mediante un controlador. Cada cambio queda registrado en commits revisables.

**Por qué importa:** GitOps reduce la necesidad de dar al CI credenciales de escritura amplias sobre el cluster y permite detectar configuration drift. No elimina la necesidad de proteger Git, el controlador, sus credenciales ni el proceso de aprobación.

**<span style="color: #29B6F6">Ejercicio:</span>** Configura ArgoCD en tu cluster local. Crea un repositorio con los manifiestos, haz que ArgoCD lo observe y verifica un cambio de imagen mediante commit y reconciliación automática.

**<span style="color: #FFA726">FreePress:</span>** Crea los manifiestos de los servicios de FreePress en el repositorio de infraestructura.

**Done cuando:** Puedes explicar los trade-offs entre push y pull, mostrar el historial del estado deseado y demostrar cómo el controlador detecta y corrige una desviación del cluster.

**Recursos:**
- [ArgoCD Docs — Getting Started](https://argo-cd.readthedocs.io/en/stable/getting_started/) — guía oficial para instalar ArgoCD y hacer el primer sync.
- [*GitOps and Kubernetes*](https://www.amazon.com/GitOps-Kubernetes-Continuous-Deployment-Environments/dp/1617297275) de Billy Yuen et al. — profundización opcional.

- [ ] **Alternativas a K8s para proyectos más chicos**

Docker Swarm (orquestación nativa de Docker, mucho más simple que K8s), Fly.io (plataforma con deploy por Dockerfile, sin gestionar infraestructura), Railway y Render (PaaS moderno con zero-config deploy). Un VPS con Docker Compose detrás de Nginx es una arquitectura válida y suficiente para la mayoría de proyectos personales y startups tempranas. Cuándo el overhead operacional de K8s no vale la pena.

**Por qué importa:** K8s tiene un costo operacional real: necesitas entender networking, RBAC, storage classes, ingress controllers, y certificate management antes de hacer el primer deploy productivo. Para un proyecto en sus primeras etapas, ese overhead es puro costo sin beneficio. Saber cuándo NO usar K8s es tan valioso como saber usarlo — y te evita perder semanas configurando infraestructura cuando podrías estar construyendo el producto.

**<span style="color: #29B6F6">Ejercicio:</span>** Despliega tu proyecto completo (backend + frontend + base de datos + cache) en Fly.io o Railway usando solo el `docker-compose.yml` o los Dockerfiles existentes. Configura variables de entorno, volúmenes persistentes para la base de datos, y dominios custom. Documenta qué limitaciones encontraste comparado con lo que podrías hacer con K8s.

**<span style="color: #FFA726">FreePress:</span>** Despliega FreePress completo (NestJS + Angular + Postgres + Redis) en Fly.io o Railway usando el `docker-compose.yml` del proyecto.

**Done cuando:** Puedes recibir un nuevo proyecto y, en 10 minutos de análisis, decidir con criterio técnico si necesita K8s, Docker Swarm, un PaaS (Fly.io/Render), o un VPS simple. Puedes articular los trade-offs de cada opción en términos de costo operacional, escalabilidad máxima, y complejidad de mantenimiento.

**Recursos:**
- [Fly.io Docs — Getting Started](https://fly.io/docs/getting-started/) — documentación oficial con ejemplos para Node.js y PostgreSQL. Muy accesible.
- [Kamal](https://kamal-deploy.org/) — herramienta de deploy de 37signals (creadores de Rails) para deployar containers en VPS con zero-downtime. Alternativa moderna a K8s para proyectos chicos.
- [Martin Fowler — "Kubernetes is for everyone?"](https://martinfowler.com/articles/dont-start-with-microservices.html) — reflexión sobre cuándo la complejidad de K8s no se justifica.
