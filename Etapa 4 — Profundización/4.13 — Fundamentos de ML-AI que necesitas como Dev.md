## Propósito

Entender la matemática mínima para no razonar por metáforas y medir el comportamiento de un coding agent con un oracle externo. No necesitas entrenar un transformer ni construir una vector database.

## Matemática mínima

### Probabilidad de tokens no es probabilidad de verdad

En cada paso, el modelo asigna probabilidades a posibles tokens y el proceso de decoding elige uno. Esas probabilidades describen continuación bajo el modelo y el contexto; no significan “80 % de que esta afirmación sea cierta”.

Para evaluar una tarea necesitas una variable observable, por ejemplo `tests_passed`, `scope_violation` o `rollback_succeeded`, definida antes de ver la salida.

### Vectores, producto punto y similitud

Un embedding representa una entrada como un vector:

```text
x = [x₁, x₂, …, xₙ]
```

El producto punto `x · y` combina pares de componentes. Cosine similarity normaliza por la longitud de los vectores:

```text
cos(x, y) = (x · y) / (||x|| ||y||)
```

Valores mayores suelen indicar cercanía bajo ese modelo de embeddings, no equivalencia ni verdad. La búsqueda exacta sigue siendo mejor para IDs, símbolos y términos que no deben aproximarse.

### Atención como ponderación

Una capa de atención transforma tokens en vectores y calcula qué información ponderar. En forma simplificada:

```text
scores = QKᵀ / √d
weights = softmax(scores)
output = weights · V
```

Esto explica que cada posición combine información de otras posiciones y que el coste crezca con el contexto. No permite deducir que el modelo “entendió” una instrucción ni predecir si una respuesta será correcta.

### Medición pequeña y honesta

Con pocos casos usa proporciones descriptivas:

```text
pass_rate = casos_que_pasan / casos_totales
false_assurance_rate = afirmó_éxito_pero_falló / casos_donde_afirmó_éxito
```

Si el agente no afirmó éxito en ningún caso, registra `false_assurance_rate` como `N/A` en vez de dividir por cero.

Separa resultados por slices relevantes, como normal/adversarial o cambio dentro/fuera de alcance. Cuatro casos enseñan el proceso, pero no estiman el rendimiento general del modelo ni justifican rankings.

## Ejercicio único — Eval de un coding agent

Usa los cuatro casos preparados en [1.6](../Etapa%201%20—%20Entrada/1.6%20—%20AI%20Literacy.md):

1. Ejecuta cada tarea en una rama o worktree limpio con el mismo modelo, configuración y límites.
2. No reveles el caso adversarial; conserva los checks como oracle externo.
3. Guarda diff, reporte del agente, checks realmente ejecutados, tiempo aproximado y resultado.
4. Ejecuta tú los checks y registra pass/fail, cambios fuera de alcance y si la afirmación del agente coincidió con la evidencia.
5. Calcula `pass_rate` y `false_assurance_rate`; compara slice normal vs adversarial.
6. Elige un fallo, cambia una sola variable —contexto, aceptación o permiso— y repite. Describe el resultado como caso observado, no como conclusión universal.
7. Explica qué parte del resultado provino del modelo, del harness, del contexto, de la herramienta o del oracle.

Si una ejecución tiene coste o acceso no disponible, usa cuatro diffs previamente generados y conserva los mismos criterios ciegos. No sustituyas los checks por una calificación subjetiva.
