# 4.2 — Pipeline de Entrega

> **Estado:** `ACTIVO` · Preparación de la unidad 16 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** tests de [1.3](../Etapa%201%20—%20Entrada/1.3%20—%20Testing%20Fundamentals.md) e imagen diagnosticada en [4.1](4.1%20—%20Containerización%20Avanzada.md).
> **Cierre:** se demuestra con el deploy y rollback de [4.3](4.3%20—%20Cloud%20Fundamentals.md), no con otro pipeline de práctica.

## Propósito

Convertir un commit revisado en un artifact identificable y desplegarlo mediante un camino repetible.

## Orientación

**Qué debes lograr:** dejar configurado el camino reproducible de PR y main que ejecutará 4.3.
**Cómo abordarlo:** aquí diseña e implementa workflow, permisos y comandos; en 4.3 ejecuta el push autorizado y demuestra digest, revisión, smoke test y rollback.
**Conservarás:** workflow, comandos y campos de trazabilidad como insumos del único entregable de la unidad 16.
**Investiga fuera solo si:** una decisión real del deploy exige documentación de GitHub Actions, Cloud Run o IAM.

**Timebox:** no tiene uno separado porque no es otro ejercicio; comparte con 4.1 y 4.3 el presupuesto total por sustrato declarado en 4.3.

## Modelo mínimo

CI reduce feedback; CD controla promoción y recuperación. La cadena commit → digest → revisión permite demostrar qué se promovió: evita rebuilds entre entornos porque el mismo digest identifica el mismo artifact. Ningún pipeline es el “único firewall”; tests, revisión, permisos, observabilidad y rollback siguen siendo controles complementarios.

## Preparación del pipeline

**Contexto proporcionado:** GitHub Actions, la imagen de 4.1 y Cloud Run como destino del único despliegue.

**Decisiones que debes tomar:** checks de PR; política del scan; permisos de CI/runtime; stop condition; comandos de smoke test y rollback.

### Lo que se prepara aquí

En pull requests configura:

1. checkout e instalación desde lockfile;
2. lint y typecheck si existen;
3. tests relevantes, incluidos los que cruzan PostgreSQL;
4. build del servicio/imagen;
5. scan de dependencias o imagen con política explícita;
6. reporte claro y sin secretos.

En main configura:

1. autenticación de GitHub Actions en GCP con Workload Identity Federation u otra credencial efímera;
2. build único etiquetado por commit SHA;
3. publicación en Artifact Registry con digest conservado;
4. deploy de ese mismo artifact a un entorno de prueba;
5. smoke test;
6. promoción o stop según evidencia;
7. referencia de la revisión anterior para rollback.

No agregues matrix builds, SAST múltiple o jobs paralelos si no soportas varias versiones ni reducen feedback medido. Una tag mutable como `latest` no demuestra qué se desplegó.

### Lo que se demuestra en 4.3

[4.3](4.3%20—%20Cloud%20Fundamentals.md) ejecuta el workflow contra GCP y conserva la relación commit → digest → revisión, la salida de checks/smoke test, las dos pruebas de acceso denegado y el rollback sin rebuild. Esa ejecución cierra la unidad 16; este archivo no crea otra entrega ni otro cierre.

## Permisos y secretos

- Define `permissions` mínimos del workflow; no uses permisos de escritura globales por comodidad.
- Separa identidad que publica imágenes de identidad que ejecuta el servicio.
- Guarda valores sensibles en Secret Manager/GitHub Secrets y evita imprimirlos o pasarlos como build args.
- Prefiere federación a una clave JSON de service account de larga vida.
- Protege el entorno que pueda afectar usuarios/datos con aprobación explícita.

## Deploy no es release

Cloud Run crea revisiones y permite mover tráfico o volver a una anterior. Usa despliegue directo para este laboratorio; entiende canary/blue-green/feature flags, pero impleméntalos solo ante riesgo que el rollout simple no controle.

Una migración de schema no debe ejecutarse al arrancar cada instancia. Usa un job/paso único y cambios compatibles; la estrategia y evidencia de rollback/roll-forward pertenecen a [2.6 — Migraciones Seguras (unidad 10)](../Etapa%202%20—%20Fundamentos/2.6%20—%20Data%20Migrations%20y%20Schema%20Evolution.md).

## Insumos listos para 4.3 cuando

- [ ] El workflow de PR instala desde el lockfile.
- [ ] El workflow de PR ejecuta los checks deterministas definidos.
- [ ] El workflow de main construye una sola imagen identificada por SHA.
- [ ] La promoción reutiliza el digest en vez de reconstruir la imagen.
- [ ] La autenticación usa una credencial efímera.
- [ ] Los permisos de CI y runtime siguen least privilege.
- [ ] Los secretos no se incluyen en build args ni logs.
- [ ] El comando de smoke test está definido antes del deploy.
- [ ] El comando de rollback está definido antes del deploy.
- [ ] Los campos commit, digest, revisión y evidencia están preparados para completarse en 4.3.
