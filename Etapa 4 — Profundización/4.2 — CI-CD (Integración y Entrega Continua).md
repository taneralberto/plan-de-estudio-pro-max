# 4.2 — Pipeline de Entrega

> **Estado:** `ACTIVO` · Preparación de la unidad 16 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** tests de [1.3](../Etapa%201%20—%20Entrada/1.3%20—%20Testing%20Fundamentals.md) e imagen diagnosticada en [4.1](4.1%20—%20Containerización%20Avanzada.md).
> **Cierre:** se demuestra con el deploy y rollback de [4.3](4.3%20—%20Cloud%20Fundamentals.md), no con otro pipeline de práctica.

## Propósito

Convertir un commit revisado en un artifact identificable y desplegarlo mediante un camino repetible. CI reduce feedback; CD controla promoción y recuperación. Ningún pipeline es el “único firewall”: tests, revisión, permisos, observabilidad y rollback siguen siendo necesarios.

## Flujo mínimo

### Pull request

1. checkout e instalación desde lockfile;
2. lint y typecheck si existen;
3. tests relevantes, incluidos los que cruzan PostgreSQL;
4. build del servicio/imagen;
5. scan de dependencias o imagen con política explícita;
6. reporte claro y sin secretos.

No agregues matrix builds, SAST múltiple o jobs paralelos si no soportas varias versiones ni reducen feedback medido.

### Main

1. autenticar GitHub Actions en GCP con Workload Identity Federation u otra credencial efímera;
2. construir una vez y etiquetar por commit SHA;
3. publicar en Artifact Registry y conservar el digest;
4. desplegar ese mismo artifact a un entorno de prueba;
5. ejecutar smoke test;
6. promover o detener según evidencia;
7. conservar referencia de la revisión anterior para rollback.

Evita rebuilds entre entornos: mismo digest significa mismo artifact. Una tag mutable como `latest` no basta para demostrar qué se desplegó.

## Permisos y secretos

- Define `permissions` mínimos del workflow; no uses permisos de escritura globales por comodidad.
- Separa identidad que publica imágenes de identidad que ejecuta el servicio.
- Guarda valores sensibles en Secret Manager/GitHub Secrets y evita imprimirlos o pasarlos como build args.
- Prefiere federación a una clave JSON de service account de larga vida.
- Protege el entorno que pueda afectar usuarios/datos con aprobación explícita.

## Deploy no es release

Cloud Run crea revisiones y permite mover tráfico o volver a una anterior. Usa despliegue directo para este laboratorio; entiende canary/blue-green/feature flags, pero impleméntalos solo ante riesgo que el rollout simple no controle.

Una migración de schema no debe ejecutarse al arrancar cada instancia. Usa un job/paso único y cambios compatibles; la estrategia detallada pertenece a la unidad 10.

## Preparación completa cuando

- [ ] Cada PR ejecuta checks deterministas desde lockfile.
- [ ] Main produce una imagen identificada por SHA/digest y no la reconstruye para promoverla.
- [ ] Autenticación, permisos y secretos siguen least privilege y no aparecen en logs.
- [ ] Smoke test y rollback tienen comandos definidos antes del deploy.
- [ ] Puedes señalar artifact, revisión y evidencia de cada entrega.
