# 4.3 — Entrega Práctica en GCP

> **Estado:** `ACTIVO ★` · Cierre de la unidad 16 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** imagen de [4.1](4.1%20—%20Containerización%20Avanzada.md) y pipeline diseñado en [4.2](4.2%20—%20CI-CD%20(Integración%20y%20Entrega%20Continua).md).
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Desplegar un backend pequeño en GCP, saber qué identidades y servicios participan, verificarlo y recuperarlo. No estudiar catálogos de cloud ni replicar infraestructura que un servicio gestionado ya resuelve.

## Orientación

**Qué debes lograr:** desplegar mediante el pipeline un artifact identificable y demostrar acceso mínimo, entrega y rollback.
**Cómo abordarlo:** reutiliza la imagen de 4.1 y el workflow de 4.2; ejecuta una sola secuencia deploy → verificación → segunda revisión → rollback.
**Entregarás:** servicio/pipeline reproducible y el registro que relaciona commit, digest, revisión, accesos, smoke test, coste y recuperación.
**Investiga fuera solo si:** IAM, Cloud SQL o Secret Manager bloquean un paso concreto del ejercicio.

## Modelo mínimo de GCP

| Necesidad | Servicio de esta unidad |
|---|---|
| ejecutar container HTTP | Cloud Run service/revision |
| guardar imagen | Artifact Registry |
| PostgreSQL gestionado | Cloud SQL |
| identidad de CI/runtime | IAM service accounts + Workload Identity Federation |
| secretos | Secret Manager |
| logs básicos | Cloud Logging |

Un proyecto GCP delimita billing, IAM y recursos; región afecta latencia, disponibilidad, residencia y coste. Elige una región cercana y compatible con Cloud Run/Cloud SQL. VPC, load balancer, CDN, Cloud Storage y múltiples regiones quedan fuera si el servicio no los necesita.

### Cloud Run no es un servidor tradicional

- Las instancias pueden iniciar/detenerse y escalar horizontalmente.
- El filesystem local es efímero; estado durable va a servicios externos.
- Concurrency, CPU/memory, min/max instances y timeout son límites configurables.
- Cold start y scale-to-zero son trade-offs medibles, no defectos universales.
- La aplicación debe escuchar `PORT`, manejar `SIGTERM` y tolerar varias instancias.

### Managed vs self-hosted

Compara coste financiero, tiempo operativo, backups/restore, actualizaciones, observabilidad, compliance, lock-in y experiencia del equipo. Para este laboratorio usa Cloud Run y Cloud SQL: la decisión enseña el camino gestionado, no declara que sea siempre mejor.

### IAM como grafo de acceso

Pregunta: **qué identidad necesita qué acción sobre qué recurso y durante cuánto tiempo**.

- GitHub obtiene credencial efímera para publicar/desplegar.
- Cloud Run usa otra service account para leer solo sus secretos y conectar a su base.
- Invocación autenticada es el default del laboratorio.
- No uses roles Owner/Editor ni descargues claves permanentes para simplificar.

## Ejercicio único — Deploy reproducible y rollback

**Timebox:** **8–12 horas totales por sustrato**, compartidas entre el diagnóstico de 4.1, la preparación de 4.2 y este despliegue, según [PROYECTOS.md](../PROYECTOS.md#límites-comunes). No repartas ese presupuesto por archivo; detente antes si la evidencia está lista y elimina alcance al llegar al límite.

**Contexto proporcionado:** `safe-change-api` o un backend equivalente ya probado; proyecto sandbox sin usuarios ni datos reales; Cloud Run, Artifact Registry, Cloud SQL PostgreSQL, Secret Manager y GitHub Actions. La imagen y el pipeline ya vienen preparados por 4.1/4.2.

**Decisiones que debes tomar:** proyecto/región; presupuesto y teardown; grafo identidad → permiso → recurso; configuración de acceso; riesgo pendiente y motivo para conservar cualquier recurso.

1. Registra región, recursos, costo esperado y comando de teardown; activa alertas/presupuesto antes de crear recursos.
2. Crea Artifact Registry, Cloud Run, Cloud SQL PostgreSQL y Secret Manager con identidades separadas para CI/runtime.
3. Configura conexión a Cloud SQL y secretos sin incluir credenciales en imagen, repo o logs.
4. Ejecuta GitHub Actions: checks → build una vez → push por SHA → deploy del digest → smoke test autenticado.
5. Guarda commit, image digest, revisión de Cloud Run y salida del smoke test.
6. Despliega una segunda revisión inocua; dirige tráfico a ella y vuelve a la anterior sin rebuild.
7. Conserva la salida que demuestra que un principal no autorizado no puede invocar el servicio.
8. Conserva por separado la salida que demuestra que ese principal no puede leer el secreto.
9. Elimina recursos al terminar o documenta por qué permanecen y cuánto cuestan.

No añadas frontend, bucket, CDN, funciones, Kubernetes ni IaC. La [unidad 17](4.5%20—%20Observabilidad%20(Los%203%20Pilares).md) reutilizará estas revisiones y el rollback para agregar telemetría y un solo incidente; aquí bastan logs de plataforma y smoke test.

## Entregable y evidencia

- **Artefacto:** servicio desplegado y pipeline reproducible/reversible de la unidad 16.
- **Evidencia independiente:** checks, smoke test autenticado, digest/revisión, logs de entrega y rollback.
- **Casos negativos:** invocación denegada y lectura de secreto denegada, con salidas separadas.
- **Límite o riesgo:** coste observado, teardown y riesgo pendiente.

## Done cuando

- [ ] Un push autorizado produce una imagen identificada por SHA/digest.
- [ ] La revisión desplegada usa exactamente el digest registrado.
- [ ] El servicio se conecta a Cloud SQL y Secret Manager.
- [ ] No hay credenciales persistentes en repo, imagen ni CI.
- [ ] CI y runtime usan identidades distintas.
- [ ] Cada permiso concedido tiene una necesidad justificada.
- [ ] El smoke test autenticado funciona con una identidad válida.
- [ ] La prueba de invocación no autorizada falla como se esperaba.
- [ ] La prueba de lectura no autorizada del secreto falla como se esperaba.
- [ ] El registro relaciona commit, digest, revisión y logs de entrega.
- [ ] El rollback vuelve a una revisión anterior sin reconstruir la imagen.
- [ ] El coste observado queda registrado.
- [ ] Los recursos se eliminaron o quedó documentado por qué permanecen y cuánto cuestan.
- [ ] Explicaste problema, decisión, evidencia e incertidumbre.
- [ ] Completaste la recuperación R1 del cierre crítico.
