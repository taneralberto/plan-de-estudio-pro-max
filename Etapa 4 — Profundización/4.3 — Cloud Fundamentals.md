# 4.3 — Cloud Fundamentals

---

- [ ] **Los servicios que TODO dev debe conocer (AWS/GCP/Azure)**

Compute (EC2/Cloud Run/Droplets), Storage (S3/Cloud Storage/Spaces), Database managed (RDS/Cloud SQL), CDN (CloudFront/Cloud CDN), DNS (Route53/Cloud DNS), IAM (Identity and Access Management — roles, policies, least privilege), VPC (redes privadas virtuales — subnets, security groups, NAT). No los 200+ servicios — los 10 que usas el 90% del tiempo.

**Por qué importa:** Tu proyecto va a necesitar infraestructura cloud real en algún momento: un servidor para el backend, un bucket para imágenes y assets, un CDN para distribuir el frontend globalmente, una base de datos managed que alguien más respalde. Sin entender estos servicios, vas a tomar decisiones por defecto que son caras, inseguras o difíciles de escalar. IAM mal configurado es el vector de ataque número uno en cloud — la mayoría de los breaches de datos en AWS son por credentials con permisos excesivos.

**<span style="color: #29B6F6">Ejercicio:</span>** Despliega tu proyecto en AWS (Free Tier) o DigitalOcean. Usa: una instancia de cómputo para el backend, S3 (o DO Spaces) para storage de imágenes con una política de bucket que solo permita acceso público de lectura a los assets, CloudFront (o DO CDN) para distribuir el frontend, y RDS Postgres (o DO Managed DB) para la base de datos. Configura IAM roles con least privilege — el backend solo debe tener acceso al bucket específico del proyecto, no a todos los buckets de la cuenta.

**<span style="color: #FFA726">FreePress:</span>** FreePress necesita un bucket para imágenes, CloudFront para el frontend Angular, y RDS Postgres. Configura IAM roles para que el backend NestJS solo acceda al bucket de assets.

- [ ] **Serverless — Functions as a Service**

Lambda (AWS), Cloud Functions (GCP), Azure Functions. El modelo de ejecución: la función duerme, un evento la dispara, ejecuta, y vuelve a dormir. Cold starts (cuánto tarda en arrancar una función fría y cómo mitigarlo). Pricing model (pagas por invocación y tiempo de ejecución, no por servidor idle). Limitaciones: tiempo máximo de ejecución, no hay estado local persistente, networking más complejo dentro de VPC.

**Por qué importa:** Serverless no reemplaza a los servidores — resuelve un problema específico muy bien: ejecutar código en respuesta a eventos esporádicos sin pagar por infraestructura idle. Para un CMS, casos de uso naturales son: procesar imágenes cuando se suben (resize, optimize), enviar emails transaccionales, generar PDFs o exports. Usar un servidor dedicado para esas tareas es pagar 24/7 por algo que se ejecuta 100 veces por día. Serverless lo hace gratis (dentro del free tier).

**<span style="color: #29B6F6">Ejercicio:</span>** Implementa el procesamiento de imágenes como una función Lambda: cuando se sube una imagen a S3, la Lambda se dispara automáticamente, genera 3 versiones optimizadas (thumbnail, medium, original comprimido con Sharp), y las sube de vuelta a S3. Mide el cold start time y el costo estimado mensual para 1000 invocaciones.

**<span style="color: #FFA726">FreePress:</span>** Cuando un artículo se publica y se sube una imagen de portada, la Lambda procesa la imagen automáticamente — resize, thumbnails y compresión.

- [ ] **Managed Services vs Self-Hosted**

El trade-off central del cloud: cuándo delegarle la operación a alguien más (managed service) y cuándo asumirla tú (self-hosted). Ejemplos: RDS vs montar PostgreSQL en un EC2 tú mismo; Auth0/Clerk vs implementar auth desde cero; Elastic Cloud vs montar Elasticsearch en tu VPS; Cloudflare Workers vs tu propio CDN. El criterio no es el costo — es la ecuación entre costo operacional (tiempo de tu equipo) + costo financiero + control + lock-in.

**Por qué importa:** Cada managed service que usas es tiempo de operación que no gastas tú. RDS te da backups automáticos, failover, actualizaciones de seguridad y monitoreo — todo sin que toques nada. Pero también te cuesta 5x más que un Postgres self-hosted y te acopla al cloud provider. La decisión incorrecta en cualquier dirección tiene consecuencias: self-hosted todo es un segundo trabajo de sysadmin; managed todo puede volverse prohibitivamente caro o impedir migración futura.

**<span style="color: #29B6F6">Ejercicio:</span>** Para tu proyecto, toma 3 decisiones concretas de managed vs self-hosted con justificación escrita: (1) Base de datos: ¿managed Postgres o self-hosted? (2) Autenticación: ¿Clerk/Auth0 o implementación propia con JWT? (3) Search: ¿Algolia/Typesense Cloud o Elasticsearch self-hosted? Para cada decisión, documenta los criterios que usaste (costo, complejidad operacional, lock-in, requisitos de compliance).

**<span style="color: #FFA726">FreePress:</span>** Las decisiones clave para FreePress: (1) PostgreSQL managed, (2) autenticación con JWT propio, (3) búsqueda con Typesense o Elasticsearch.

**Done cuando:** Puedes recibir un nuevo proyecto con su contexto (etapa, equipo, presupuesto, requisitos de compliance) y producir una tabla de decisiones de managed vs self-hosted para los servicios principales, con justificación técnica y económica para cada elección. Puedes identificar cuándo el lock-in de un managed service es un riesgo real vs cuando es un trade-off aceptable.
