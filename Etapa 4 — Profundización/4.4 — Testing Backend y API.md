# 4.4 — Testing Backend y API

Testing es una disciplina de diseño: los tests te obligan a pensar en contratos, responsabilidades y límites ANTES de implementar.

> Los tipos de tests y cómo equilibrarlos se tratan en [1.3 — Testing Fundamentals](../Etapa%201%20—%20Entrada/1.3%20—%20Testing%20Fundamentals.md). Aquí se asumen esos fundamentos y se profundiza en backend, contratos y E2E.

---
- [ ] **Unit Testing — Qué testear y qué NO**

No testees implementación, testea comportamiento. La diferencia entre un test frágil (acoplado al "cómo") y un test robusto (acoplado al "qué"). Test doubles: mocks, stubs, spies, fakes — cuándo usar cada uno y por qué mockear TODO es un antipatrón. Coverage: mídelo pero no lo idolatres. Un 100% de coverage con mocks vacíos no vale nada.

**Por qué importa:** Los unit tests mal escritos son peor que no tener tests — te dan falsa confianza y se rompen con cada refactor, frenando el desarrollo en lugar de acelerarlo.

**<span style="color: #29B6F6">Ejercicio:</span>** Escribe tests unitarios para un servicio de tu proyecto usando Jest/Vitest. Practica la diferencia entre mock y stub en el mismo test suite. Después deliberadamente sobrescribe un test con mocks excesivos y explica por qué es un problema.

**<span style="color: #FFA726">FreePress:</span>** Prueba el servicio de artículos (ArticleService) de FreePress — es un buen candidato porque tiene lógica de negocio clara.

**Done cuando:** Puedes mirar un test y decir si está testeando comportamiento o implementación, justificar cuándo usar un stub vs un mock vs un fake, y refactorizar un test frágil sin cambiar lo que verifica.

**Recursos:**

- Libro: *Unit Testing: Principles, Practices, and Patterns* de Vladimir Khorikov — profundización en diseño y mantenibilidad de unit tests
- Artículo: *"Mocks Aren't Stubs"* de Martin Fowler — clarifica la terminología de una vez por todas

---
- [ ] **Integration Testing y API Testing**

Testear endpoints reales contra una base de datos real (no mocks). Testcontainers para levantar PostgreSQL en Docker durante los tests — el enfoque más confiable. Supertest para HTTP assertions en NestJS. Contract testing con Pact: verificar que el contrato entre cliente y servidor se respeta. Por qué los integration tests te dan más confianza que 100 unit tests con mocks.

**Por qué importa:** Un unit test puede pasar perfectamente mientras tu API devuelve un 500 en producción porque el ORM genera una query inválida. Los integration tests cierran esa brecha entre "funciona en aislamiento" y "funciona de verdad".

**<span style="color: #29B6F6">Ejercicio:</span>** Escribe integration tests para la API REST de tu proyecto que levanten PostgreSQL real con Testcontainers. Cubre al menos: crear un recurso, actualizarlo, listar con paginación, y un caso de error (ej: recurso no encontrado devuelve 404, no 500).

**<span style="color: #FFA726">FreePress:</span>** Prueba los endpoints de artículos: crear artículo, publicar artículo, listar artículos con paginación, y artículo no encontrado devuelve 404.

**Done cuando:** Tienes una suite de integration tests reproducible con un comando, que levanta una base de datos real y falla si el contrato de la API cambia sin querer. La automatizarás en CI al estudiar 4.2.

**Recursos:**

- [Testcontainers para Node.js](https://node.testcontainers.org/) — la forma correcta de testear con bases de datos reales
- [Supertest](https://github.com/ladjs/supertest) — HTTP assertions para Node.js
- [Pact](https://pact.io/) — contract testing entre servicios
- Artículo: *"Testing NestJS with Testcontainers"* — busca el más reciente, hay varios buenos

---
- [ ] **E2E Testing**

Playwright o Cypress para testear el flujo completo (frontend + backend + base de datos). Cuándo vale la pena y cuándo es overkill: los E2E son lentos, frágiles si se abusa de selectores de UI, y costosos de mantener. Test data management: fixtures, factories, cómo limpiar el estado entre tests. Visual regression testing con Playwright screenshots.

**Por qué importa:** Un E2E test es el único que verifica que el sistema COMPLETO funciona como lo vería un usuario real. No reemplaza los otros niveles — los complementa para los flujos críticos (login, publicar artículo, proceso de pago).

**<span style="color: #29B6F6">Ejercicio:</span>** Escribe tests E2E con Playwright para los flujos de mayor riesgo de tu proyecto y ejecútalos localmente con un comando reproducible. Intégralos al pipeline al estudiar 4.2.

**<span style="color: #FFA726">FreePress:</span>** Los 3 flujos críticos de FreePress son: (1) registro de usuario y primer login, (2) crear y publicar un artículo, (3) un editor intenta acceder a una ruta de admin y recibe 403.

**Done cuando:** Puedes decidir si un flujo merece un E2E test o no (justificado por costo/beneficio), escribir el test con Playwright, y hacerlo reproducible y diagnosticar su flakiness antes de automatizarlo en CI.

**Recursos:**

- [Playwright docs](https://playwright.dev/) — la herramienta que está ganando la batalla contra Cypress
- [Playwright Test Generator](https://playwright.dev/docs/codegen) — genera tests grabando interacciones, buen punto de partida
- Artículo: *"Testing Trophy"* de Kent C. Dodds — la filosofía aplica al backend también
