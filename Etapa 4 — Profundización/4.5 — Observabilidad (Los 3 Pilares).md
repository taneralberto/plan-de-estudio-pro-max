# 4.5 — Observabilidad y SRE

> **Estado:** `ACTIVO ★` · Unidad 18 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** servicio desplegado y reversible de la [unidad 17](4.3%20—%20Cloud%20Fundamentals.md).
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Detectar un síntoma, obtener evidencia suficiente para decidir, mitigar el impacto y recuperar servicio/datos. Observabilidad no es instalar tres productos: es poder formular preguntas nuevas sobre un sistema a partir de sus señales.

## Señales mínimas

### Logs estructurados

Registra eventos con campos estables y buscables:

- timestamp, level, service/revision y event name;
- request/trace ID para correlación;
- operación, resultado, duración y error con stack/cause;
- campos de dominio solo cuando ayudan a investigar.

No registres tokens, credenciales, bodies completos ni datos personales por defecto. Un `userId` puede ser sensible; usa identificadores mínimos, control de acceso y retención justificada. Los mensajes deben permitir actuar, no narrar cada línea del programa.

### Métricas

Para un servicio usa RED:

- **Rate:** requests elegibles por unidad de tiempo.
- **Errors:** proporción de requests que incumplen el resultado esperado.
- **Duration:** distribución de latencia, no solo promedio.

Para recursos usa USE: utilización, saturación y errores. No conviertas `requestId`, `userId`, URL completa o valores sin límite en labels: la alta cardinalidad vuelve costosas/inestables las series. Mantén esos IDs en logs o traces.

### Traces

Un trace conecta spans del mismo flujo mediante propagación de contexto. Instrumenta una frontera HTTP y una operación PostgreSQL con OpenTelemetry; añade más spans únicamente para responder una pregunta. Sampling reduce coste y puede ocultar casos raros, por lo que errores o tráfico de diagnóstico pueden requerir otra política.

Si hay un solo proceso y logs/métricas responden la pregunta, tracing adicional puede esperar.

## SLI, SLO y alertas

Un **SLI** es una medida del servicio desde la experiencia relevante. Ejemplos:

```text
availability = requests_exitosos / requests_elegibles
latency = requests_elegibles_bajo_umbral / requests_elegibles
```

Un **SLO** fija un objetivo y ventana para un SLI. El error budget es la fracción permitida de eventos malos (`1 - objetivo`) en esa ventana; no es permiso para ignorar incidentes.

Elige umbral y objetivo desde necesidad/medición, no por copiar “99.9 %”. Alerta sobre síntomas accionables y consumo rápido del budget. CPU alta sin impacto puede ser contexto; errores/latencia del servicio suelen ser mejor señal de guardia.

Una alerta debe indicar owner, impacto, evidencia inicial y runbook. Si nadie sabe qué acción tomar, todavía no está lista.

## Recuperación

### Runbook

Incluye:

1. síntoma/trigger y alcance;
2. dashboards, queries o comandos iniciales;
3. hipótesis frecuentes sin asumir causa;
4. mitigaciones seguras y cómo verificarlas;
5. rollback/roll-forward y stop condition;
6. escalación y comunicación;
7. recuperación de datos cuando aplique.

### RTO, RPO y restore

- **RTO:** tiempo máximo aceptable para restaurar el servicio.
- **RPO:** punto máximo de pérdida de datos aceptable, expresado como tiempo desde el último estado recuperable.

Un backup no es evidencia de recuperación hasta restaurarlo y verificar integridad. Mide tiempo real de restore y compara el estado recuperado con datos conocidos.

### Postmortem

Registra impacto, timeline, detección, condiciones contribuyentes, mitigación, recuperación y acciones con owner/señal de finalización. “Una persona cometió un error” no explica qué control permitió impacto; tampoco declares una única root cause si hubo varias condiciones.

## Ejercicio único — Incidente integrado

**Timebox:** hasta 120 minutos sobre el sandbox desplegado en la unidad 17. Si llegas al límite, conserva la evidencia y separa únicamente la señal o recuperación pendiente según la regla antiatasco; no instales otro stack. Usa Cloud Logging/Monitoring y OpenTelemetry con el backend disponible, no Loki, Prometheus, Grafana y Jaeger.

Antes de inyectar el fallo:

1. Define un SLI de éxito y uno de latencia, sus SLOs de laboratorio y una alerta por síntoma.
2. Añade logs estructurados con request/trace ID e instrumenta un flujo `POST /reservations` → PostgreSQL.
3. Escribe un runbook con rollback y verificación.
4. Crea un dataset pequeño conocido y un backup lógico reproducible; registra hora y checksum/conteo esperado.

Luego:

5. Despliega en el sandbox una revisión controlada que introduzca latencia o 5xx para un input sintético, sin exponer el hook a usuarios reales.
6. Genera tráfico, observa la alerta y localiza el flujo usando métrica → log → trace. Registra qué señal aportó cada decisión.
7. Ejecuta el rollback de Cloud Run previsto en la unidad 17 y comprueba que SLI/smoke test se recuperan.
8. Restaura el backup en una base temporal, verifica datos conocidos y mide restore. No sobrescribas la única copia.
9. Compara detección, mitigación y restore con SLO/RTO/RPO; escribe un postmortem breve y una acción preventiva verificable.

Si el tracing no está disponible en GCP, exporta temporalmente a consola o a un collector local. El objetivo es correlacionar un flujo, no operar otro stack.


## Done cuando

- [ ] Un síntoma genera una alerta accionable y puedes seguirlo por request/trace ID sin exponer datos sensibles.
- [ ] RED describe el servicio; USE se usa solo para investigar recursos relevantes.
- [ ] Puedes localizar el tramo lento/fallido en un trace o justificar por qué otra señal basta.
- [ ] El runbook permite rollback y verifica recuperación con smoke test/SLI.
- [ ] Restauraste datos en un destino temporal y comprobaste integridad, RTO y RPO observados.
- [ ] El postmortem separa impacto, evidencia, condiciones contribuyentes y acciones verificables.
- [ ] Documentaste qué no detectaría la instrumentación actual y cuándo mejorarla.
- [ ] Cumpliste artefacto, caso negativo y R1/R7/R30 del cierre crítico.
