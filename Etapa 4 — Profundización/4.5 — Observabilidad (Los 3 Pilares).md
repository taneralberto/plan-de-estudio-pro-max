# 4.5 — Observabilidad y SRE

> **Estado:** `ACTIVO ★` · Unidad 17 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** servicio desplegado y reversible de la [unidad 16](4.3%20—%20Cloud%20Fundamentals.md).
> **Cierre:** cumple el [cierre de una unidad crítica](../METODOLOGIA.md#cierre-de-una-unidad-crítica).

## Propósito

Detectar un síntoma, obtener evidencia suficiente para decidir, mitigar el impacto y recuperar servicio/datos. Observabilidad no es instalar tres productos: es poder formular preguntas nuevas sobre un sistema a partir de sus señales.

## Orientación

**Qué debes lograr:** detectar, explicar y recuperar un incidente pequeño usando la señal mínima que permita decidir.
**Cómo abordarlo:** prepara SLI/alerta/runbook, inyecta un fallo controlado, observa métricas y logs, añade trace solo si queda una pregunta abierta y ejecuta el rollback.
**Entregarás:** un paquete de incidente con alerta, runbook, timeline, evidencia de señales/recuperación y postmortem.
**Investiga fuera solo si:** una señal pendiente cambia el diagnóstico; el restore y el tracing adicional permanecen condicionales.

## Señales mínimas

### Logs estructurados

Registra eventos con campos estables y buscables:

- timestamp, level, service/revision y event name;
- request/trace ID para correlación;
- operación, resultado, duración y error con stack/cause;
- campos de dominio solo cuando ayudan a investigar.

No registres tokens, credenciales, bodies completos ni datos personales por defecto. Un `userId` puede ser sensible; usa identificadores mínimos, control de acceso y retención justificada. Los mensajes deben permitir actuar, no narrar cada línea del programa.

### Métricas

Para un servicio usa RED:

- **Rate:** requests elegibles por unidad de tiempo.
- **Errors:** proporción de requests que incumplen el resultado esperado.
- **Duration:** distribución de latencia, no solo promedio.

Para recursos usa USE: utilización, saturación y errores. No conviertas `requestId`, `userId`, URL completa o valores sin límite en labels: la alta cardinalidad vuelve costosas/inestables las series. Mantén esos IDs en logs o traces.

### Traces

Un trace conecta spans del mismo flujo mediante propagación de contexto. Si después de observar métricas y logs todavía no puedes aislar el tramo, instrumenta una frontera HTTP y una operación PostgreSQL con OpenTelemetry; añade más spans únicamente para responder esa pregunta.

Sampling reduce coste y puede ocultar casos raros, por lo que errores o tráfico de diagnóstico pueden requerir otra política. Si hay un solo proceso y logs/métricas responden la pregunta, tracing adicional puede esperar.

## SLI, SLO y alertas

Un **SLI** es una medida del servicio desde la experiencia relevante. Ejemplos:

```text
availability = requests_exitosos / requests_elegibles
latency = requests_elegibles_bajo_umbral / requests_elegibles
```

Un **SLO** fija un objetivo y ventana para un SLI. El error budget es la fracción permitida de eventos malos (`1 - objetivo`) en esa ventana; no es permiso para ignorar incidentes.

Elige umbral y objetivo desde necesidad/medición, no por copiar “99.9 %”. Alerta sobre síntomas accionables y consumo rápido del budget. CPU alta sin impacto puede ser contexto; errores/latencia del servicio suelen ser mejor señal de guardia.

Una alerta debe indicar owner, impacto, evidencia inicial y runbook. Si nadie sabe qué acción tomar, todavía no está lista.

## Recuperación

### Runbook

Incluye:

1. síntoma/trigger y alcance;
2. dashboards, queries o comandos iniciales;
3. hipótesis frecuentes sin asumir causa;
4. mitigaciones seguras y cómo verificarlas;
5. rollback/roll-forward y stop condition;
6. escalación y comunicación;
7. recuperación de datos cuando aplique.

### RTO, RPO y restore

- **RTO:** tiempo máximo aceptable para restaurar el servicio.
- **RPO:** punto máximo de pérdida de datos aceptable, expresado como tiempo desde el último estado recuperable.

El restore verificable tiene dueño en [2.6 — Migraciones Seguras](../Etapa%202%20—%20Fundamentos/2.6%20—%20Data%20Migrations%20y%20Schema%20Evolution.md). En esta unidad enlaza esa evidencia cuando exista y aplique; no repitas el laboratorio de backup/restore.

### Postmortem

Registra impacto, timeline, detección, condiciones contribuyentes, mitigación, recuperación y acciones con owner/señal de finalización. “Una persona cometió un error” no explica qué control permitió impacto; tampoco declares una única root cause si hubo varias condiciones.

## Ejercicio único — Incidente integrado

**Timebox:** hasta 120 minutos sobre el sandbox desplegado en la unidad 16. Si llegas al límite, conserva la evidencia y separa únicamente la señal pendiente según la regla antiatasco; no instales otro stack.

**Contexto proporcionado:** el servicio y rollback de unidad 16; Cloud Logging/Monitoring; una revisión controlada con latencia o 5xx para input sintético, sin usuarios reales.

**Decisiones que debes tomar:** SLI/SLO y umbral; síntoma de alerta; consultas iniciales; si un trace aporta al diagnóstico después de observar logs/métricas; mitigación y acción preventiva.

Antes de inyectar el fallo:

1. Define un SLI de éxito y uno de latencia, sus SLOs de laboratorio y una alerta por síntoma.
2. Añade logs estructurados con request ID.
3. Escribe un runbook con rollback, verificación y stop condition.

Luego:

4. Despliega la revisión controlada que introduce latencia o 5xx para el input sintético.
5. Genera tráfico, observa la alerta e intenta localizar el tramo con métricas y logs. Registra qué aportó cada señal.
6. Si métricas y logs no aíslan el tramo, instrumenta el trace mínimo `POST /reservations` → PostgreSQL, repite el tráfico sintético y registra qué decisión cambió. Si ya responden la pregunta, registra por qué no añadiste trace.
7. Ejecuta el rollback de Cloud Run previsto en la unidad 16 y comprueba que SLI/smoke test se recuperan.
8. Compara detección y mitigación con el SLO; enlaza RTO/RPO del restore de la unidad 10 solo si esa evidencia ya existe y aplica.
9. Escribe un postmortem breve con una acción preventiva verificable.

El objetivo es responder la pregunta operativa, no demostrar tres herramientas. La recuperación de datos se verifica una vez, en la unidad 10.

## Entregable y evidencia

- **Artefacto:** alerta, runbook, timeline y postmortem del único incidente.
- **Evidencia independiente:** SLI, salidas de métrica/log/trace condicional, revisiones y smoke test posterior al rollback.
- **Caso negativo:** revisión controlada que produce latencia o 5xx para tráfico sintético.
- **Límite o riesgo:** blind spots, incertidumbre y trigger concreto para mejorar instrumentación; restore enlazado solo si aplica.

## Done cuando

- [ ] El fallo sintético genera la alerta esperada.
- [ ] La alerta identifica owner, impacto y runbook.
- [ ] RED describe el síntoma del servicio sin exponer datos sensibles.
- [ ] Métricas y logs localizan el tramo o dejan explícita la pregunta pendiente.
- [ ] La decisión de añadir u omitir trace se tomó después de observar métricas y logs.
- [ ] Si se añadió trace, quedó registrada qué decisión permitió tomar.
- [ ] USE se reservó para recursos relevantes.
- [ ] El runbook ejecutó el rollback previsto.
- [ ] El smoke test y el SLI demuestran recuperación.
- [ ] El restore remite a la evidencia canónica de la unidad 10 cuando existe y aplica.
- [ ] El postmortem separa impacto, evidencia y condiciones contribuyentes.
- [ ] La acción preventiva tiene owner o señal verificable de finalización.
- [ ] Documentaste incertidumbre, blind spots y trigger de mejora.
- [ ] Explicaste problema, decisión, evidencia e incertidumbre.
- [ ] Completaste la recuperación R1 del cierre crítico.
