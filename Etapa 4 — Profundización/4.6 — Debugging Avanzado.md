- [ ] **Herramientas de debugging**

Node.js debugger con VS Code y Chrome DevTools (breakpoints condicionales, watch expressions, call stack, REPL en el contexto del breakpoint — infinitamente más útil que `console.log`). `strace` en Linux: intercepta y registra las syscalls de un proceso en tiempo real — cuando no sabes por qué un proceso se cuelga o falla sin output visible, `strace -p <pid>` te muestra qué está haciendo en el kernel. Wireshark y `tcpdump` para analizar tráfico de red: cuando el bug está en la comunicación entre dos servicios y los logs de ambos lados no muestran el problema. Heap snapshots y memory profiling en Node.js: identificar memory leaks tomando dos snapshots en momentos distintos y comparando qué objetos crecieron. Chrome Performance Recorder para CPU profiling del frontend.

**Por qué importa:** El 90% de los bugs en producción se pueden resolver con logs y métricas. El otro 10% — los bugs intermitentes, los memory leaks graduales, los problemas de red entre servicios — requieren herramientas más potentes. No conocerlas no significa que esos bugs no existan: significa que tardas 10 horas en resolver algo que con la herramienta correcta tomaría 30 minutos. `strace` y Wireshark no son herramientas de sysadmin — son herramientas de cualquier developer que trabaja en sistemas reales.

**<span style="color: #29B6F6">Ejercicio:</span>** Haz tres ejercicios de debugging con herramientas reales en tu proyecto: (1) Configura el Node.js debugger en VS Code para tu backend, pon un breakpoint condicional que solo se activa cuando el `userId` de un request es específico, y explora el call stack completo; (2) Simula un memory leak (ej: guardando objects en un array global que nunca se limpia) y detéctalo tomando dos heap snapshots con 30 segundos de diferencia en Chrome DevTools; (3) Usa `tcpdump` o Wireshark para capturar el tráfico HTTP entre el frontend y el backend y verifica que los headers de autenticación se envían correctamente.

**<span style="color: #FFA726">FreePress:</span>** Usa FreePress como proyecto de práctica para estos ejercicios — configura el debugger en el backend de NestJS y simula memory leaks en el proceso real.

**Done cuando:** Cuando tu proyecto tiene un memory leak en producción (la memoria del proceso crece gradualmente sin bajar), puedes identificar qué tipo de objeto está acumulándose usando heap snapshots sin necesidad de reiniciar el proceso. Puedes configurar el debugger de VS Code para adjuntarse a un proceso Node.js ya corriendo — no solo iniciar uno nuevo en modo debug.

**Recursos:**
- [Node.js Docs — Debugging Guide](https://nodejs.org/en/learn/getting-started/debugging) — la guía oficial para debuggear Node.js con VS Code y Chrome DevTools. El punto de partida para el ejercicio.
- [Chrome DevTools — Memory](https://developer.chrome.com/docs/devtools/memory-problems/) — la guía oficial para detectar memory leaks con heap snapshots. Incluye el flujo completo de toma y comparación de snapshots.
- [*"strace Wow Much Syscall"*](https://www.brendangregg.com/blog/2014-05-11/strace-wow-much-syscall.html) de Brendan Gregg — introducción práctica a `strace` con ejemplos reales. El autor también tiene el libro definitivo de performance en Linux (*Systems Performance*).
