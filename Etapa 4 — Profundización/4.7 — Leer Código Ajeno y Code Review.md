# 4.7 — Leer Código Ajeno y Revisar Cambios

> **Estado:** `ACTIVO ★` · Primera pasada de la unidad 19 del [ROADMAP](../ROADMAP.md).
> **Prerrequisitos:** backend verificable, sus comandos locales y una spec; unidades 3, 6 y 7.
> **Cierre:** prepara el mapa y los riesgos; la unidad se demuestra en [4.8 — Ingeniería con Coding Agents](4.8%20—%20AI%20Engineering%20(la%20nueva%20disciplina).md).

## Propósito

Construir un modelo suficiente de código ajeno para localizar un cambio, revisar su diff y formular riesgos comprobables. No hace falta entender todo el repositorio ni arreglar deuda incidental.

## Modelo mínimo

### Orientarse desde evidencia

Empieza por el propósito y README, scripts y dependencias, estructura, entrypoint, configuración, tests y fronteras externas. El framework sugiere convenciones, pero no demuestra la arquitectura real: confírmala en el código y sus puntos de entrada.

### Trazar un flujo y un fallo

Sigue una request backend desde el contrato HTTP hasta dominio y PostgreSQL. Después recorre un fallo desde un test o log hasta su causa. Anota archivos, invariantes, transformaciones y puntos con efectos externos; ese trazado permite revisar sin depender de la explicación del autor.

### Leer el cambio, no la explicación

Fija la revisión base y examina archivos y líneas cambiados, lockfiles, código generado y modificaciones no solicitadas. Compara el diff con las convenciones existentes y con el alcance. El resumen del autor o del agente orienta; no verifica la entrega.

### Smells son hipótesis, no hallazgos

Registra cada sospecha como `observación → riesgo o coste → evidencia → cambio mínimo o decisión de no tocar`. Un nombre de catálogo no prueba un defecto. Para modularidad y deuda, consulta [3.2 — Patrones de Arquitectura](../Etapa%203%20—%20Arquitectura/3.2%20—%20Patrones%20de%20Arquitectura%20Avanzados.md).

### Historial y debugging ajeno

Usa `git log`, `git blame` y tests para responder una hipótesis concreta: cuándo cambió una conducta, qué contrato se esperaba o dónde se desvía la ejecución. Evita leer historial por inercia, comprender todo el repositorio o refactorizar mientras investigas un fallo no relacionado.

## Preparación para la delegación

Sobre el Proyecto A, B u otro backend sanitizado, produce un mapa breve con:

- comandos de baseline y verificación;
- flujo feliz y un fallo;
- archivos probables del cambio;
- invariantes y resultado observable;
- límites externos y riesgos verificables.

Este mapa alimenta el único ejercicio de 4.8; no es otro ejercicio ni un entregable adicional.

## Primera pasada completa cuando

Puedes explicar el flujo, localizar el punto probable del cambio y formular riesgos verificables sin convertir sospechas en defectos.
